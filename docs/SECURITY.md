# SECURITY.md

# KeyKeeper2 Security Specification

Version: 2.0.0

Status: Draft

---

# 1. Purpose

Настоящий документ определяет требования к подсистеме безопасности проекта **KeyKeeper2**.

Документ описывает:

- архитектуру безопасности;
- модель доступа;
- аутентификацию пользователя;
- управление блокировкой устройства;
- защиту пользовательских данных;
- взаимодействие компонентов с подсистемой Security;
- требования к дальнейшему развитию криптографической защиты.

SECURITY.md является дополнением к документам:

- REQUIREMENTS.md
- ARCHITECTURE.md
- SOFTWARE.md
- STORAGE.md

---

# 2. Security Philosophy

Подсистема безопасности строится на следующих принципах.

- Security First
- Least Privilege
- Single Responsibility
- Fail Safe
- Defense in Depth
- Documentation First

Безопасность должна обеспечиваться архитектурой системы, а не отдельными функциями.

---

# 3. Security Goals

Подсистема безопасности должна обеспечивать:

- защиту пользовательских данных;
- защиту от случайного доступа;
- защиту от несанкционированного использования устройства;
- централизованную проверку разрешений;
- минимизацию хранения секретных данных в оперативной памяти;
- возможность дальнейшего внедрения криптографии.

---

# 4. Security Architecture

Подсистема Security является самостоятельным компонентом проекта.

```text
components/

security/
```

Все проверки безопасности выполняются только этим компонентом.

Никакой другой компонент проекта не должен самостоятельно принимать решения о предоставлении доступа.

---

## 4.1 Internal Structure

```text
SecurityService

├── PinManager

├── LockManager

├── SessionManager

└── PermissionManager
```

Каждый модуль имеет собственную область ответственности.

---

# 5. SecurityService

SecurityService является центральной точкой доступа ко всей подсистеме безопасности.

Все остальные компоненты проекта работают только через него.

---

## Responsibilities

SecurityService отвечает за:

- проверку PIN;
- управление блокировкой;
- управление пользовательской сессией;
- проверку разрешений;
- публикацию событий безопасности;
- координацию внутренних менеджеров.

---

## Public API

SecurityService предоставляет единый публичный интерфейс.

Например:

```text
lock()

unlock(pin)

isLocked()

checkPermission()

changePin()

startSession()

endSession()
```

Конкретная реализация определяется программным кодом.

---

# 6. PinManager

PinManager отвечает исключительно за работу с PIN-кодом.

---

## Responsibilities

Поддерживаются следующие операции:

- установка PIN;
- изменение PIN;
- проверка PIN;
- удаление PIN;
- проверка корректности PIN.

---

## PIN Requirements

Поддерживаемая длина:

- 4 цифры;
- 5 цифр;
- 6 цифр.

Допускаются только цифровые символы.

---

## Wrong Attempts

Подсистема должна учитывать количество неверных попыток ввода.

После успешного ввода PIN счётчик должен автоматически сбрасываться.

Конкретная политика ограничения попыток определяется настройками проекта.

---

# 7. LockManager

LockManager управляет состоянием устройства.

---

## Supported States

Поддерживаются состояния:

```text
Locked

Unlocked
```

В дальнейшем допускается расширение модели без изменения публичного API.

---

## Lock Sources

Устройство может быть заблокировано:

- после включения питания;
- вручную пользователем;
- автоматически по таймеру;
- после завершения пользовательской сессии.

---

## Unlock

Разблокировка выполняется после успешной проверки PIN через SecurityService.

Никакой другой компонент не имеет права самостоятельно изменять состояние блокировки.

---

# 8. SessionManager

SessionManager управляет пользовательской сессией.

---

## Responsibilities

Отвечает за:

- создание сессии;
- завершение сессии;
- контроль времени бездействия;
- автоматическую блокировку.

---

## Session Lifetime

Сессия начинается после успешной разблокировки устройства.

Сессия завершается:

- при ручной блокировке;
- после Auto Lock;
- после выключения устройства.

---

# 9. PermissionManager

PermissionManager определяет возможность выполнения защищённых операций.

Все проверки разрешений централизованы.

---

## Protected Operations

Проверка разрешений обязательна перед выполнением следующих действий:

- Print Password;
- Print OTP;
- Export Vault;
- Import Vault;
- Restore Backup;
- Change PIN;
- Security Settings;
- Web Login.

---

## Access Decision

PermissionManager возвращает одно из состояний:

```text
Allowed

Denied
```

При отказе операция не должна выполняться.

---

# 10. Device States

Подсистема безопасности использует фиксированную модель состояний устройства.

```text
Power On

↓

Locked

↓

PIN OK

↓

Unlocked

↓

Auto Lock

↓

Locked
```

Все переходы между состояниями выполняются только через SecurityService.

---

# 11. Auto Lock

Подсистема безопасности должна поддерживать автоматическую блокировку устройства.

Auto Lock предназначен для предотвращения несанкционированного доступа при отсутствии активности пользователя.

---

## 11.1 Timeout

Пользователь должен иметь возможность настроить время автоматической блокировки.

Рекомендуемые значения:

- Disabled;
- 30 секунд;
- 1 минута;
- 2 минуты;
- 5 минут;
- 10 минут.

После истечения заданного времени устройство автоматически переходит в состояние **Locked**.

---

## 11.2 Activity Detection

Таймер Auto Lock должен сбрасываться при следующих действиях пользователя:

- вращение энкодера;
- короткое нажатие;
- длинное нажатие;
- выполнение подтверждённой операции;
- взаимодействие с GUI.

Фоновые операции не должны сбрасывать таймер.

---

## 11.3 Immediate Lock

Пользователь должен иметь возможность немедленно заблокировать устройство.

После блокировки:

- GUI переходит на экран блокировки;
- закрываются все защищённые окна;
- очищаются временные данные;
- завершается активная пользовательская сессия.

---

# 12. Secure Operations

Все операции проекта разделяются на две категории:

- обычные;
- защищённые.

Обычные операции доступны всегда.

Защищённые операции требуют проверки SecurityService.

---

## 12.1 Public Operations

Не требуют разблокировки:

- отображение стартового экрана;
- просмотр информации об устройстве;
- изменение яркости дисплея;
- выбор языка (если разрешено настройками).

---

## 12.2 Protected Operations

Требуют успешной авторизации:

- просмотр списка аккаунтов;
- просмотр пароля;
- печать пароля;
- печать OTP;
- изменение PIN;
- изменение настроек безопасности;
- импорт базы;
- экспорт базы;
- восстановление резервной копии.

---

# 13. Quick Screen Security

Стартовый экран предназначен для максимально быстрого выполнения наиболее часто используемых действий.

Он работает даже при заблокированном устройстве, но с ограничениями безопасности.

---

## 13.1 Available Actions

Поддерживаются следующие действия:

```text
Short BACK → Unlock

Long BACK → Print Password

Short OK → Print URL
```

---

## 13.2 Print URL

Команда **Print URL** не требует разблокировки устройства.

Она отправляет через USB только адрес страницы, связанный с паролем по умолчанию.

Если URL не задан, операция завершается без выполнения каких-либо действий.

---

## 13.3 Print Password

Команда **Print Password** предназначена для быстрого ввода заранее настроенного пароля.

Используется пароль по умолчанию, сохранённый в настройках устройства.

Если пароль отсутствует или поле пустое, операция не выполняется.

---

## 13.4 Unlock

Команда **Unlock** переводит пользователя на экран ввода PIN.

После успешной проверки PIN становится доступен полный функционал устройства.

---

# 14. USB Security

Все операции передачи данных через USB должны проходить проверку безопасности.

USBService не имеет прямого доступа к Vault.

---

## Protected USB Operations

Проверка обязательна перед:

- Print Password;
- Print OTP;
- пользовательскими макросами;
- последовательной отправкой защищённых данных.

---

## Public USB Operations

Допускается выполнение без разблокировки:

- Print URL с Quick Screen;
- передача служебной информации, не содержащей конфиденциальных данных.

---

# 15. Web Security

Локальный Web UI использует SecurityService для проверки доступа.

---

## Authentication

Перед открытием защищённых разделов Web UI должна выполняться авторизация.

После блокировки устройства доступ через Web UI автоматически прекращается.

---

## Session Control

Web UI использует ту же пользовательскую сессию, что и устройство.

После завершения сессии все защищённые страницы должны стать недоступны.

---

# 16. Storage Security

Storage Layer отвечает только за хранение данных.

Storage не принимает решений о безопасности.

Все проверки выполняются SecurityService.

---

## Access Rules

StorageProvider обязан выполнять операции только после получения разрешения через соответствующий сервис.

Прямой доступ GUI к файловой системе запрещён.

---

## Temporary Data

Временные файлы должны удаляться после завершения операции.

При отмене импорта или экспорта не должно оставаться временных данных.

---

# 17. Memory Protection

Конфиденциальная информация должна храниться в оперативной памяти минимально возможное время.

---

## Sensitive Data

К конфиденциальным данным относятся:

- PIN;
- пароль;
- OTP;
- секретные ключи;
- содержимое Vault.

---

## Memory Cleanup

После завершения использования буферы, содержащие конфиденциальные данные, должны очищаться.

Это относится как к оперативной памяти, так и к временным структурам данных.

---

# 18. EventBus Security

Все события безопасности публикуются через EventBus.

Примеры событий:

```text
DeviceLocked

DeviceUnlocked

PinChanged

PinVerified

PermissionGranted

PermissionDenied

SessionStarted

SessionEnded

AutoLockActivated
```

Другие компоненты могут подписываться на эти события, но не должны изменять состояние Security напрямую.

---

# 19. Future Security Features

Архитектура подсистемы безопасности должна предусматривать возможность расширения без изменения публичного API.

Планируемые возможности:

- AES-256 Encryption;
- Secure Element;
- аппаратное хранение ключей;
- многоуровневые разрешения;
- несколько пользователей;
- журнал безопасности;
- аппаратная аутентификация;
- защищённое резервное копирование.

Все новые функции должны интегрироваться через SecurityService.

---

# 20. Summary

Подсистема **Security** является самостоятельным компонентом архитектуры **KeyKeeper2** и обеспечивает централизованное управление безопасностью устройства.

Все проверки PIN, управление блокировкой, пользовательскими сессиями и разрешениями выполняются исключительно через **SecurityService**.

Такое разделение соответствует принципам **Security First**, **Single Responsibility Principle (SRP)** и **Documentation First**, обеспечивая чистую, расширяемую и безопасную архитектуру проекта.

Настоящий документ является обязательной частью архитектурной документации и должен поддерживаться в актуальном состоянии совместно с **REQUIREMENTS.md**, **ARCHITECTURE.md** и **SOFTWARE.md**.
