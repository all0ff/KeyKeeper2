# CODING_STANDARD.md

# KeyKeeper2 Coding Standard

Version: 2.0.0

Status: Draft

---

# 1. Purpose

Настоящий документ определяет единые правила написания исходного кода проекта **KeyKeeper2**.

Документ предназначен для:

- обеспечения единого стиля разработки;
- повышения читаемости кода;
- упрощения сопровождения проекта;
- уменьшения количества ошибок;
- облегчения совместной разработки.

Настоящий документ является обязательным для всех компонентов проекта.

---

# 2. Development Philosophy

Проект строится на следующих принципах:

- Documentation First;
- Architecture Before Code;
- Readability First;
- Simplicity;
- Single Responsibility;
- Component Isolation;
- Event-Driven Architecture.

Красивый код менее важен, чем понятный код.

Простой код предпочтительнее сложного.

---

# 3. General Rules

Все новые модули должны соответствовать архитектуре проекта.

Запрещается:

- писать код без документации;
- нарушать архитектурные границы компонентов;
- обращаться к внутренним компонентам напрямую;
- дублировать существующую функциональность.

Перед написанием нового кода необходимо ознакомиться с:

- ARCHITECTURE.md;
- SOFTWARE.md;
- AI_PROMPT.md;
- соответствующим ADR.

---

# 4. Project Structure

Исходный код располагается только в предусмотренных каталогах.

Основная структура проекта:

```text
components/
main/
```

Каждый компонент должен иметь собственную директорию.

Например:

```text
components/

gui/
vault/
storage/
security/
usb/
wifi/
web/
settings/
system/
bsp/
```

Запрещается размещать код компонентов вне каталога `components/`.

---

# 5. File Organization

Каждый компонент должен иметь предсказуемую структуру.

Рекомендуемый пример:

```text
component/

include/
src/
tests/
CMakeLists.txt
README.md
```

Если компонент не содержит тестов или дополнительной документации, соответствующие каталоги могут отсутствовать.

---

## Header Files

Заголовочные файлы содержат:

- объявления классов;
- перечисления;
- структуры;
- интерфейсы;
- публичные константы.

В заголовочных файлах не должна размещаться сложная реализация.

---

## Source Files

Файлы `.cpp` содержат реализацию.

Каждый файл должен иметь одну основную область ответственности.

Если размер файла становится чрезмерным, его следует разделить на несколько логически связанных файлов.

---

# 6. Naming Conventions

Во всём проекте используется единый стиль именования.

---

## Classes

Имена классов используют стиль:

```text
PascalCase
```

Примеры:

```cpp
VaultService

SecurityService

StorageProvider

ScreenManager
```

---

## Interfaces

Абстрактные интерфейсы начинаются с буквы `I`.

Примеры:

```cpp
IStorageProvider

IUsbDevice

ILogger
```

---

## Functions

Имена функций используют стиль:

```text
camelCase
```

Примеры:

```cpp
loadVault()

saveVault()

printPassword()

unlockSession()
```

Функции должны описывать выполняемое действие.

---

## Variables

Переменные используют стиль:

```text
camelCase
```

Примеры:

```cpp
vaultFile

selectedItem

currentScreen

sessionTimeout
```

Следует избегать сокращений, не являющихся общеупотребительными.

---

## Constants

Константы используют стиль:

```cpp
constexpr
```

Имена записываются в стиле:

```text
kPascalCase
```

Пример:

```cpp
constexpr uint32_t kDefaultTimeout = 30000;
```

---

## Enum

Перечисления используют PascalCase.

Элементы перечислений также используют PascalCase.

Пример:

```cpp
enum class LockState
{
    Locked,
    Unlocked,
    Waiting
};
```

---

# 7. Include Rules

Каждый файл должен подключать только необходимые заголовочные файлы.

Порядок подключения:

1. собственный заголовочный файл;
2. стандартная библиотека C++;
3. ESP-IDF;
4. сторонние библиотеки;
5. заголовки проекта.

Например:

```cpp
#include "VaultService.hpp"

#include <memory>
#include <string>

#include "esp_log.h"

#include "lvgl.h"

#include "EventBus.hpp"
```

Неиспользуемые `#include` должны удаляться.

---

# 8. C++ Style

Проект использует современный стандарт **C++20**.

Следует использовать возможности языка только в тех случаях, когда они действительно повышают читаемость и надёжность кода.

---

## Recommended Features

Разрешается использовать:

- `constexpr`;
- `enum class`;
- `std::array`;
- `std::span`;
- `std::optional`;
- `std::string_view`;
- `std::unique_ptr`;
- `std::shared_ptr` (при необходимости);
- range-based for;
- `override`;
- `final`;
- `= default`;
- `= delete`.

---

## Avoid

Следует избегать:

- глобальных переменных;
- макросов вместо `constexpr`;
- множественного наследования (без необходимости);
- сложных шаблонных конструкций;
- неочевидных сокращений.

Код должен быть максимально понятным.

---

# 9. Classes

Каждый класс должен иметь одну область ответственности.

Не допускается создание "универсальных" классов.

---

## Single Responsibility

Например:

```text
VaultService
```

отвечает только за работу с Vault.

```text
StorageService
```

не должен выполнять:

- проверку PIN;
- шифрование;
- работу GUI.

Эти задачи относятся к другим компонентам.

---

## Constructors

Конструкторы должны выполнять только инициализацию объекта.

Запрещается:

- открывать файлы;
- запускать задачи;
- выполнять длительные операции;
- обращаться к сети.

Такие действия должны выполняться отдельными методами.

---

## Dependencies

Зависимости следует передавать через конструктор или интерфейс.

Например:

```cpp
class VaultService
{
public:
    explicit VaultService(IStorageProvider& storage);
};
```

Это упрощает тестирование и замену реализаций.

---

# 10. Functions

Каждая функция должна выполнять одно логически завершённое действие.

---

## Function Size

Рекомендуемый размер функции:

- до 30 строк — предпочтительно;
- до 50 строк — допустимо;
- более 50 строк — рекомендуется разделить.

Это правило носит рекомендательный характер и не является жёстким ограничением.

---

## Parameters

Следует:

- передавать большие объекты по `const&`;
- использовать `std::string_view` для неизменяемых строк;
- избегать большого количества параметров.

Если параметров становится слишком много, следует использовать структуру параметров.

---

## Return Values

Функция должна возвращать результат своей работы.

Не следует использовать выходные параметры без необходимости.

Например:

```cpp
bool loadVault();

Account findAccount();

std::optional<Account> findById();
```

---

# 11. Error Handling

Обработка ошибок должна быть предсказуемой и единообразной.

---

## General Rules

Необходимо:

- проверять результат операций;
- обрабатывать ошибки на соответствующем уровне;
- не игнорировать возвращаемые значения.

---

## Exceptions

Проект не использует исключения C++.

Ошибки должны передаваться:

- кодом возврата;
- `std::optional`;
- `std::expected` (при появлении поддержки);
- специализированными структурами результата.

---

## Assertions

`assert()` допускается использовать только для проверки внутренних предположений во время разработки.

Проверка пользовательских данных должна выполняться обычной логикой программы.

---

# 12. Memory Management

Управление памятью должно быть максимально безопасным.

---

## Dynamic Allocation

Следует минимизировать динамическое выделение памяти.

Если выделение необходимо, рекомендуется использовать RAII и умные указатели.

---

## Ownership

Право владения объектом должно быть очевидным.

Не допускается наличие неясного владельца ресурса.

---

## Raw Pointers

Обычные указатели могут использоваться только как невладеющие ссылки на объект.

Использование `new` и `delete` напрямую должно быть сведено к минимуму.

---

# 13. EventBus Usage

Взаимодействие компонентов осуществляется через **EventBus**.

---

## Allowed

Разрешается:

```text
GUI

↓

EventBus

↓

VaultService
```

или

```text
USBService

↓

EventBus

↓

SecurityService
```

---

## Forbidden

Запрещается:

```text
GUI

↓

StorageService
```

или

```text
Vault

↓

GUI
```

Компоненты не должны зависеть друг от друга напрямую, если это противоречит архитектуре.

---

## Events

События должны быть:

- небольшими;
- независимыми;
- легко сериализуемыми;
- понятными по названию.

---

# 14. Logging

Для журналирования используется единая система логирования проекта.

---

## Rules

Каждый компонент должен использовать собственный TAG.

Например:

```cpp
static constexpr const char* TAG = "Vault";
```

или

```cpp
static constexpr const char* TAG = "Storage";
```

---

## Log Levels

Используются стандартные уровни ESP-IDF:

- Error;
- Warning;
- Info;
- Debug;
- Verbose.

---

## Sensitive Data

Запрещается записывать в журнал:

- пароль;
- PIN;
- OTP;
- ключи шифрования;
- содержимое Vault.

Конфиденциальная информация никогда не должна появляться в логах.

---

# 15. Documentation & Code Review

Любой новый код должен сопровождаться актуальной документацией.

---

## Documentation

При изменении архитектуры необходимо обновить:

- ARCHITECTURE.md;
- SOFTWARE.md;
- соответствующий ADR;
- AI_PROMPT.md (при необходимости).

Документация является частью результата разработки.

---

## Code Review Checklist

Перед включением изменений рекомендуется проверить:

- соответствие архитектуре;
- соблюдение Coding Standard;
- отсутствие дублирования кода;
- читаемость;
- корректность обработки ошибок;
- отсутствие утечек памяти;
- отсутствие нарушения компонентных границ;
- актуальность документации.

---

# 16. Summary

Настоящий документ определяет единый стандарт разработки проекта **KeyKeeper2**.

Соблюдение данных правил обеспечивает единообразие исходного кода, упрощает сопровождение проекта и снижает вероятность архитектурных ошибок.

Все новые компоненты должны соответствовать требованиям настоящего стандарта, архитектурной документации и принятым архитектурным решениям (ADR). Любые изменения, затрагивающие структуру проекта или принципы разработки, должны сопровождаться обновлением документации и, при необходимости, созданием нового ADR.
