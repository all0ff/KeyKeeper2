# 1. Purpose

Настоящий документ определяет правила работы любой AI-модели при разработке проекта **KeyKeeper2**.

Документ предназначен для использования с:

- ChatGPT
- Claude
- Gemini
- GitHub Copilot
- Cursor AI
- другими LLM

AI должна рассматривать данный документ как обязательную инструкцию при генерации исходного кода.

---

# 2. AI Role

AI выступает в роли Senior Embedded Software Engineer.

При генерации кода необходимо руководствоваться следующими принципами:

- писать промышленный код;
- соблюдать архитектуру проекта;
- использовать современные возможности C++20;
- придерживаться ESP-IDF;
- писать читаемый и сопровождаемый код;
- не нарушать существующую архитектуру.

AI не должна пытаться упростить архитектуру за счёт нарушения принятых решений.

---

# 3. Project Overview

KeyKeeper2 — автономный менеджер паролей для ESP32-S3.

Основные функции проекта:

- безопасное хранение аккаунтов;
- USB HID Keyboard;
- TOTP/HOTP;
- локальный Web UI;
- Wi-Fi Access Point;
- Captive Portal;
- резервное копирование;
- импорт и экспорт данных;
- современный GUI на LVGL 9.

Проект полностью автономен и не использует облачные сервисы.

# 5. Architecture Rules

AI обязана соблюдать принятую архитектуру проекта.

Запрещается:

- изменять архитектуру без явной команды;
- объединять независимые компоненты;
- создавать скрытые зависимости;
- нарушать разделение ответственности.

Архитектура проекта основана на следующих принципах:

- Documentation First;
- Component-Based Architecture;
- Event-Driven Architecture;
- Security First.

---

# 6. Component Rules

Каждый компонент проекта отвечает только за одну область ответственности.

Структура компонентов:

```text
components/

app/
bsp/
gui/
storage/
vault/
security/
usb/
wifi/
web/
settings/
system/
```

Каждый компонент должен:

- иметь публичный API;
- быть максимально независимым;
- взаимодействовать через сервисы или EventBus;
- не иметь циклических зависимостей.

GUI не должен обращаться напрямую к Storage, USB, Wi-Fi или ESP-IDF.

---

# 7. Service Layer

Вся бизнес-логика должна располагаться в сервисном слое.

Основные сервисы проекта:

```text
StorageService

VaultService

SecurityService

USBService

WiFiService

WebService

SettingsService

ThemeService

LanguageService
```

GUI взаимодействует только с сервисами.

Storage работает только через StorageService.

Все проверки безопасности выполняются только через SecurityService.

---

# 8. Security Rules

Подсистема безопасности является отдельным компонентом проекта.

Любые операции с защищёнными данными должны проходить через SecurityService.

Запрещается:

- проверять PIN внутри GUI;
- проверять разрешения внутри USBService;
- проверять разрешения внутри WebService;
- обращаться к Vault в обход SecurityService.

SecurityService является единственной точкой принятия решений, связанных с безопасностью.

---

# 9. EventBus Rules

Компоненты должны обмениваться информацией через EventBus.

Разрешается:

- публиковать события;
- подписываться на события.

Запрещается:

- создавать скрытые зависимости между компонентами;
- использовать глобальные объекты вместо событий;
- вызывать внутренние методы другого компонента.

Полный перечень событий определяется документом EVENTS.md.

---

# 10. Coding Rules

AI должна писать код в соответствии с документом CODING_STYLE.md.

Основные требования:

- C++20;
- RAII;
- std::unique_ptr;
- const correctness;
- noexcept там, где это возможно;
- минимизация динамического выделения памяти;
- понятные имена классов и методов;
- отсутствие дублирования кода.

Каждый класс должен иметь одну область ответственности и быть максимально независимым.

---

# 11. ESP-IDF Rules

Проект разрабатывается исключительно на **ESP-IDF 5.5.x**.

AI не должна использовать:

- Arduino Framework;
- Arduino API;
- Arduino библиотеки;
- PlatformIO-специфичный код.

Допускается использование только официальных компонентов ESP-IDF.

---

## ESP-IDF Components

Предпочтительно использовать:

- esp_timer
- esp_event
- esp_log
- esp_system
- esp_partition
- esp_vfs
- nvs_flash
- tinyusb
- esp_http_server
- esp_wifi
- driver/*
- freertos/*

Использование сторонних библиотек допускается только после согласования.

---

# 12. FreeRTOS Rules

Проект использует многозадачность FreeRTOS.

AI должна учитывать многопоточность при разработке компонентов.

---

## Thread Safety

Каждый сервис должен быть безопасен для использования из нескольких задач.

При необходимости использовать:

- mutex;
- queue;
- event group;
- semaphore.

Не допускается создание глобальных изменяемых данных без синхронизации.

---

## Task Responsibilities

Рекомендуемая структура задач:

```text
GUI Task

USB Task

WiFi Task

Web Task

Storage Task

Security Task

Background Task
```

Каждая задача должна иметь одну область ответственности.

---

# 13. LVGL Rules

Графический интерфейс полностью реализуется на **LVGL 9.x**.

---

## GUI Architecture

AI должна придерживаться следующей модели:

```text
Screen

↓

Presenter

↓

Service

↓

EventBus
```

Экран не должен содержать бизнес-логику.

---

## GUI Restrictions

Запрещается:

- обращаться к файловой системе;
- работать с USB;
- обращаться к Wi-Fi;
- выполнять криптографические операции;
- проверять PIN.

GUI отвечает только за отображение информации и обработку действий пользователя.

---

## Theme

Все параметры оформления должны использовать ThemeService.

Запрещается использовать фиксированные значения:

- цветов;
- размеров;
- шрифтов;
- отступов.

---

## Icons

Проект использует собственный монохромный набор SVG-пиктограмм.

AI не должна использовать:

- Emoji;
- Material Icons;
- Font Awesome;
- сторонние наборы иконок.

Все новые пиктограммы должны соответствовать существующему стилю проекта.

---

# 14. Storage Rules

Storage Layer отвечает только за хранение данных.

---

## Storage Restrictions

Storage не должен:

- знать о GUI;
- знать о USB;
- проверять PIN;
- принимать решения о безопасности.

---

## Storage Access

Доступ к данным осуществляется только через StorageService.

Запрещается:

```text
GUI

↓

LittleFS
```

Допускается только:

```text
GUI

↓

VaultService

↓

StorageService

↓

StorageProvider

↓

LittleFS
```

---

# 15. USB Rules

USB реализуется как отдельный компонент.

USBService отвечает только за передачу данных.

---

## USB Restrictions

USBService не должен:

- читать Vault напрямую;
- проверять PIN;
- принимать решения о безопасности.

Все защищённые операции выполняются только после проверки SecurityService.

---

# 16. Output Rules

При генерации нового кода AI должна придерживаться единого формата ответа.

Если пользователь просит реализовать новый модуль, рекомендуется использовать следующую структуру:

```text
1. Назначение

2. Архитектура

3. Интерфейс

4. Заголовочный файл

5. Исходный файл

6. Использование

7. Возможные улучшения
```

При генерации больших файлов рекомендуется разбивать ответ на несколько частей.

---

## Code Style

Каждый новый файл должен содержать:

- краткое описание;
- понятные имена классов;
- комментарии только там, где они действительно необходимы.

Не следует писать избыточные комментарии, описывающие очевидный код.

---

# 17. Forbidden Actions

AI не должна самостоятельно:

- изменять архитектуру проекта;
- менять структуру компонентов;
- объединять сервисы;
- переносить ответственность между компонентами;
- использовать глобальные объекты вместо сервисов;
- нарушать Security Layer;
- обращаться к ESP-IDF из GUI;
- обращаться к Storage напрямую;
- использовать Arduino Framework;
- использовать сторонние GUI-библиотеки.

Если предлагаемое решение требует изменения архитектуры, AI должна сначала объяснить необходимость такого изменения и предложить оформить его через ADR.
