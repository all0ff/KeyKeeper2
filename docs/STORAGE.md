# STORAGE.md

# KeyKeeper2 Storage Design Specification

Version: 2.0.0

Status: Draft

---

# 1. Purpose

Настоящий документ определяет архитектуру подсистемы хранения данных проекта **KeyKeeper2**.

Документ описывает:

- организацию хранения данных;
- структуру файлов;
- интерфейсы доступа к данным;
- резервное копирование;
- импорт и экспорт;
- взаимодействие Storage с другими компонентами проекта.

STORAGE.md является дополнением к документам:

- REQUIREMENTS.md
- ARCHITECTURE.md
- SOFTWARE.md
- SECURITY.md

---

# 2. Storage Overview

Storage Layer отвечает исключительно за долговременное хранение пользовательских данных.

Подсистема не содержит бизнес-логики и не принимает решений, связанных с безопасностью.

Все операции выполняются через сервисный слой.

---

## Responsibilities

Storage Layer отвечает за:

- сохранение данных;
- загрузку данных;
- резервное копирование;
- восстановление;
- импорт;
- экспорт;
- управление файловой структурой.

Storage Layer не отвечает за:

- проверку PIN;
- проверку разрешений;
- работу GUI;
- USB;
- Wi-Fi;
- Web UI.

---

# 3. Design Principles

Подсистема хранения строится на следующих принципах:

- Single Responsibility;
- Documentation First;
- Layer Separation;
- Storage Independence;
- File System Abstraction;
- Reliability First.

Любая файловая система должна быть заменяемой без изменения логики приложения.

---

# 4. Storage Architecture

Подсистема хранения представляет собой отдельный компонент проекта.

```text
components/

storage/
```

Доступ к данным осуществляется по следующей схеме:

```text
GUI

↓

VaultService

↓

StorageService

↓

StorageProvider

↓

LittleFS / microSD
```

GUI и другие компоненты не должны обращаться к файловой системе напрямую.

---

## Security Boundary

Storage не выполняет проверку прав доступа.

Перед обращением к Storage защищённые операции должны быть подтверждены через **SecurityService**.

Storage получает только уже авторизованные запросы.

---

# 5. Storage Components

Подсистема хранения состоит из следующих компонентов:

```text
StorageService

↓

StorageProvider

↓

LittleFSProvider

↓

SDProvider
```

Каждый компонент имеет одну область ответственности.

---

## StorageService

StorageService является единственной публичной точкой доступа к подсистеме хранения.

Он отвечает за:

- открытие базы данных;
- сохранение данных;
- загрузку данных;
- создание резервных копий;
- восстановление;
- импорт;
- экспорт.

StorageService не содержит информации о структуре GUI и не взаимодействует с пользователем напрямую.

---

## StorageProvider

StorageProvider определяет общий интерфейс доступа к физическому носителю данных.

Он скрывает особенности конкретной файловой системы.

Основные операции:

- Open;
- Close;
- Read;
- Write;
- Remove;
- Exists;
- Rename;
- Create Directory;
- List Files.

---

## LittleFSProvider

Реализует StorageProvider для встроенной Flash-памяти.

Используется как основной носитель данных.

---

## SDProvider

Реализует StorageProvider для карты памяти microSD.

Используется для:

- резервного копирования;
- импорта;
- экспорта;
- хранения пользовательских архивов.

При отсутствии microSD соответствующие функции должны быть недоступны, не влияя на работу основной базы данных.

---

# 6. StorageService

StorageService инкапсулирует всю работу с подсистемой хранения.

Все остальные компоненты проекта используют только его публичный API.

---

## Responsibilities

StorageService отвечает за:

- выбор StorageProvider;
- открытие базы данных;
- сохранение изменений;
- управление резервными копиями;
- контроль целостности операций;
- публикацию событий через EventBus.

---

## Access Rules

Разрешается:

```text
VaultService

↓

StorageService
```

Запрещается:

```text
GUI

↓

LittleFS
```

или

```text
USBService

↓

StorageProvider
```

Все обращения должны проходить через StorageService.

---

# 7. StorageProvider

StorageProvider представляет собой абстрактный интерфейс файлового хранилища.

Это позволяет заменить файловую систему без изменения логики приложения.

---

## Supported Backends

Предусматривается поддержка:

- LittleFS;
- microSD.

Архитектура допускает добавление других типов хранилищ в будущем.

---

## Provider Responsibilities

Каждый Provider отвечает только за операции файловой системы.

Он не должен:

- знать структуру Vault;
- проверять права доступа;
- выполнять шифрование;
- взаимодействовать с GUI.

---

# 8. Vault Database

Основные пользовательские данные хранятся в файле:

```text
vault.db
```

Формат базы данных определяется компонентом **Vault**.

Storage отвечает только за сохранение и загрузку файла.

---

## Database Responsibilities

Файл `vault.db` содержит:

- учётные записи;
- категории;
- OTP;
- пользовательские настройки Vault;
- служебные данные Vault.

Storage не анализирует содержимое файла.

---

## Database Version

Каждая база данных должна содержать номер версии формата.

Это позволяет выполнять миграцию данных при обновлении прошивки.

---

# 9. File Structure

Подсистема хранения использует фиксированную структуру каталогов.

Пример:

```text
/

vault.db

metadata.json

backup/

logs/

temp/

icons/
```

При необходимости структура может быть расширена без нарушения совместимости.

---

## vault.db

Основной файл пользовательских данных.

Обязателен для работы устройства.

---

## metadata.json

Содержит служебную информацию.

Например:

- версия формата;
- версия приложения;
- дата создания;
- дата последнего изменения.

Данный файл не содержит конфиденциальных данных.

---

## backup/

Каталог резервных копий.

Каждая резервная копия хранится отдельным файлом.

---

## logs/

Каталог диагностических журналов.

Используется только при включённом журналировании.

Запись конфиденциальной информации запрещена.

---

## temp/

Каталог временных файлов.

Используется во время:

- импорта;
- экспорта;
- восстановления.

После завершения операции временные файлы должны удаляться автоматически.

---

## icons/

Дополнительный каталог для пользовательских ресурсов.

Его использование не является обязательным и может быть отключено в сборке проекта.

---

# 10. Backup

Подсистема хранения должна поддерживать создание резервных копий.

Все операции выполняются через StorageService.

---

## Backup Operations

Поддерживаются:

- Create Backup;
- List Backups;
- Restore Backup;
- Delete Backup.

---

## Backup Location

Резервные копии могут храниться:

- во внутренней памяти;
- на карте microSD.

Выбор места хранения определяется настройками проекта.

---

## Backup Naming

Рекомендуемый формат имени файла:

```text
backup_YYYYMMDD_HHMMSS.kkb
```

Например:

```text
backup_20260806_143015.kkb
```

---

## Backup Validation

Перед восстановлением резервная копия должна быть проверена.

Проверяются:

- существование файла;
- корректность структуры;
- версия формата;
- целостность данных.

При ошибке восстановление не выполняется.

---

# 11. Import / Export

Поддерживаются операции импорта и экспорта пользовательской базы данных.

---

## Export

Экспорт создаёт независимую копию текущей базы данных.

Экспорт не изменяет существующую базу.

---

## Import

Импорт заменяет или дополняет существующую базу данных в соответствии с выбранным режимом.

Перед импортом должна выполняться проверка структуры импортируемого файла.

---

## Security

Импорт и экспорт относятся к защищённым операциям.

Перед выполнением должна быть выполнена проверка через **SecurityService**.

StorageService получает только авторизованный запрос.

---

# 12. Cache

Подсистема хранения может использовать внутреннее кэширование.

Кэш предназначен исключительно для повышения производительности.

---

## Cached Data

Допускается кэширование:

- структуры базы;
- списка файлов;
- часто используемых метаданных.

Конфиденциальные данные не должны храниться в кэше дольше необходимого.

---

## Cache Invalidation

Кэш должен автоматически обновляться после:

- сохранения;
- импорта;
- восстановления;
- удаления данных.

---

# 13. Error Handling

Все ошибки должны корректно обрабатываться.

StorageService не должен завершать работу приложения при возникновении ошибки.

---

## Error Categories

Поддерживаются категории ошибок:

- File Not Found;
- Read Error;
- Write Error;
- Storage Full;
- Invalid Format;
- Backup Error;
- Import Error;
- Export Error;
- Provider Error.

---

## Error Reporting

Ошибки должны передаваться вызывающему компоненту в виде информативного результата.

GUI самостоятельно принимает решение о способе отображения сообщения пользователю.

---

# 14. Performance

Подсистема хранения должна обеспечивать быстрый доступ к пользовательским данным.

---

## Requirements

Следует минимизировать:

- количество операций записи;
- повторное открытие файлов;
- лишнее копирование данных.

Все длительные операции должны выполняться в отдельной задаче FreeRTOS.

---

## Asynchronous Operations

Следующие операции рекомендуется выполнять асинхронно:

- резервное копирование;
- восстановление;
- импорт;
- экспорт.

Во время выполнения этих операций GUI должен оставаться полностью отзывчивым.

---

# 15. Future Extensions

Архитектура подсистемы хранения должна предусматривать возможность дальнейшего расширения без изменения публичного API.

Планируемые возможности:

- AES-256 Encryption;
- несколько Vault;
- сжатие резервных копий;
- цифровая подпись резервных копий;
- дополнительные StorageProvider;
- поддержка внешних накопителей;
- облачная синхронизация (опционально).

Новые возможности должны интегрироваться через существующие интерфейсы StorageService и StorageProvider.

---

# 16. Summary

Подсистема **Storage** отвечает исключительно за долговременное хранение пользовательских данных и полностью отделена от бизнес-логики приложения.

Доступ к файловой системе осуществляется только через **StorageService**, который использует абстракцию **StorageProvider** для работы с LittleFS и microSD.

Подсистема не выполняет проверку прав доступа, не взаимодействует с GUI и не содержит логики безопасности. Все защищённые операции предварительно проходят проверку через **SecurityService**, что обеспечивает чёткое разделение ответственности между компонентами **Storage**, **Vault** и **Security**.

Такая архитектура соответствует принципам **Single Responsibility**, **Layer Separation**, **Documentation First** и обеспечивает простоту сопровождения, возможность расширения и переносимость проекта.
