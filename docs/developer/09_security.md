# Security Development Guide

**Project:** KeyKeeper2

**Version:** 2.0

---

# 1. Purpose

Документ определяет правила разработки компонентов безопасности проекта **KeyKeeper2**.

Он предназначен для разработчиков программного обеспечения и описывает принципы реализации безопасного кода внутри архитектуры проекта.

В документе рассматриваются:

* архитектура SecurityService;
* модель безопасности системы;
* жизненный цикл пользовательской сессии;
* правила взаимодействия компонентов;
* контроль доступа;
* безопасная работа с чувствительными данными;
* рекомендации по реализации новых функций.

Документ не заменяет **SECURITY.md**.

SECURITY.md описывает архитектуру безопасности системы, тогда как настоящий документ объясняет, **как реализовывать эту архитектуру в исходном коде**.

---

# 2. Scope

Настоящий документ распространяется на все компоненты проекта.

Особенно обязательным он является для разработчиков следующих модулей:

* SecurityService;
* VaultService;
* StorageService;
* USBService;
* WebService;
* WiFiService;
* SettingsService;
* GUI.

Любой компонент, который получает доступ к пользовательским данным, обязан соблюдать требования настоящего документа.

---

# 3. Security Philosophy

Безопасность является одним из базовых требований проекта.

Все программное обеспечение строится вокруг следующих принципов.

## Zero Trust

Ни один компонент не считается доверенным автоматически.

Каждый запрос проверяется независимо.

Даже если пользователь уже разблокировал устройство, каждая чувствительная операция проходит через SecurityService.

---

## Least Privilege

Каждый компонент получает только минимально необходимые права.

Например:

* GUI не имеет доступа к базе данных.
* USBService не принимает решений об авторизации.
* StorageService не знает, имеет ли пользователь право читать данные.
* WebService не может самостоятельно открыть хранилище.

---

## Secure by Default

Любое новое поведение системы должно быть безопасным по умолчанию.

Если разработчик забыл выполнить проверку безопасности, операция должна завершиться отказом.

---

## Fail Secure

При любой ошибке система должна переходить в безопасное состояние.

Примеры:

* ошибка проверки PIN → отказ в доступе;
* повреждение базы данных → прекращение операции;
* потеря пользовательской сессии → немедленная блокировка устройства;
* ошибка USB → прекращение передачи данных.

---

## Separation of Responsibilities

Каждый компонент отвечает только за собственную область.

Например:

GUI отвечает только за отображение информации.

SecurityService отвечает только за безопасность.

VaultService отвечает только за работу с записями.

StorageService отвечает только за хранение данных.

Такое разделение уменьшает вероятность появления ошибок безопасности.

---

# 4. Architecture Position

Подсистема безопасности располагается в центре архитектуры проекта.

Все операции с защищёнными данными проходят через SecurityService.

```text
User

↓

GUI

↓

SecurityService

↓

VaultService

↓

StorageService
```

Никакой другой компонент не имеет права принимать решение о предоставлении доступа к данным.

---

# 5. SecurityService

SecurityService является центральным компонентом подсистемы безопасности.

Через него проходят все операции, связанные с:

* аутентификацией;
* авторизацией;
* управлением пользовательской сессией;
* блокировкой устройства;
* проверкой разрешений;
* публикацией событий безопасности.

SecurityService не содержит пользовательский интерфейс.

SecurityService не работает напрямую с файловой системой.

SecurityService не выполняет отображение сообщений пользователю.

---

# 6. Responsibilities

SecurityService отвечает за следующие задачи.

## Authentication

Проверка личности пользователя.

Поддерживаются:

* PIN;
* дополнительные методы (в будущем).

---

## Session Management

Создание пользовательской сессии.

Продление активности.

Автоматическое завершение.

Блокировка устройства.

---

## Authorization

Проверка прав перед выполнением операции.

Каждый компонент обязан запросить разрешение перед доступом к защищённым данным.

---

## Security State

Поддерживаются состояния:

* Locked
* Unlocking
* Unlocked
* Timeout
* Error

Переключение между состояниями выполняется только SecurityService.

---

## Security Events

SecurityService публикует события:

* DeviceLocked
* DeviceUnlocked
* AuthenticationSucceeded
* AuthenticationFailed
* SessionExpired
* PermissionDenied
* SecurityError

События распространяются через EventBus.

---

# 7. Security Boundaries

Одним из важнейших принципов проекта является строгое разделение ответственности.

Каждый компонент имеет собственную границу безопасности.

## GUI

GUI:

может:

* отображать данные;
* получать действия пользователя.

не может:

* проверять PIN;
* принимать решения о доступе;
* читать базу данных напрямую;
* выполнять криптографические операции.

---

## VaultService

VaultService:

может:

* работать с пользовательскими записями;
* искать записи;
* изменять записи.

не может:

* самостоятельно принимать решение о доступе.

Перед каждой защищённой операцией VaultService обращается к SecurityService.

---

## StorageService

StorageService:

может:

* читать файлы;
* записывать файлы;
* удалять файлы.

не знает:

* кто является пользователем;
* разблокировано ли устройство;
* разрешено ли выполнять операцию.

---

## USBService

USBService:

может:

* передавать данные;
* принимать соединения.

не может:

* самостоятельно экспортировать секретные данные.

Передача начинается только после разрешения SecurityService.

---

## WebService

WebService предоставляет транспорт.

Все решения о доступе принимаются SecurityService.

---

# 8. Security Model

Каждая защищённая операция проходит одинаковую последовательность.

```text
User Action

↓

GUI

↓

SecurityService

↓

Permission Check

↓

Requested Service

↓

Result
```

Например:

Просмотр записи.

```text
User

↓

GUI

↓

SecurityService

↓

VaultService

↓

StorageService
```

Передача пароля через USB.

```text
User

↓

GUI

↓

SecurityService

↓

VaultService

↓

USBService
```

Экспорт резервной копии.

```text
User

↓

GUI

↓

SecurityService

↓

StorageService

↓

USBService
```

Во всех случаях именно **SecurityService** является единственной точкой принятия решения.

Если проверка не пройдена, дальнейшее выполнение операции немедленно прекращается.

На этом этапе остальные сервисы не должны выполнять никаких действий с пользовательскими данными.


---

# 9. Authentication

Аутентификация является первой ступенью защиты устройства.

Все проверки личности пользователя выполняются исключительно через **SecurityService**.

Никакой другой компонент проекта не имеет права самостоятельно проверять:

* PIN-код;
* мастер-пароль;
* состояние авторизации;
* успешность предыдущих проверок.

Это обеспечивает единое поведение системы и исключает дублирование логики безопасности.

---

## Authentication Flow

Типичный процесс аутентификации выглядит следующим образом.

```text
User

↓

GUI

↓

SecurityService

↓

PIN Verification

↓

Create Session

↓

Publish Event

↓

Unlocked
```

После успешной проверки создаётся пользовательская сессия.

Если проверка завершается ошибкой, устройство остаётся заблокированным.

---

## Authentication Attempts

SecurityService обязан учитывать количество последовательных неудачных попыток.

После превышения допустимого количества попыток могут применяться дополнительные ограничения.

Например:

* временная задержка;
* увеличение времени ожидания;
* обязательная повторная попытка позже.

Логика ограничения должна быть централизована внутри SecurityService.

---

## Authentication Sources

Все способы аутентификации должны использовать единый интерфейс SecurityService.

Даже если в будущем появятся:

* биометрия;
* аппаратный ключ;
* внешнее устройство;
* NFC;

остальные компоненты проекта не должны изменяться.

---

# 10. Session Management

После успешной аутентификации создаётся пользовательская сессия.

Сессия представляет собой временное состояние, подтверждающее успешную проверку личности пользователя.

---

## Session Lifecycle

Жизненный цикл сессии:

```text
Locked

↓

Authenticate

↓

Unlocked

↓

Active

↓

Idle

↓

Timeout

↓

Locked
```

Сессия завершается автоматически после блокировки устройства.

---

## Session State

SecurityService хранит только одно актуальное состояние.

Допустимые состояния:

* Locked
* Unlocked
* Expired
* AuthenticationRequired
* Error

Другие сервисы получают информацию только через публичный API.

---

## Session Timeout

При отсутствии активности выполняется автоматическая блокировка.

Таймер активности сбрасывается при:

* действиях пользователя;
* успешных операциях;
* переходах между экранами;
* подтверждённых запросах.

После истечения времени ожидания SecurityService:

* уничтожает пользовательскую сессию;
* очищает временные данные;
* публикует событие SessionExpired;
* переводит устройство в состояние Locked.

---

## Session Ownership

Пользовательская сессия принадлежит исключительно SecurityService.

Запрещается:

* копировать состояние сессии;
* кэшировать признак авторизации;
* хранить локальные флаги "разблокировано".

Все проверки выполняются только через SecurityService.

---

# 11. Authorization

После успешной аутентификации каждая операция проходит проверку разрешений.

Наличие активной сессии не означает автоматическое разрешение на выполнение любых действий.

---

## Authorization Flow

Каждая защищённая операция проходит одинаковую последовательность.

```text
Request

↓

SecurityService

↓

Permission Check

↓

Allowed / Denied
```

Если разрешение отсутствует, операция прекращается.

---

## Permission Rules

Разрешения проверяются перед:

* открытием Vault;
* просмотром записи;
* редактированием записи;
* удалением записи;
* экспортом;
* импортом;
* передачей через USB;
* использованием Web-интерфейса;
* изменением настроек безопасности.

---

## Single Decision Point

Только SecurityService принимает решение.

Компоненты не должны самостоятельно выполнять проверки вроде:

```cpp
if (isUnlocked)
```

или

```cpp
if (authenticated)
```

Все подобные проверки должны выполняться через публичный API SecurityService.

---

# 12. Protected Operations

Защищёнными считаются любые операции, способные раскрыть пользовательские данные или изменить состояние устройства.

---

## Vault Operations

Перед выполнением проверяются:

* наличие активной сессии;
* разрешение пользователя.

---

## Storage Operations

Перед чтением или записью защищённых данных выполняется проверка доступа.

StorageService самостоятельно не определяет права пользователя.

---

## USB Operations

Передача данных через USB разрешается только после успешной проверки SecurityService.

Даже если USB уже подключён, повторная проверка обязательна.

---

## Web Operations

Любая операция Web-интерфейса проходит через SecurityService.

WebService не принимает решений самостоятельно.

---

## Settings

Изменение следующих параметров требует проверки безопасности:

* PIN;
* параметры безопасности;
* экспорт;
* импорт;
* очистка устройства;
* резервное копирование.

---

# 13. EventBus Integration

SecurityService взаимодействует с остальной системой исключительно через EventBus.

---

## Published Events

Основные события:

* DeviceLocked
* DeviceUnlocked
* AuthenticationSucceeded
* AuthenticationFailed

---

## Event Consumers

Типичные подписчики:

WebService

Каждый компонент самостоятельно решает, как реагировать на событие.

Он только предоставляет информацию о возможности выполнения операции.

---

# 15. Security State Machine

Состояние устройства может изменяться только SecurityService.

```text
Locked

↓

Authenticating

↓

Unlocked

↓

Idle

↓

Timeout

↓

Locked
```

Запрещается переводить устройство между этими состояниями из других компонентов.

---

# 16. Failure Behaviour

При любой ошибке подсистема безопасности должна переходить в безопасное состояние.

Примеры:

* ошибка проверки PIN → отказ в доступе;
* ошибка проверки разрешений → отказ в операции;
* потеря пользовательской сессии → блокировка устройства;
* повреждение внутреннего состояния → публикация SecurityError;
* внутренняя ошибка SecurityService → переход в состояние Locked.

Главное правило:

**При любой неопределённости система должна выбирать наиболее безопасное поведение.**

---

# 17. Sensitive Data Handling

Одним из важнейших требований проекта является правильная работа с конфиденциальными данными.

К чувствительным данным относятся:

* PIN-код;
* мастер-пароль;
* OTP-секреты;
* криптографические ключи;
* содержимое пользовательских записей;
* резервные ключи;
* расшифрованные данные.

---

## Lifetime

Конфиденциальные данные должны существовать в памяти только минимально необходимое время.

Правильная последовательность:

```text id="q0n1wf"
Read

↓

Use

↓

Overwrite

↓

Release
```

После завершения операции буфер должен быть очищен.

---

## Memory Ownership

Каждый чувствительный объект должен иметь единственного владельца.

Предпочтительно использовать:

* автоматические объекты;
* RAII;
* std::unique_ptr.

Не рекомендуется использовать глобальные объекты для хранения секретной информации.

---

## Buffer Reuse

Буферы с секретными данными не должны использоваться повторно без очистки.

Перед повторным использованием память должна быть полностью перезаписана.

---

# 18. Secure Coding Rules

Все компоненты проекта обязаны соблюдать единые правила безопасного программирования.

---

## Validate Input

Любые входные данные считаются недоверенными.

Необходимо проверять:

* длину;
* диапазон;
* формат;
* допустимые символы;
* структуру.

---

## Never Trust External Data

Недоверенными считаются:

* USB;
* Web;
* microSD;
* резервные копии;
* импортируемые файлы;
* пользовательский ввод.

Даже данные, созданные предыдущей версией программы, должны проверяться перед использованием.

---

## Explicit Checks

Не следует полагаться на предположения.

Каждая операция должна явно проверять:

* права доступа;
* состояние системы;
* успешность предыдущих шагов.

---

## Fail Early

Ошибки должны обнаруживаться как можно раньше.

При обнаружении ошибки выполнение операции немедленно прекращается.

---

## No Hidden Side Effects

Функции SecurityService должны выполнять только документированные действия.

Не допускается скрытое изменение состояния других компонентов.

---

# 19. Logging Rules

Журналирование необходимо для диагностики системы.

Однако безопасность имеет приоритет над полнотой журналов.

---

## Allowed Information

Разрешается записывать:

* состояние системы;
* тип ошибки;
* идентификатор операции;
* время выполнения;
* техническую информацию.

---

## Forbidden Information

Категорически запрещается журналировать:

* PIN;
* пароли;
* OTP;
* секретные ключи;
* содержимое Vault;
* расшифрованные данные;
* резервные коды.

---

## Error Messages

Сообщения об ошибках не должны раскрывать внутреннее устройство системы.

Например:

Правильно:

```text id="5n5q9g"
Authentication failed.
```

Неправильно:

```text id="lqf1gv"
PIN is incorrect.
```

или

```text id="lxy05t"
User entered 1234.
```

---

# 20. Security Testing

Подсистема безопасности должна тестироваться отдельно от остальных компонентов.

---

## Authentication Tests

Проверяются:

* правильный PIN;
* неправильный PIN;
* последовательные ошибки;
* повторная попытка;
* создание пользовательской сессии.

---

## Session Tests

Проверяются:

* создание сессии;
* завершение сессии;
* таймаут;
* повторная разблокировка;
* восстановление после ошибок.

---

## Authorization Tests

Проверяются:

* разрешённые операции;
* запрещённые операции;
* попытки обхода SecurityService;
* повторные проверки.

---

## Storage Tests

Проверяется невозможность доступа к данным без успешной авторизации.

---

## USB Tests

Проверяются:

* попытка передачи данных при заблокированном устройстве;
* отключение USB во время передачи;
* повторное подключение.

---

## Web Tests

Проверяются:

* доступ без авторизации;
* завершение пользовательской сессии;
* потеря соединения;
* отказ SecurityService.

---

# 21. Security Review Checklist

Перед включением нового кода необходимо проверить следующие вопросы.

---

## Architecture

# 22. Common Mistakes

Следующие ошибки считаются критическими.

---

## Caching Authorization

Запрещается:

```cpp id="ynxgzd"
bool unlocked = true;
```

Такое состояние быстро устаревает.

Необходимо каждый раз обращаться к SecurityService.

---

## Direct Storage Access

Запрещается:

```text id="drj09z"
GUI

↓

StorageService
```

Правильно:

```text id="z0j0dv"
GUI

↓

SecurityService

↓

StorageService
```

---

## Long Living Secrets

Нельзя хранить PIN в памяти после завершения проверки.

Буферы должны очищаться сразу после использования.

---

## Duplicate Checks

Проверка безопасности должна существовать только в одном месте.

Если одинаковая проверка появляется в нескольких сервисах — архитектура нарушена.

---

# 23. Best Practices

При разработке рекомендуется:

* использовать только SecurityService;
* очищать чувствительные данные;
* минимизировать время хранения секретной информации;
* использовать EventBus;
* выполнять проверку перед каждой защищённой операцией;
* не хранить локальные признаки авторизации;
* использовать принцип Least Privilege;
* придерживаться Zero Trust;
* проектировать новые функции безопасными по умолчанию.

# 25. Summary

Подсистема безопасности проекта **KeyKeeper2** построена вокруг **SecurityService**, который является единственной точкой принятия решений, связанных с аутентификацией, авторизацией и управлением пользовательской сессией.

Все компоненты взаимодействуют с системой безопасности исключительно через публичный API SecurityService и получают информацию о её состоянии посредством EventBus. Такое разделение обязанностей исключает дублирование логики, уменьшает связанность компонентов и обеспечивает единообразное применение политики безопасности во всём проекте.

Следование рекомендациям настоящего документа позволяет создавать безопасный, сопровождаемый и предсказуемый код, полностью соответствующий архитектуре KeyKeeper2 и принципам **Zero Trust**, **Least Privilege**, **Fail Secure** и **Secure by Default**.
