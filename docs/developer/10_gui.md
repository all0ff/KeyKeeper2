# GUI Development Guide

**Project:** KeyKeeper2

**Version:** 2.0

---

# GUI Architecture

# 1. Purpose

Документ определяет правила разработки графического интерфейса проекта **KeyKeeper2**.

Он предназначен для разработчиков пользовательского интерфейса и описывает:

* архитектуру GUI;
* организацию экранов;
* правила взаимодействия компонентов;
* модель навигации;
* жизненный цикл экранов;
* взаимодействие GUI с сервисным слоем.

Документ не заменяет **GUI.md**.

GUI.md описывает архитектуру пользовательского интерфейса, тогда как настоящий документ объясняет, **как реализовывать интерфейс внутри проекта**.

---

# 2. GUI Philosophy

GUI является отдельным компонентом архитектуры.

Его задача — исключительно взаимодействие с пользователем.

GUI никогда не должен принимать архитектурные решения.

Он не должен содержать:

* бизнес-логику;
* криптографию;
* файловые операции;
* работу с USB;
* работу с Wi-Fi;
* работу с Web;
* проверки безопасности.

Все подобные задачи выполняются соответствующими сервисами.

---

# 3. Architecture Position

Общее положение GUI в архитектуре проекта.

```text id="uyqfkn"
User

↓

GUI

↓

EventBus

↓

Service Layer

↓

Storage / USB / Web

↓

ESP-IDF
```

GUI является только верхним уровнем взаимодействия с пользователем.

Все остальные компоненты скрыты за сервисным слоем.

---

# 4. Responsibilities

GUI отвечает только за:

* отображение информации;
* обработку пользовательского ввода;
* отображение сообщений;
* навигацию;
* запуск пользовательских действий;
* визуальное состояние приложения.

GUI **не отвечает** за:

* безопасность;
* хранение данных;
* криптографию;
* работу с сетью;
* работу USB;
* работу файловой системы.

---

# 5. GUI Principles

При разработке необходимо соблюдать следующие принципы.

## Single Responsibility

Каждый экран отвечает только за одну пользовательскую задачу.

---

## Stateless Screens

Экран не должен хранить бизнес-данные.

После закрытия экран может быть уничтожен без потери состояния системы.

---

## Service Driven

GUI никогда не принимает решений самостоятельно.

Все действия передаются соответствующим сервисам.

---

## Event Driven

GUI получает изменения состояния системы через EventBus.

GUI не опрашивает сервисы непрерывно.

---

## Predictable Navigation

Любой переход между экранами выполняется централизованно.

---

# 6. GUI Structure

Подсистема GUI состоит из следующих компонентов.

```text id="jlwm9k"
GUI

├── Navigation Manager

├── Screen Manager

├── Theme Manager

├── Icon Manager

├── Dialog Manager

├── Input Manager

└── Screen Modules
```

Каждый компонент имеет собственную область ответственности.

---

# 7. Screen Architecture

Каждый экран является независимым модулем.

Типичная структура:

```text id="d4lzfh"
Screen

├── Header

├── Content

├── Footer

└── Event Handlers
```

Экран не должен обращаться к внутренним структурам другого экрана.

---

---

## System Screens

---

## Navigation Screens

Экраны навигации:

* Categories
* Settings

---

## Content Screens

Экраны отображения информации:

## Dialog Screens

Временные окна:

* Warning

---

# 9. Screen Responsibilities

Каждый экран отвечает только за:

* отображение собственного содержимого;
* обработку собственного ввода;
* публикацию событий.

Экран не должен:

* открывать другие экраны напрямую;
* изменять глобальное состояние приложения;
* работать с файловой системой;
* обращаться к USB;
* выполнять криптографические операции.

---

# 10. Screen Communication

Экраны не взаимодействуют друг с другом напрямую.

Например, экран настроек не должен вызывать методы экрана хранилища.

Все взаимодействие выполняется через:

* Navigation Manager;
* EventBus;
* соответствующий сервис.

---

# 11. Screen Lifecycle

Каждый экран проходит одинаковый жизненный цикл.

```text id="t2qglf"
Create

↓

Initialize

↓

Show

↓

Active

↓

Hide

↓

Destroy
```

Каждый этап должен быть явно реализован.

---

## Create

Создание объектов экрана.

Запрещается выполнять длительные операции.

---

## Initialize

Инициализация элементов интерфейса.

Создаются:

* кнопки;
* списки;
* подписи;
* контейнеры.

---

## Show

Экран становится активным.

Разрешается:

* подписаться на события;
* запросить необходимые данные у сервисов;
* обновить отображение.

---

## Active

Во время активности экран:

* отображает данные;
* принимает ввод пользователя;
* реагирует на события EventBus.

---

## Hide

Перед скрытием:

* прекращаются анимации;
* снимаются подписки;
* сохраняется необходимое визуальное состояние.

---

## Destroy

Все объекты LVGL уничтожаются.

После Destroy экран не должен содержать действительных указателей на элементы интерфейса.

---

# 12. Data Flow

Типичная пользовательская операция.

```text id="mrprpv"
User

↓

GUI

↓

EventBus

↓

Requested Service

↓

Result

↓

GUI Update
```

GUI инициирует действие и отображает результат, но не принимает решений о выполнении операции.

---

# 13. Interaction with Services

GUI работает только через публичные интерфейсы сервисов.

Например:

```text id="suc5z2"
GUI

↓

SecurityService
```

или

```text id="tktv6u"
GUI

↓

VaultService
```

или

```text id="7ph7zn"
GUI

↓

SettingsService
```

Использование внутренних структур сервисов запрещено.

---

# 14. GUI and EventBus

GUI является одним из основных потребителей EventBus.

Он получает события:

* DeviceLocked
* DeviceUnlocked
* USBConnected
* USBDisconnected
* WiFiConnected
* SessionExpired
* StorageUpdated

После получения события экран самостоятельно принимает решение о необходимости обновления отображения.

GUI не должен изменять состояние системы при обработке событий без явного действия пользователя.

---

# 15. Navigation Manager

Navigation Manager является единственной подсистемой, отвечающей за переходы между экранами.

Ни один экран проекта не должен самостоятельно открывать или закрывать другие экраны.

Это обеспечивает:

* единое поведение интерфейса;
* отсутствие циклических зависимостей;
* централизованное управление жизненным циклом экранов;
* предсказуемость навигации.

---

## Responsibilities

Navigation Manager отвечает за:

* открытие экранов;
* закрытие экранов;
* возврат назад;
* замену текущего экрана;
* управление стеком экранов;
* передачу параметров между экранами.

Navigation Manager не содержит бизнес-логики.

---

## Navigation Flow

Типичный переход:

```text id="4m5ykt"
User

↓

GUI

↓

Navigation Manager

↓

Screen Manager

↓

Target Screen
```

Экран не должен самостоятельно создавать другой экран.

---

# 16. Navigation Stack

Навигация строится на стеке экранов.

Типичная последовательность:

```text id="z7zqeg"
Main Menu

↓

Vault

↓

Entry

↓

Edit
```

При возврате предыдущий экран восстанавливается автоматически.

---

## Push

Открывает новый экран поверх текущего.

---

## Pop

Закрывает текущий экран и возвращает предыдущий.

---

## Replace

Полностью заменяет текущий экран новым.

---

## Reset

Полностью очищает стек навигации.

Используется:

* после блокировки;
* после выхода пользователя;
* после сброса устройства.

---

# 17. Screen Manager

Screen Manager отвечает за создание и уничтожение экранов.

Каждый экран создаётся только через Screen Manager.

---

## Responsibilities

Screen Manager:

* создаёт экран;
* инициализирует экран;
* уничтожает экран;
* освобождает ресурсы;
* контролирует жизненный цикл объектов LVGL.

---

## Screen Registration

Все экраны регистрируются централизованно.

Например:

```text id="ktghwy"
LockScreen

MainMenuScreen

VaultScreen

EntryScreen

SettingsScreen
```

Добавление нового экрана должно сопровождаться регистрацией в Screen Manager.

---

# 18. Dialog Manager

Dialog Manager управляет всеми временными окнами интерфейса.

Диалоги не являются полноценными экранами.

---

## Responsibilities

Dialog Manager отвечает за:

* подтверждения;
* предупреждения;
* сообщения об ошибках;
* индикаторы выполнения;
* запрос PIN;
* запрос подтверждения.

---

## Dialog Types

Типичные диалоги:

* Confirmation
* Warning
* Error
* Success
* Progress
* PIN Entry

Каждый тип имеет единый внешний вид.

---

## Modal Dialogs

Модальные окна блокируют взаимодействие с основным экраном.

До закрытия модального окна пользователь не может взаимодействовать с остальным интерфейсом.

---

# 19. Input Manager

Input Manager обрабатывает пользовательский ввод.

Поддерживаются:

* кнопки;
* сенсорный экран;
* энкодер (при наличии);
* аппаратные клавиши.

---

## Responsibilities

Input Manager:

* получает события ввода;
* преобразует их в события GUI;
* передаёт события активному экрану.

---

## Input Processing

Последовательность обработки:

```text id="c0nr2g"
Hardware

↓

Input Manager

↓

Active Screen

↓

EventBus
```

Экран получает только уже обработанные события.

---

# 20. Screen State

Каждый экран имеет собственное состояние.

Например:

```text id="fr2bq7"
Inactive

↓

Loading

↓

Ready

↓

Updating

↓

Closing
```

Переходы между состояниями должны быть явными.

---

## Loading

Экран ожидает данные.

В это время допускается отображение индикатора загрузки.

---

## Ready

Экран полностью готов к работе.

Пользователь может взаимодействовать с интерфейсом.

---

## Updating

Происходит обновление отображаемых данных.

Обновляться должны только изменившиеся элементы.

---

## Closing

Экран завершает работу.

Освобождаются:

* объекты LVGL;
* подписки EventBus;
* временные ресурсы.

---

# 21. GUI Updates

Обновление интерфейса должно быть минимальным.

Не рекомендуется полностью перестраивать экран после каждого изменения.

Следует обновлять только изменившиеся элементы.

---

## Incremental Update

Правильно:

* обновить один Label;
* обновить одну кнопку;
* изменить состояние переключателя.

Неправильно:

* полностью удалить экран;
* заново создать все объекты.

---

# 22. Screen Parameters

Navigation Manager может передавать экрану параметры.

Например:

```text id="8djvdc"
Entry ID

↓

Entry Screen
```

или

```text id="8d84k5"
Category ID

↓

Vault Screen
```

Экран не должен самостоятельно искать эти данные.

---

# 23. GUI Synchronization

Все объекты LVGL принадлежат GUI Task.

Другие задачи не должны обращаться к ним напрямую.

Для обновления интерфейса используется EventBus.

---

## Correct Flow

```text id="jlwm9v"
Service

↓

EventBus

↓

GUI Task

↓

LVGL
```

---

## Forbidden Flow

Запрещается:

```text id="69jlwm"
USB Task

↓

LVGL
```

или

```text id="1ghlh6"
Storage Task

↓

LVGL
```

Все подобные обращения нарушают потокобезопасность.

---

# 24. Navigation Best Practices

При разработке рекомендуется:

* использовать Navigation Manager для всех переходов;
* не открывать экраны напрямую;
* не хранить ссылки на уничтоженные экраны;
* минимизировать количество одновременно существующих экранов;
* использовать Dialog Manager для всех временных сообщений;
* обновлять только изменившиеся элементы интерфейса;
* освобождать ресурсы сразу после закрытия экрана.

Такой подход делает навигацию предсказуемой, уменьшает потребление памяти и соответствует компонентной архитектуре проекта.

---

# 25. Theme Manager

Theme Manager отвечает за единый внешний вид всего пользовательского интерфейса.

Все визуальные параметры приложения централизованы.

Экраны не должны самостоятельно определять:

* цвета;
* размеры элементов;
* стили;
* радиусы скругления;
* толщину рамок;
* отступы.

Все подобные параметры предоставляет Theme Manager.

---

## Responsibilities

Theme Manager отвечает за:

* регистрацию тем;
* применение темы;
* обновление визуального оформления;
* предоставление стилей экранам;
* единообразие интерфейса.

Theme Manager не содержит бизнес-логики.

---

## Theme Structure

Типичная структура темы:

```text id="jlwm2h"
Theme

├── Colors

├── Fonts

├── Buttons

├── Lists

├── Dialogs

├── Header

└── Footer
```

Каждый экран использует готовые стили.

---

## Theme Switching

При изменении темы обновление должно происходить централизованно.

Экраны не должны самостоятельно перестраивать своё оформление.

---

# 26. Color System

Все цвета проекта должны использовать именованные идентификаторы.

Например:

```text id="mls0xg"
Primary

Secondary

Background

Surface

Accent

Success

Warning

Error

Disabled
```

Использование "магических" значений RGB непосредственно в коде запрещено.

---

## Consistency

Один и тот же смысл всегда должен отображаться одинаковым цветом.

Например:

* ошибки — красный;
* предупреждения — жёлтый;
* успешные действия — зелёный.

---

# 27. Font Management

Все шрифты регистрируются централизованно.

GUI не должен самостоятельно создавать экземпляры шрифтов.

---

## Font Categories

Рекомендуется использовать несколько категорий:

* Large Title
* Title
* Subtitle
* Body
* Small
* Monospace (при необходимости)

Размеры шрифтов должны быть едиными во всём приложении.

---

# 28. Icon Manager

Icon Manager управляет всеми пиктограммами проекта.

GUI никогда не использует изображения напрямую.

---

## Responsibilities

Icon Manager отвечает за:

* регистрацию пиктограмм;
* предоставление иконок экранам;
* единый стиль;
* поддержку различных разрешений.

---

## Icon Identifiers

GUI использует только логические идентификаторы.

Например:

```text id="vbx6j7"
ICON_HOME

ICON_LOCK

ICON_USB

ICON_WIFI

ICON_SETTINGS

ICON_BACK

ICON_SEARCH
```

Это позволяет заменить графические ресурсы без изменения кода экранов.

---

## Icon Style

Все пиктограммы должны соответствовать единому стилю проекта.

Не допускается смешивание различных наборов иконок.

---

# 29. Animation Management

Анимации используются только для улучшения пользовательского опыта.

Они не должны:

* отвлекать пользователя;
* скрывать ошибки;
* замедлять работу интерфейса.

---

## Recommended Animations

Разрешаются:

* плавное появление;
* плавное исчезновение;
* небольшое смещение;
* индикация загрузки;
* прогресс.

---

## Forbidden Animations

Не рекомендуется использовать:

* длительные переходы;
* сложные последовательности;
* анимации, влияющие на производительность;
* одновременное выполнение большого количества анимаций.

---

# 30. GUI Performance

Производительность интерфейса имеет высокий приоритет.

Интерфейс должен оставаться отзывчивым при любых действиях пользователя.

---

## Rendering

Следует минимизировать количество операций перерисовки.

Если изменился один элемент, не следует перестраивать весь экран.

---

## Object Count

Количество одновременно существующих объектов LVGL должно быть минимальным.

Следует использовать повторное использование объектов там, где это возможно.

---

## Refresh

Обновление должно выполняться только при изменении данных.

Избыточное обновление приводит к снижению производительности.

---

# 31. Memory Management

GUI является одной из наиболее ресурсоёмких подсистем.

Поэтому память должна использоваться максимально эффективно.

---

## Object Lifetime

Каждый объект LVGL должен иметь понятный жизненный цикл.

После уничтожения объекта ссылки на него должны быть удалены.

---

## Dynamic Allocation

Динамическое создание объектов допускается только при необходимости.

Не рекомендуется регулярно создавать и уничтожать одинаковые элементы.

---

## Temporary Objects

Временные объекты должны уничтожаться сразу после завершения операции.

---

# 32. Resource Management

GUI отвечает только за собственные ресурсы.

Например:

* контейнеры;
* кнопки;
* изображения;
* списки;
* текстовые поля.

Освобождение ресурсов должно происходить централизованно при уничтожении экрана.

---

# 33. GUI Thread Safety

Все объекты LVGL принадлежат GUI Task.

Другие задачи не должны:

* создавать объекты;
* изменять объекты;
* удалять объекты.

---

## Correct Update

```text id="obcb8b"
Service

↓

EventBus

↓

GUI Task

↓

LVGL Update
```

---

## Incorrect Update

```text id="pxtqlu"
Storage Task

↓

LVGL Widget
```

или

```text id="lvzt0x"
USB Task

↓

Button Update
```

Подобные обращения запрещены.

---

# 34. Performance Monitoring

Во время разработки рекомендуется контролировать:

* время построения экранов;
* количество объектов;
* использование памяти;
* скорость переключения экранов;
* количество операций перерисовки.

Проблемы производительности должны выявляться на ранних этапах разработки.

---

# 35. GUI Best Practices

При разработке рекомендуется:

* использовать Theme Manager;
* использовать Icon Manager;
* применять централизованные стили;
* обновлять только изменившиеся элементы;
* минимизировать количество объектов LVGL;
* своевременно освобождать память;
* избегать тяжёлых операций в GUI Task;
* использовать EventBus для получения изменений;
* сохранять единый визуальный стиль во всём приложении.

Следование этим рекомендациям обеспечивает высокую производительность интерфейса, предсказуемое поведение экранов и соответствие архитектуре проекта.

# GUI Integration, Testing and Development Guidelines

# 36. GUI and Service Layer

GUI никогда не взаимодействует с аппаратным обеспечением напрямую.

Любая операция выполняется через соответствующий сервис.

Типичная схема взаимодействия:

```text
GUI

↓

Service Layer

↓

Platform Layer

↓

ESP-IDF
```

Такое разделение позволяет изменять реализацию сервисов без изменения пользовательского интерфейса.

---

## Allowed Services

GUI может взаимодействовать только с публичными API следующих сервисов:

* SecurityService;
* VaultService;
* StorageService;
* SettingsService;
* USBService;
* WiFiService;
* WebService;
* NotificationService.

Использование внутренних структур сервисов запрещено.

---

# 37. GUI and Security

GUI никогда не принимает решений, связанных с безопасностью.

Экран может только:

* запросить выполнение операции;
* получить результат проверки;
* отобразить соответствующее сообщение.

Все решения принимает исключительно SecurityService.

---

## Authentication Example

Типичный процесс:

```text
User

↓

PIN Screen

↓

SecurityService

↓

Authentication Result

↓

GUI Update
```

GUI не должен самостоятельно проверять правильность PIN-кода.

---

# 38. GUI and Storage

GUI не работает с файлами.

Последовательность обращения:

```text
GUI

↓

VaultService

↓

StorageService

↓

Storage Provider
```

GUI получает только готовые данные для отображения.

---

# 39. GUI and USB

GUI может инициировать экспорт данных или передачу через USB.

Однако непосредственно взаимодействие с USB выполняет USBService.

Типичный сценарий:

```text
GUI

↓

SecurityService

↓

USBService
```

---

# 40. GUI and Web

GUI используется для настройки Web-интерфейса.

Все сетевые операции выполняются WebService и WiFiService.

GUI только отображает:

* состояние подключения;
* параметры сети;
* ошибки;
* уведомления.

---

# 41. GUI Error Handling

Все ошибки отображаются единообразно.

Не допускается самостоятельная обработка ошибок каждым экраном.

Рекомендуется использовать Dialog Manager.

---

## Error Categories

Ошибки можно разделить на категории:

* информационные;
* предупреждения;
* ошибки пользователя;
* системные ошибки;
* критические ошибки.

Для каждой категории должен использоваться единый стиль отображения.

---

# 42. Notifications

Кратковременные уведомления используются для отображения результатов операций.

Например:

* запись сохранена;
* экспорт завершён;
* устройство подключено;
* сеть недоступна.

Уведомления не должны блокировать работу пользователя.

---

# 43. Accessibility

Интерфейс должен оставаться понятным и удобным.

Рекомендуется:

* достаточный размер элементов управления;
* читаемые шрифты;
* высокий контраст;
* единообразное расположение элементов;
* понятные подписи.

---

# 44. Localization

GUI должен быть готов к поддержке нескольких языков.

Все отображаемые строки должны использовать централизованную систему локализации.

Запрещается размещать текстовые строки непосредственно в коде экранов.

---

# 45. GUI Testing

Каждый экран должен тестироваться отдельно.

Необходимо проверять:

* открытие;
* закрытие;
* навигацию;
* отображение данных;
* обработку пользовательского ввода;
* реакции на события EventBus.

---

## Navigation Tests

Проверяются:

* переход вперёд;
* возврат назад;
* замена экранов;
* очистка стека;
* восстановление предыдущего состояния.

---

## Dialog Tests

Необходимо проверить:

* подтверждения;
* предупреждения;
* ошибки;
* отображение прогресса;
* запрос PIN.

---

## Performance Tests

Во время тестирования контролируются:

* время открытия экранов;
* использование памяти;
* количество объектов LVGL;
* плавность анимаций;
* скорость обновления интерфейса.

---

# 46. GUI Code Review Checklist

Перед включением нового GUI-кода рекомендуется проверить следующие пункты.

---

## Architecture

□ Экран не содержит бизнес-логики.

□ Экран не взаимодействует с оборудованием напрямую.

□ Используются только публичные API сервисов.

---

## Navigation

□ Все переходы выполняются через Navigation Manager.

□ Нет прямого создания экранов.

---

## Memory

□ Все объекты LVGL корректно освобождаются.

□ После уничтожения экрана отсутствуют висячие указатели.

---

## EventBus

□ Используются подписки только на необходимые события.

□ Все подписки снимаются при закрытии экрана.

---

## Theme

□ Используются централизованные стили.

□ Не используются жёстко заданные цвета.

---

## Icons

□ Используются только зарегистрированные идентификаторы иконок.

---

## Performance

□ Нет лишних операций обновления.

□ Нет тяжёлых вычислений в GUI Task.

---

Экран самостоятельно изменяет данные пользователя.

Правильно:

Экран вызывает соответствующий сервис.

## Direct Hardware Access

```text
GUI

↓

USB Driver
```

Правильно:

```text
GUI

↓

USBService
```

---

## Direct Storage Access

Неправильно:

```text
GUI

↓

LittleFS
```

Правильно:

```text
GUI

↓

StorageService
```

Подобные операции должны выполняться сервисами.
