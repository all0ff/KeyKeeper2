# Build System Development Guide

**Project:** KeyKeeper2

**Version:** 2.0

---

# Part 1 — Build System Architecture

# 1. Purpose

Документ определяет правила организации системы сборки проекта **KeyKeeper2**.

Он предназначен для разработчиков прошивки и описывает:

* архитектуру системы сборки;
* организацию проекта;
* использование ESP-IDF;
* использование CMake;
* структуру компонентов;
* правила подключения модулей;
* требования к воспроизводимой сборке.

Настоящий документ дополняет:

* BUILD.md
* ARCHITECTURE.md
* SOFTWARE.md

и описывает практические правила сопровождения системы сборки.

---

# 2. Build Philosophy

Система сборки должна обеспечивать:

* воспроизводимость;
* переносимость;
* модульность;
* минимальное количество ручных действий;
* автоматическое определение зависимостей;
* простое подключение новых компонентов.

Любая сборка проекта должна давать одинаковый результат при одинаковых исходных данных.

---

# 3. Build Architecture

Общая схема системы сборки.

```text id="3a8qtw"
Developer

↓

CMake

↓

ESP-IDF Build System

↓

Compiler

↓

Linker

↓

Firmware Image
```

ESP-IDF управляет процессом сборки, а CMake описывает структуру проекта.

---

# 4. Build Components

В сборке участвуют следующие основные элементы.

```text id="3fqjlwm"
Project

├── CMake

├── ESP-IDF

├── Components

├── BSP

├── Services

├── GUI

└── Application
```

Каждый компонент собирается независимо и предоставляет собственный интерфейс.

---

# 5. Project Structure

Рекомендуемая структура проекта:

```text id="zht6n6"
project/

├── main/

├── components/

├── bsp/

├── docs/

├── tools/

├── scripts/

├── sdkconfig.defaults

├── CMakeLists.txt

└── README.md
```

Структура должна оставаться стабильной на протяжении всего жизненного цикла проекта.

---

# 6. ESP-IDF

Проект использует **ESP-IDF** как основную платформу разработки.

ESP-IDF предоставляет:

* FreeRTOS;
* драйверы периферии;
* стек USB;
* сетевой стек;
* файловые системы;
* инструменты сборки;
* систему компонентов.

Низкоуровневые возможности ESP-IDF должны использоваться только через BSP или сервисный слой.

---

# 7. CMake

Вся система сборки основана на **CMake**.

Каждый модуль проекта должен иметь собственный файл `CMakeLists.txt`.

Не допускается создание единого файла сборки для всего проекта.

---

## Responsibilities

Каждый `CMakeLists.txt` отвечает за:

* регистрацию компонента;
* описание исходных файлов;
* экспорт публичных заголовков;
* объявление зависимостей.

---

# 8. Components

Каждый модуль проекта оформляется как отдельный компонент.

Например:

```text id="cb3z3o"
SecurityService

VaultService

StorageService

USBService

GUI

BSP
```

Компоненты должны иметь минимальные зависимости друг от друга.

---

## Component Independence

Компонент должен собираться независимо от остальных, если его зависимости удовлетворены.

Это облегчает:

* сопровождение;
* тестирование;
* повторное использование.

---

# 9. Dependency Management

Все зависимости должны быть явно объявлены.

Не допускается использование неявных зависимостей.

Пример:

```text id="x3u7hq"
GUI

↓

SecurityService

↓

EventBus
```

Если компонент использует другой модуль, зависимость должна быть отражена в системе сборки.

---

# 10. Build Order

Последовательность сборки определяется автоматически системой зависимостей.

Типичная схема:

```text id="8bqgfd"
ESP-IDF

↓

BSP

↓

Core Services

↓

GUI

↓

Application
```

Разработчик не должен вручную управлять порядком сборки.

---

# 11. Configuration Files

Основными файлами конфигурации являются:

* `sdkconfig`
* `sdkconfig.defaults`
* `CMakeLists.txt`

Изменения конфигурации должны быть минимальными и документированными.

---

# 12. Generated Files

Все автоматически создаваемые файлы должны находиться вне исходного дерева проекта.

Например:

```text id="qpk8qs"
build/

sdkconfig

compile_commands.json
```

Эти файлы не должны редактироваться вручную.

---

# 13. Source Organization

Исходный код рекомендуется разделять по функциональным областям.

Например:

```text id="kypknr"
components/

↓

service/

↓

security/

↓

storage/

↓

usb/
```

Такая организация облегчает навигацию по проекту и упрощает сопровождение.

---

# 14. Build Principles

При сопровождении системы сборки рекомендуется придерживаться следующих правил:

* один компонент — одна зона ответственности;
* минимальные зависимости;
* отсутствие циклических ссылок;
* использование возможностей ESP-IDF без их модификации;
* отсутствие ручных изменений автоматически создаваемых файлов;
* воспроизводимость любой сборки;
* документирование всех нестандартных решений.

Следование этим принципам обеспечивает стабильную и масштабируемую систему сборки, соответствующую архитектуре KeyKeeper2.

---

# 15. Build Configurations

Проект поддерживает несколько конфигураций сборки.

Каждая конфигурация предназначена для определённого этапа разработки.

---

## Development Build

Используется во время активной разработки.

Особенности:

* включены сообщения журнала;
* расширенная диагностика;
* проверки ASSERT;
* удобство отладки.

---

## Debug Build

Предназначена для поиска ошибок.

Характеристики:

* максимальная отладочная информация;
* отключённые оптимизации;
* полная символическая информация;
* подробный стек вызовов.

---

## Release Build

Используется для пользовательских прошивок.

Особенности:

* оптимизация размера и производительности;
* отключённые отладочные сообщения;
* минимальное количество диагностической информации;
* стабильная конфигурация.

---

## Test Build

Используется автоматическими тестами.

Дополнительно могут включаться:

* mock-компоненты;
* тестовые драйверы;
* дополнительные проверки.

---

# 16. sdkconfig Management

Файл **sdkconfig** содержит параметры ESP-IDF.

Он не должен использоваться для хранения проектных настроек.

---

## sdkconfig.defaults

Все рекомендуемые параметры проекта должны храниться в:

```text id="s3dt9u"
sdkconfig.defaults
```

Этот файл входит в репозиторий.

---

## sdkconfig

Файл:

```text id="whbqov"
sdkconfig
```

является локальным результатом конфигурирования.

Его изменение вручную не рекомендуется.

---

# 17. Component Dependencies

Каждый компонент обязан явно объявлять зависимости.

Например:

```text id="xzv8al"
GUI

↓

EventBus

↓

SecurityService
```

или

```text id="lq8yks"
VaultService

↓

StorageService
```

---

## Public Dependencies

Публичные зависимости экспортируются другим компонентам.

Они должны быть минимальными.

---

## Private Dependencies

Внутренние зависимости не должны становиться частью публичного интерфейса.

Это уменьшает связанность проекта.

---

# 18. Include Directories

Каждый компонент экспортирует только необходимые заголовочные файлы.

Не рекомендуется открывать весь каталог проекта для поиска include-файлов.

---

## Public Headers

Публичные интерфейсы размещаются отдельно.

Например:

```text id="h7plvt"
include/
```

---

## Private Headers

Внутренние заголовочные файлы не должны использоваться другими компонентами.

---

# 19. Third-Party Libraries

Все сторонние библиотеки подключаются централизованно.

Примеры:

* LVGL;
* TinyUSB;
* mbedTLS;
* ESP-IDF Components.

---

## Modification Policy

Исходный код сторонних библиотек изменять не рекомендуется.

Если требуется исправление:

* использовать официальное обновление;
* оформлять отдельный patch;
* документировать изменения.

---

# 20. Version Management

Каждая сборка должна иметь информацию о версии.

Рекомендуется использовать:

* Major;
* Minor;
* Patch;
* Build Number.

Например:

```text id="v10psb"
2.1.0

Build 145
```

---

## Version Source

Версия должна определяться автоматически.

Не рекомендуется изменять её вручную в нескольких местах проекта.

---

# 21. Build Metadata

В прошивку рекомендуется включать следующую информацию:

* версия;
* дата сборки;
* время сборки;
* версия ESP-IDF;
* ревизия платы;
* Git Commit Hash.

Это облегчает диагностику и поддержку.

---

# 22. Compiler Settings

Все параметры компилятора должны задаваться централизованно.

Не рекомендуется изменять флаги компиляции отдельных компонентов без документированной необходимости.

---

## Warnings

Проект должен собираться без предупреждений.

Рекомендуется использовать строгие проверки компилятора.

При появлении нового предупреждения его следует устранить, а не отключать.

---

## Optimization

Для Release рекомендуется использовать оптимизацию, обеспечивающую баланс между производительностью и размером прошивки.

Настройки оптимизации должны быть одинаковыми для всех компонентов, если нет документированного исключения.

---

# 23. Build Reproducibility

Сборка должна быть полностью воспроизводимой.

При одинаковых:

* исходных файлах;
* версии ESP-IDF;
* версии компилятора;
* конфигурации;

результат сборки должен быть идентичным.

---

## Environment Consistency

Для всех разработчиков рекомендуется использовать одинаковые версии:

* ESP-IDF;
* CMake;
* Ninja;
* Python;
* Toolchain.

Несовпадение версий может привести к различиям в результате сборки.

---

# 24. Build Best Practices

При сопровождении системы сборки рекомендуется:

* использовать единые конфигурации;
* минимизировать количество зависимостей между компонентами;
* экспортировать только необходимые заголовочные файлы;
* использовать `sdkconfig.defaults` как основную конфигурацию проекта;
* не изменять автоматически создаваемые файлы вручную;
* централизованно управлять версиями;
* документировать все нестандартные параметры сборки;
* регулярно проверять сборку в конфигурациях Development, Debug и Release.

Следование этим правилам обеспечивает стабильную систему сборки, облегчает сопровождение проекта и делает процесс разработки предсказуемым для всех участников команды.

---

# 25. Build Automation

Система сборки проекта должна максимально исключать ручные операции.

Любая типовая задача должна выполняться автоматически с использованием стандартных инструментов.

Автоматизации подлежат:

* сборка проекта;
* очистка артефактов;
* генерация документации;
* запуск тестов;
* анализ кода;
* создание прошивки;
* упаковка релизов.

---

## Automation Goals

Автоматизация должна обеспечивать:

* воспроизводимость;
* минимизацию человеческих ошибок;
* одинаковый процесс сборки для всех разработчиков;
* быстрый запуск типовых операций.

---

# 26. Build Scripts

Все вспомогательные сценарии рекомендуется размещать в каталоге:

```text id="q9v8at"
tools/

или

scripts/
```

Каждый сценарий должен выполнять одну определённую задачу.

---

## Typical Scripts

Например:

```text id="s6n3pk"
build

clean

flash

monitor

test

package

docs
```

Названия должны быть понятными и единообразными.

---

# 27. Continuous Integration (CI)

Проект должен поддерживать автоматическую проверку изменений.

Каждый запрос на включение изменений должен автоматически запускать процесс проверки.

---

## CI Pipeline

Рекомендуемая последовательность:

```text id="8dgrmy"
Checkout

↓

Configure

↓

Build

↓

Static Analysis

↓

Unit Tests

↓

Integration Tests

↓

Package
```

Если любой этап завершился ошибкой, процесс считается неуспешным.

---

## CI Requirements

Автоматическая проверка должна гарантировать:

* успешную сборку;
* отсутствие ошибок компиляции;
* отсутствие предупреждений высокого уровня;
* успешное прохождение тестов.

---

# 28. Static Code Analysis

Перед объединением изменений рекомендуется выполнять статический анализ исходного кода.

---

## Goals

Статический анализ помогает обнаружить:

* потенциальные ошибки;
* утечки памяти;
* использование неинициализированных данных;
* опасные конструкции;
* нарушения стандарта кодирования.

---

## Analysis Scope

Проверке подлежит:

* исходный код;
* заголовочные файлы;
* компоненты;
* BSP;
* сервисный слой;
* GUI.

---

# 29. Formatting

Форматирование исходного кода должно быть полностью автоматизировано.

Все разработчики используют единые правила форматирования.

---

## Formatting Tool

Используемый инструмент должен:

* одинаково работать на всех платформах;
* автоматически форматировать код;
* поддерживать C++20.

---

## Formatting Policy

Перед отправкой изменений рекомендуется выполнить автоматическое форматирование проекта.

Ручное форматирование не должно отличаться от автоматического.

---

# 30. Unit Testing

Каждый модуль проекта должен иметь возможность независимого тестирования.

Особенно рекомендуется покрывать тестами:

* сервисный слой;
* алгоритмы;
* бизнес-логику;
* обработку ошибок.

---

## Test Isolation

Unit-тест не должен зависеть:

* от оборудования;
* от GUI;
* от USB;
* от сети;
* от файловой системы.

При необходимости используются mock-компоненты.

---

# 31. Integration Testing

После успешного прохождения модульных тестов выполняется интеграционная проверка.

Интеграционные тесты проверяют взаимодействие компонентов.

Например:

```text id="w2e4zr"
GUI

↓

SecurityService

↓

StorageService
```

или

```text id="50ysl0"
USBService

↓

BSP

↓

USB Driver
```

---

# 32. Hardware Testing

Некоторые функции невозможно проверить без реального оборудования.

К ним относятся:

* дисплей;
* сенсорный экран;
* USB;
* питание;
* GPIO;
* SPI;
* I²C.

Для подобных компонентов рекомендуется использовать отдельный набор аппаратных тестов.

---

# 33. Documentation Generation

Документация должна генерироваться автоматически.

Рекомендуется автоматически формировать:

* API Reference;
* описание компонентов;
* диаграммы зависимостей;
* отчёты анализа.

Автоматически созданные документы не редактируются вручную.

---

# 34. Build Artifacts

После успешной сборки формируются артефакты.

Типичный набор:

```text id="eewa8x"
Firmware

Bootloader

Partition Table

Map File

ELF

Binary Image

Build Report
```

Каждый артефакт должен иметь понятное имя и версию.

---

# 35. Release Packaging

При подготовке релиза рекомендуется автоматически создавать пакет поставки.

Он может содержать:

* бинарные файлы;
* контрольные суммы;
* информацию о версии;
* журнал изменений;
* инструкции по обновлению.

Процесс упаковки должен быть частью автоматизированной сборки.

---

# 36. Build Reports

После завершения сборки рекомендуется формировать отчёт.

Он может включать:

* версию проекта;
* размер прошивки;
* объём Flash;
* использование RAM;
* время сборки;
* результат тестирования.

Такие отчёты облегчают анализ изменений между версиями.

---

# 37. Automation Best Practices

При автоматизации процесса сборки рекомендуется:

* исключить ручные действия;
* выполнять проверку кода автоматически;
* запускать тесты при каждом изменении;
* автоматически формировать документацию;
* автоматически создавать релизные пакеты;
* сохранять отчёты сборки;
* поддерживать одинаковый процесс сборки для всех разработчиков.

Следование этим рекомендациям обеспечивает стабильный процесс разработки, повышает качество программного обеспечения и делает сопровождение проекта более эффективным.

---

# 38. Build Troubleshooting

Несмотря на автоматизацию процесса сборки, во время разработки могут возникать ошибки.

Настоящий раздел описывает общий подход к диагностике проблем.

---

## Troubleshooting Strategy

При возникновении ошибки рекомендуется придерживаться следующей последовательности:

```text id="k7r3tp"
Read Error

↓

Identify Component

↓

Check Configuration

↓

Check Dependencies

↓

Rebuild

↓

Verify Fix
```

Не рекомендуется сразу изменять конфигурацию проекта без анализа причины ошибки.

---

## Typical Build Errors

Наиболее распространённые причины неудачной сборки:

* отсутствующие зависимости;
* ошибки CMake;
* несовместимые версии ESP-IDF;
* повреждённый кэш сборки;
* ошибки компиляции;
* ошибки линковки;
* неправильная конфигурация проекта.

Каждая ошибка должна устраняться в первопричине, а не обходиться временными решениями.

---

# 39. Clean Build

При возникновении трудно диагностируемых ошибок рекомендуется выполнить полную очистку проекта.

Типичная последовательность:

```text id="vqf2zr"
Clean

↓

Configure

↓

Build
```

Полная пересборка позволяет исключить влияние устаревших промежуточных файлов.

---

## Build Cache

Кэш сборки используется только для ускорения компиляции.

Он не должен содержать критически важную информацию проекта.

При необходимости кэш может быть полностью удалён.

---

# 40. Compiler Diagnostics

Компилятор предоставляет наиболее точную информацию о причинах ошибок.

Во время анализа рекомендуется обращать внимание на:

* первое сообщение об ошибке;
* цепочку включения заголовочных файлов;
* предупреждения перед ошибкой;
* сообщения линковщика.

Исправление первой ошибки часто автоматически устраняет множество последующих сообщений.

---

# 41. Dependency Problems

Ошибки зависимостей являются одной из наиболее распространённых причин неудачной сборки.

При обнаружении подобных ошибок необходимо проверить:

* регистрацию компонента;
* экспорт публичных заголовков;
* корректность зависимостей CMake;
* отсутствие циклических ссылок.

---

## Circular Dependencies

Циклические зависимости запрещены.

Например:

```text id="m2g8hw"
GUI

↓

Security

↓

GUI
```

Подобная структура должна быть переработана.

---

# 42. Release Build

Релизная сборка отличается от сборки для разработки.

Основные требования:

* отсутствие отладочных сообщений;
* оптимизация производительности;
* фиксированная конфигурация;
* проверенная версия зависимостей.

Релизная сборка должна формироваться только после успешного прохождения полного цикла тестирования.

---

## Release Verification

Перед выпуском рекомендуется проверить:

* успешную компиляцию;
* успешную линковку;
* размер прошивки;
* использование памяти;
* прохождение автоматических тестов;
* соответствие версии.

---

# 43. Firmware Packaging

После успешной сборки формируется комплект файлов для распространения.

Типичный состав:

```text id="u7zvkb"
Firmware Image

Bootloader

Partition Table

Checksum

Release Notes
```

Все файлы должны иметь единое обозначение версии.

---

## Checksums

Для каждого бинарного файла рекомендуется автоматически вычислять контрольную сумму.

Это позволяет:

* проверить целостность файла;
* обнаружить повреждение при передаче;
* подтвердить идентичность релизов.

---

Каждый релиз должен сопровождаться описанием изменений.

Минимальное содержание:

* номер версии;
* дата выпуска;
* основные изменения;
* исправленные ошибки;
* известные ограничения.

Release Notes являются частью релизного пакета.

# 48. Common Mistakes

Наиболее распространённые ошибки сопровождения системы сборки.

---

## Manual Changes in Generated Files

Запрещается изменять:

* `sdkconfig`;
* содержимое каталога `build`;
* автоматически созданные отчёты.

Изменения должны вноситься в исходные конфигурационные файлы.

---

## Hidden Dependencies

Компонент не должен использовать модуль, который не объявлен как зависимость.

Неявные зависимости усложняют сопровождение проекта.

---

## Environment Differences

Использование различных версий инструментов разработчиками может приводить к различным результатам сборки.

Для всех участников проекта рекомендуется единое окружение разработки.
