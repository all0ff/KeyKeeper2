# BSP Development Guide

**Project:** KeyKeeper2

**Version:** 2.0

---

# Part 1 — BSP Architecture

# 1. Purpose

Документ определяет правила разработки **Board Support Package (BSP)** проекта **KeyKeeper2**.

Он предназначен для разработчиков низкоуровневой части прошивки и описывает:

* архитектуру BSP;
* правила разработки драйверов;
* взаимодействие с ESP-IDF;
* организацию аппаратной абстракции;
* поддержку различных ревизий платы;
* требования к переносимости.

Настоящий документ дополняет **ARCHITECTURE.md** и **SOFTWARE.md** и описывает практические правила реализации аппаратного уровня.

---

# 2. What is BSP

Board Support Package представляет собой слой аппаратной абстракции между операционной системой ESP-IDF и сервисным слоем приложения.

Общая схема:

```text id="0eq5n7"
Application

↓

Service Layer

↓

BSP

↓

ESP-IDF

↓

Hardware
```

BSP скрывает особенности конкретной платы и предоставляет единый программный интерфейс для остальных компонентов проекта.

---

# 3. BSP Philosophy

BSP строится на следующих принципах.

## Hardware Isolation

Весь код, зависящий от аппаратной платформы, должен находиться только внутри BSP.

Остальные компоненты проекта не должны знать:

* номера GPIO;
* используемые SPI-шины;
* параметры дисплея;
* характеристики контроллеров;
* особенности разводки платы.

---

## Stable Interface

Публичный интерфейс BSP должен изменяться как можно реже.

Замена дисплея, сенсорного контроллера или другого оборудования не должна требовать изменения сервисного слоя.

---

## Single Responsibility

Каждый модуль BSP отвечает только за одно аппаратное устройство.

Например:

* Display Driver;
* Touch Driver;
* GPIO Driver;
* USB Driver;
* Power Driver.

Модуль не должен управлять несколькими независимыми устройствами одновременно.

---

## Portability

BSP должен обеспечивать возможность переноса прошивки на новую ревизию платы с минимальными изменениями.

При изменении аппаратной части изменения должны ограничиваться BSP.

---

# 4. BSP Position in Architecture

Место BSP в общей архитектуре проекта.

```text id="9srm5z"
GUI

↓

Service Layer

↓

BSP

↓

ESP-IDF

↓

Hardware
```

Сервисный слой никогда не должен обращаться напрямую к драйверам ESP-IDF.

Все взаимодействие осуществляется через BSP.

---

# 5. Responsibilities

BSP отвечает за:

* инициализацию аппаратных устройств;
* управление периферией;
* предоставление унифицированного API;
* обработку аппаратных событий;
* управление конфигурацией платы.

BSP **не отвечает** за:

* бизнес-логику;
* пользовательский интерфейс;
* безопасность;
* хранение пользовательских данных;
* работу EventBus.

---

# 6. BSP Structure

Рекомендуемая структура каталога BSP:

```text id="qzv6ht"
bsp/

├── board/

├── display/

├── touch/

├── gpio/

├── power/

├── usb/

├── storage/

├── leds/

├── buzzer/

└── common/
```

Каждый каталог реализует один аппаратный компонент или группу тесно связанных компонентов.

---

# 7. Module Responsibilities

Каждый модуль BSP имеет чётко определённую область ответственности.

---

## Board

Отвечает за описание аппаратной платформы:

* ревизию платы;
* конфигурацию выводов;
* параметры оборудования.

---

## Display

Отвечает за:

* инициализацию дисплея;
* передачу кадров;
* управление подсветкой (через отдельный модуль при необходимости);
* предоставление интерфейса для LVGL.

---

## Touch

Отвечает за:

* получение координат касания;
* обработку событий контроллера;
* калибровку.

---

## GPIO

Предоставляет единый интерфейс работы с цифровыми выводами.

Сервисный слой не должен использовать функции GPIO из ESP-IDF напрямую.

---

## Power

Отвечает за:

* включение питания отдельных узлов;
* управление режимами энергопотребления;
* контроль состояния питания.

---

# 8. Public API

Каждый модуль BSP должен предоставлять минимальный публичный интерфейс.

Внешние компоненты должны использовать только публичные функции.

Внутренние структуры модулей не должны быть доступны сервисному слою.

---

## Interface Stability

При разработке необходимо стремиться к совместимости интерфейсов между ревизиями оборудования.

Изменения аппаратной реализации не должны требовать изменения вызывающего кода.

---

# 9. Initialization Model

Инициализация аппаратуры выполняется централизованно.

Типичная последовательность:

```text id="z2r2rj"
Boot

↓

Board Detect

↓

Clock

↓

GPIO

↓

Power

↓

Display

↓

Touch

↓

USB

↓

Storage

↓

Ready
```

Каждый модуль инициализируется только после успешной подготовки зависимостей.

---

# 10. Dependency Rules

Модули BSP должны иметь минимальное количество зависимостей.

Например:

Display может зависеть от SPI.

Touch может зависеть от I²C.

Power может использовать GPIO.

Однако Display не должен зависеть от USB или Storage.

---

# 11. Error Handling

При ошибке инициализации модуль обязан вернуть код ошибки вызывающей стороне.

BSP не должен самостоятельно принимать решение о завершении работы системы.

Решение принимает уровень выше.

---

# 12. Event Model

При возникновении аппаратных событий BSP уведомляет сервисный слой через соответствующий драйвер или сервис.

Типичные события:

* подключение USB;
* отключение USB;
* касание экрана;
* изменение состояния питания;
* обнаружение карты памяти.

BSP не взаимодействует с EventBus напрямую.

---

# 13. Coding Rules

При разработке BSP рекомендуется:

* избегать глобальных переменных;
* минимизировать использование динамической памяти;
* не выполнять длительные операции в обработчиках прерываний;
* документировать все аппаратные зависимости;
* использовать единый стиль именования модулей и функций.

Все аппаратно-зависимые решения должны оставаться внутри BSP и не распространяться на остальные уровни архитектуры.

---

# 14. Display Driver

Display Driver является единственной точкой взаимодействия с дисплеем устройства.

Все остальные компоненты проекта работают с дисплеем исключительно через LVGL и BSP.

Запрещается использовать драйверы ESP-IDF напрямую из сервисного слоя или GUI.

---

## Responsibilities

Display Driver отвечает за:

* инициализацию дисплея;
* настройку интерфейса передачи данных;
* передачу кадров;
* обновление экрана;
* управление режимами дисплея;
* предоставление интерфейса для LVGL.

---

## Display Architecture

Типичная схема взаимодействия:

```text id="l0y2rf"
GUI

↓

LVGL

↓

Display Driver

↓

ESP-IDF

↓

LCD Controller
```

Display Driver скрывает особенности конкретного контроллера дисплея.

---

## Display Initialization

Последовательность инициализации:

```text id="ptv5hm"
Reset

↓

Configure Bus

↓

Initialize Controller

↓

Set Orientation

↓

Enable Backlight

↓

Ready
```

Каждый этап должен завершаться проверкой успешности выполнения.

---

# 15. LVGL Integration

Display Driver предоставляет интерфейс для библиотеки LVGL.

BSP отвечает за:

* регистрацию дисплея;
* передачу буферов изображения;
* уведомление о завершении обновления;
* синхронизацию с аппаратной частью.

GUI не должен знать, какой контроллер дисплея используется.

---

## Flush Callback

Передача изображения выполняется через callback LVGL.

Display Driver обязан:

* принять буфер;
* передать его дисплею;
* уведомить LVGL о завершении передачи.

---

## Double Buffering

При необходимости рекомендуется использовать двойную буферизацию.

Это обеспечивает:

* более плавную анимацию;
* уменьшение мерцания;
* повышение производительности интерфейса.

---

# 16. Touch Driver

Touch Driver отвечает за получение информации от сенсорного контроллера.

Он не взаимодействует с GUI напрямую.

---

## Responsibilities

Touch Driver:

* инициализирует контроллер;
* считывает координаты;
* определяет состояние касания;
* передаёт данные LVGL.

---

## Touch Flow

Типичная последовательность:

```text id="n53a4d"
Touch Controller

↓

Touch Driver

↓

LVGL

↓

GUI
```

---

## Calibration

При необходимости драйвер должен поддерживать калибровку координат.

Все параметры калибровки должны храниться отдельно от логики драйвера.

---

# 17. GPIO Driver

GPIO Driver предоставляет единый интерфейс работы с цифровыми выводами платы.

Остальные компоненты проекта не должны использовать API GPIO из ESP-IDF напрямую.

---

## Responsibilities

GPIO Driver отвечает за:

* настройку выводов;
* чтение входов;
* управление выходами;
* обработку прерываний;
* инкапсуляцию аппаратной конфигурации.

---

## GPIO Naming

Следует использовать логические имена сигналов.

Например:

```text id="h6f8pm"
DISPLAY_RESET

DISPLAY_BACKLIGHT

TOUCH_INTERRUPT

USB_DETECT

POWER_ENABLE

STATUS_LED
```

Использование номеров GPIO в коде сервисного слоя запрещено.

---

# 18. Backlight Driver

Подсветка дисплея должна быть выделена в отдельный модуль.

---

## Responsibilities

Backlight Driver отвечает за:

* включение подсветки;
* выключение подсветки;
* регулировку яркости;
* плавное изменение яркости (при необходимости).

---

## Brightness Control

Яркость должна задаваться через публичный API.

GUI не должен напрямую управлять PWM или GPIO.

---

# 19. Power Driver

Power Driver управляет режимами питания устройства.

---

## Responsibilities

Power Driver отвечает за:

* включение питания;
* отключение питания отдельных компонентов;
* переход в режим сна;
* пробуждение устройства;
* управление энергопотреблением.

---

## Power States

Типичные состояния:

```text id="qg0s7m"
Off

↓

Boot

↓

Active

↓

Idle

↓

Sleep

↓

Wake
```

---

## Safe Shutdown

Перед отключением питания Power Driver обязан:

* завершить активные операции;
* уведомить сервисный слой;
* перевести оборудование в безопасное состояние.

---

# 20. LED Driver

Если плата содержит светодиодную индикацию, управление выполняется отдельным модулем.

---

## Responsibilities

LED Driver отвечает за:

* включение;
* выключение;
* мигание;
* индикацию состояний.

Логика отображения состояния устройства определяется сервисным слоем.

---

# 21. Buzzer Driver

При наличии звукового сигнала рекомендуется выделить отдельный драйвер.

---

## Responsibilities

Buzzer Driver отвечает за:

* воспроизведение коротких сигналов;
* управление длительностью;
* управление частотой (при необходимости).

GUI не должен управлять аппаратным таймером напрямую.

---

# 22. Interrupt Handling

Все аппаратные прерывания должны обрабатываться максимально быстро.

Обработчик прерывания не должен:

* выполнять длительные вычисления;
* выделять память;
* обращаться к файловой системе;
* выполнять сетевые операции.

При необходимости ISR должен только зарегистрировать событие и передать его на дальнейшую обработку.

---

# 23. Driver Error Handling

Каждый драйвер обязан корректно сообщать об ошибках.

Типичные ошибки:

* устройство не обнаружено;
* ошибка инициализации;
* ошибка передачи данных;
* аппаратный сбой;
* неверная конфигурация.

Драйвер не должен самостоятельно завершать работу системы.

---

# 24. Driver Development Best Practices

При разработке драйверов рекомендуется:

* использовать единый публичный API;
* полностью скрывать аппаратные особенности реализации;
* минимизировать количество зависимостей между драйверами;
* не использовать глобальные аппаратные константы вне BSP;
* проверять результаты всех аппаратных операций;
* документировать особенности конкретной аппаратной платформы;
* проектировать драйверы таким образом, чтобы их можно было заменить без изменения сервисного слоя.

Такой подход обеспечивает переносимость проекта, упрощает поддержку новых ревизий платы и полностью соответствует компонентной архитектуре KeyKeeper2.

---

# 25. USB Driver

USB Driver обеспечивает аппаратное взаимодействие устройства с USB-интерфейсом.

Драйвер предоставляет унифицированный интерфейс независимо от используемой реализации USB в ESP-IDF.

---

## Responsibilities

USB Driver отвечает за:

* инициализацию USB;
* определение состояния подключения;
* управление USB PHY;
* передачу событий USBService;
* обработку аппаратных ошибок.

USB Driver не реализует бизнес-логику обмена данными.

---

## Architecture

Типичная схема:

```text id="4kt1ph"
USBService

↓

USB Driver

↓

TinyUSB

↓

ESP-IDF

↓

USB Hardware
```

Все особенности реализации USB скрываются внутри BSP.

---

## Connection Events

USB Driver должен сообщать о следующих событиях:

* Cable Connected
* Cable Disconnected
* Enumeration Complete
* Suspend
* Resume
* Error

Передача событий выполняется через сервисный слой.

---

# 26. SPI Driver

SPI Driver предоставляет единый интерфейс для всех SPI-устройств платы.

---

## Responsibilities

SPI Driver отвечает за:

* инициализацию SPI;
* управление скоростью передачи;
* передачу данных;
* синхронизацию доступа к шине;
* конфигурацию устройств.

---

## Shared Bus

Если несколько устройств используют одну SPI-шину, драйвер обязан корректно управлять доступом.

Например:

```text id="8hrlms"
Display

↓

SPI Driver

↑

Flash
```

Все переключения Chip Select должны выполняться драйвером.

---

# 27. I²C Driver

I²C Driver инкапсулирует работу с устройствами, подключёнными по шине I²C.

---

## Responsibilities

Драйвер отвечает за:

* настройку шины;
* обнаружение устройств;
* чтение регистров;
* запись регистров;
* обработку ошибок передачи.

---

## Connected Devices

Типичные устройства:

* Touch Controller
* RTC
* Sensor
* Battery Monitor

Каждый клиент использует общий API I²C Driver.

---

# 28. Flash Driver

Flash Driver предоставляет интерфейс для работы с внешней или внутренней Flash-памятью.

---

## Responsibilities

Flash Driver отвечает за:

* чтение;
* запись;
* стирание;
* проверку доступности памяти;
* получение информации о разделах.

---

## Abstraction

StorageService никогда не должен знать:

* тип памяти;
* производителя;
* параметры микросхемы.

Все особенности реализации скрываются внутри Flash Driver.

---

# 29. SD Card Driver

При наличии поддержки microSD используется отдельный драйвер.

---

## Responsibilities

SD Driver отвечает за:

* обнаружение карты;
* подключение;
* отключение;
* чтение;
* запись;
* проверку состояния.

---

## Hot Plug

Если аппаратная платформа поддерживает горячее подключение карты памяти, драйвер должен корректно обрабатывать:

* вставку карты;
* извлечение карты;
* ошибки чтения;
* ошибки записи.

---

# 30. RTC Driver

Если устройство оснащено часами реального времени, используется отдельный драйвер.

---

## Responsibilities

RTC Driver отвечает за:

* чтение времени;
* установку времени;
* синхронизацию;
* контроль состояния часов.

Все вычисления времени выполняются сервисным слоем.

---

# 31. Hardware Timers

Аппаратные таймеры должны использоваться только внутри BSP.

---

## Responsibilities

BSP отвечает за:

* создание таймеров;
* запуск;
* остановку;
* освобождение ресурсов.

Остальные компоненты работают через соответствующие сервисы.

---

# 32. DMA Usage

Если аппаратная периферия поддерживает DMA, рекомендуется использовать его для:

* дисплея;
* USB;
* SPI;
* SD.

Использование DMA должно быть полностью скрыто внутри BSP.

---

# 33. Clock Configuration

Настройка тактирования выполняется централизованно.

BSP отвечает за:

* выбор источника тактирования;
* настройку PLL;
* конфигурацию периферийных частот;
* проверку стабильности системы.

Сервисный слой не должен изменять параметры тактирования.

---

# 34. Hardware Resources

Все аппаратные ресурсы должны распределяться централизованно.

К ним относятся:

* GPIO;
* SPI;
* I²C;
* UART;
* USB;
* DMA;
* таймеры;
* PWM;
* ADC.

Каждый ресурс должен иметь единственного владельца.

---

# 35. Resource Ownership

Для предотвращения конфликтов необходимо определить владельца каждого аппаратного ресурса.

Пример:

```text id="w7c4tb"
SPI1

↓

Display Driver

I²C0

↓

Touch Driver

USB

↓

USB Driver
```

Два драйвера не должны одновременно управлять одним и тем же аппаратным интерфейсом.

---

# 36. Hardware Error Recovery

Каждый драйвер должен поддерживать восстановление после типичных аппаратных ошибок.

Например:

* повторная инициализация устройства;
* повторная передача данных;
* сброс контроллера;
* восстановление после потери питания.

Если восстановление невозможно, драйвер обязан сообщить об ошибке вызывающему компоненту.

---

# 37. BSP Performance

При разработке BSP необходимо стремиться к минимальным накладным расходам.

Рекомендуется:

* избегать лишнего копирования данных;
* использовать DMA при больших объёмах передачи;
* минимизировать блокировки;
* не выполнять тяжёлые операции в ISR;
* использовать аппаратные возможности контроллера.

---

# 38. Driver Best Practices

При разработке аппаратных драйверов рекомендуется:

* полностью скрывать реализацию оборудования;
* использовать единый стиль API;
* минимизировать зависимости между драйверами;
* корректно освобождать аппаратные ресурсы;
* документировать ограничения оборудования;
* проектировать драйверы таким образом, чтобы их можно было заменить без изменения сервисного слоя.

Следование этим правилам обеспечивает переносимость BSP, упрощает поддержку новых аппаратных платформ и делает код независимым от конкретной ревизии устройства.

---

# 39. Board Initialization

Инициализация аппаратной платформы выполняется централизованно.

За последовательность запуска отвечает модуль **Board Manager**.

Все аппаратные компоненты должны быть подготовлены до запуска сервисного слоя.

---

## Boot Sequence

Рекомендуемая последовательность запуска:

```text
Power On

↓

CPU Initialization

↓

Clock Configuration

↓

GPIO Initialization

↓

Power Driver

↓

Display Driver

↓

Touch Driver

↓

USB Driver

↓

Storage Driver

↓

Board Ready

↓

Application Start
```

Каждый этап завершается проверкой успешности выполнения.

При возникновении ошибки дальнейшая инициализация прекращается.

---

# 40. Board Configuration

Описание аппаратной платформы должно быть полностью отделено от логики драйверов.

Конфигурация платы включает:

* ревизию устройства;
* используемый дисплей;
* тип сенсорного контроллера;
* схему подключения периферии;
* параметры питания;
* особенности разводки платы.

Все параметры должны храниться централизованно.

---

## Configuration Files

Рекомендуется использовать отдельные конфигурационные файлы для каждой ревизии платы.

Например:

```text
board_rev_a

board_rev_b

board_rev_c
```

Драйверы получают параметры из конфигурации и не должны содержать аппаратно-зависимые константы.

---

# 41. Multi-Board Support

Архитектура BSP должна предусматривать поддержку нескольких аппаратных платформ.

При добавлении новой платы изменения должны ограничиваться:

* конфигурацией платы;
* аппаратными драйверами;
* параметрами инициализации.

Сервисный слой и GUI не должны изменяться.

---

## Hardware Variants

Поддержка различных вариантов оборудования должна быть прозрачной для приложения.

Например, разные модели дисплеев или сенсорных контроллеров должны использовать одинаковый публичный API.

---

# 42. Board Detection

Если аппаратная платформа позволяет определить ревизию автоматически, эта процедура выполняется во время запуска.

Типичный процесс:

```text
Boot

↓

Read Board ID

↓

Select Configuration

↓

Initialize Drivers
```

Если автоматическое определение невозможно, используется заранее выбранная конфигурация.

---

# 43. Hardware Diagnostics

BSP должен предоставлять средства базовой диагностики оборудования.

Во время запуска рекомендуется проверить:

* доступность дисплея;
* работу сенсорного контроллера;
* состояние USB;
* доступность памяти;
* наличие карты памяти (при использовании);
* состояние источника питания.

Результаты проверки передаются сервисному слою.

---

# 44. Self-Test

При необходимости BSP может поддерживать режим самодиагностики.

Самодиагностика позволяет проверить:

* GPIO;
* SPI;
* I²C;
* USB;
* дисплей;
* сенсор;
* Flash;
* SD Card.

Режим самодиагностики должен быть независим от пользовательского интерфейса.

---

# 45. BSP Testing

Каждый драйвер должен тестироваться отдельно.

Рекомендуется выполнять:

* модульные тесты;
* интеграционные тесты;
* тесты производительности;
* стресс-тесты;
* тесты восстановления после ошибок.

Каждый аппаратный модуль должен иметь собственный набор тестов.

---

## Driver Tests

Для каждого драйвера рекомендуется проверить:

* успешную инициализацию;
* повторную инициализацию;
* корректную обработку ошибок;
* восстановление после аппаратного сбоя;
* освобождение ресурсов.

---

# 46. BSP Code Review Checklist

Перед включением нового BSP-кода рекомендуется проверить следующие пункты.

---

## Architecture

□ Аппаратная зависимость полностью локализована в BSP.

□ Публичный API минимален и стабилен.

□ Нет обращения к ESP-IDF из сервисного слоя.

---

## Drivers

□ Каждый драйвер отвечает только за своё устройство.

□ Нет скрытых зависимостей между драйверами.

□ Все аппаратные ошибки обрабатываются.

---

## Resources

□ Аппаратные ресурсы имеют единственного владельца.

□ Нет конфликтов использования SPI, I²C, GPIO и других интерфейсов.

---

## Memory

□ Отсутствуют утечки памяти.

□ Корректно освобождаются аппаратные ресурсы.

---

## Initialization

□ Последовательность запуска соответствует архитектуре.

□ Все ошибки корректно возвращаются вызывающей стороне.

---

# 47. Common Mistakes

Наиболее распространённые ошибки при разработке BSP.

---

## Hardware Constants Outside BSP

Неправильно:

Использование номеров GPIO в сервисном слое.

Правильно:

Все аппаратные параметры определяются только внутри BSP.

---

## Direct ESP-IDF Calls

Неправильно:

```text
Service

↓

ESP-IDF
```

Правильно:

```text
Service

↓

BSP

↓

ESP-IDF
```

---

## Mixed Responsibilities

Неправильно:

Один драйвер одновременно управляет дисплеем, подсветкой и сенсором.

Правильно:

Каждое устройство имеет собственный специализированный драйвер.

---

## Hardware Knowledge in GUI

GUI не должен знать:

* модель дисплея;
* тип контроллера;
* номера GPIO;
* параметры шин.

Вся информация скрыта внутри BSP.

---

# 48. BSP Best Practices

При разработке рекомендуется:

* полностью изолировать аппаратно-зависимый код;
* использовать единый стиль API;
* централизовать конфигурацию платы;
* минимизировать зависимости между драйверами;
* документировать особенности оборудования;
* проектировать драйверы с возможностью замены оборудования;
* использовать логические идентификаторы вместо аппаратных констант;
* своевременно освобождать аппаратные ресурсы;
* выполнять проверку результатов всех аппаратных операций.
