# ESP-IDF Development Guide

**Project:** KeyKeeper2

**Version:** 2.0

---

# Purpose

Документ определяет правила использования **ESP-IDF** в проекте **KeyKeeper2**.

Он описывает:

* архитектурные ограничения;
* рекомендуемые компоненты ESP-IDF;
* правила использования SDK;
* взаимодействие с сервисным слоем проекта.

Документ не является руководством по ESP-IDF.

---

# Supported Version

Проект использует официальную версию:

**ESP-IDF 5.x**

Использование других версий допускается только после проверки совместимости и обновления документации.

---

# Architecture Position

ESP-IDF является базовым программным уровнем проекта.

Общая архитектура:

```text id="t8w3dj"
Application

↓

Service Layer

↓

BSP

↓

ESP-IDF

↓

ESP32-S3 Hardware
```

Прикладные компоненты не должны зависеть от внутренних деталей ESP-IDF.

---

# ESP-IDF Components

Проект использует следующие основные компоненты ESP-IDF:

* FreeRTOS;
* NVS;
* SPI Flash;
* FATFS;
* LittleFS;
* SDMMC;
* USB Device;
* TinyUSB;
* Wi-Fi;
* HTTP Server;
* mbedTLS;
* ESP Timer;
* GPIO;
* SPI Master;
* I2C (при необходимости);
* Logging.

Использование дополнительных компонентов должно быть обосновано архитектурными требованиями.

---

# Component Boundaries

Каждый компонент проекта использует только необходимые ему возможности ESP-IDF.

Например:

* GUI не работает напрямую с GPIO;
* VaultService не использует файловую систему напрямую;
* USBService не обращается к драйверам дисплея;
* SecurityService не использует аппаратные драйверы.

Доступ к аппаратным возможностям осуществляется через BSP или соответствующий сервис.

---

# Initialization

Инициализация системы выполняется поэтапно.

Типичная последовательность:

```text id="d2cfvx"
ESP-IDF

↓

BSP

↓

Storage

↓

Security

↓

GUI

↓

Application
```

Каждый компонент отвечает за собственную инициализацию.

---

# FreeRTOS Integration

ESP-IDF предоставляет FreeRTOS как основу многозадачной системы.

Все задачи создаются через специализированные сервисы проекта.

Прямое создание задач в пользовательском интерфейсе или бизнес-логике не рекомендуется.

---

# Logging

Для журналирования используется подсистема логирования ESP-IDF.

Все сообщения должны использовать единый формат.

Рекомендуется применять уровни:

* Error;
* Warning;
* Info;
* Debug;
* Verbose.

Вывод через `printf()` в прикладном коде не допускается.

---

# Memory Management

Необходимо учитывать ограничения встроенной платформы.

Рекомендуется:

* минимизировать динамическое выделение памяти;
* использовать статические объекты при возможности;
* избегать фрагментации памяти;
* контролировать объём стека задач.

---

# NVS

NVS используется только для хранения системных параметров.

Примеры:

* конфигурация устройства;
* сетевые параметры;
* пользовательские настройки.

Конфиденциальные пользовательские данные в NVS не сохраняются.

---

# File Systems

Проект использует две файловые системы.

## LittleFS

Основное внутреннее хранилище.

Используется для:

* базы данных;
* конфигурации;
* внутренних файлов.

---

## microSD

Используется для:

* резервного копирования;
* импорта;
* экспорта;
* пользовательских файлов.

Работа с файловыми системами выполняется через StorageService.

---

# USB

ESP-IDF предоставляет аппаратную поддержку USB.

Протокол USB HID реализуется компонентом USBService.

Прикладной код не должен взаимодействовать с TinyUSB напрямую.

---

# Wi-Fi

ESP-IDF предоставляет стек Wi-Fi.

Работа с сетью выполняется исключительно через WiFiService.

Другие компоненты используют только публичный API сервиса.

---

# HTTP Server

Встроенный HTTP Server используется только WebService.

GUI, VaultService и другие компоненты не работают с HTTP напрямую.

---

# Timers

Для работы со временем рекомендуется использовать:

* ESP Timer;
* FreeRTOS Timers.

Использование аппаратных таймеров напрямую допускается только внутри BSP.

---

# GPIO

Работа с GPIO выполняется исключительно через BSP.

Использование функций:

* gpio_set_level();
* gpio_get_level();
* gpio_config();

в прикладных компонентах запрещено.

---

# SPI / I2C

Все аппаратные интерфейсы инициализируются BSP.

Прикладной код не должен самостоятельно открывать SPI- или I2C-устройства.

---

# Error Handling

Все функции ESP-IDF должны проверять возвращаемые значения.

Используются:

* `esp_err_t`;
* `ESP_OK`;
* `ESP_ERROR_CHECK()`;
* специализированные обработчики ошибок.

Игнорирование ошибок не допускается.

---

# Build Integration

Сборка проекта полностью выполняется средствами ESP-IDF.

Используются:

* idf.py;
* CMake;
* sdkconfig.

Изменения конфигурации должны документироваться.

---

# Best Practices

При разработке рекомендуется:

* использовать официальные API ESP-IDF;
* минимизировать зависимость компонентов от SDK;
* изолировать аппаратно-зависимый код в BSP;
* использовать сервисный слой вместо прямых вызовов драйверов;
* соблюдать требования Documentation First.

# Summary

Проект **KeyKeeper2** использует **ESP-IDF 5.x** как базовую программную платформу.

ESP-IDF обеспечивает доступ к аппаратным ресурсам ESP32-S3, однако прикладные компоненты взаимодействуют с ним только через BSP и сервисный слой. Такой подход снижает связанность компонентов, упрощает сопровождение проекта и обеспечивает переносимость архитектуры при сохранении всех преимуществ официального SDK.
