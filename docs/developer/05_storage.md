# Storage Development Guide

**Project:** KeyKeeper2

**Version:** 2.0

---

# Purpose

Документ определяет правила разработки подсистемы хранения данных проекта **KeyKeeper2**.

Он описывает:

* архитектуру хранения;
* StorageService;
* StorageProvider;
* работу с LittleFS;
* работу с microSD;
* правила доступа к данным;
* резервное копирование;
* импорт и экспорт.

Документ предназначен для разработчиков подсистемы хранения и сервисов, использующих пользовательские данные.

---

# Architecture Position

Подсистема хранения располагается в сервисном слое.

Общая архитектура:

```text id="0vzvtn"
Application

↓

GUI

↓

EventBus

↓

StorageService

↓

StorageProvider

↓

LittleFS / microSD

↓

ESP-IDF
```

Все операции хранения проходят через StorageService.

---

# Design Principles

Подсистема хранения построена на следующих принципах:

* единая точка доступа;
* отсутствие прямой работы с файловой системой;
* независимость сервисов от типа носителя;
* возможность замены реализации без изменения бизнес-логики;
* разделение внутреннего и внешнего хранения.

---

# Responsibilities

StorageService отвечает за:

* сохранение данных;
* загрузку данных;
* удаление данных;
* резервное копирование;
* импорт;
* экспорт;
* миграцию структуры хранения.

StorageService не выполняет криптографические операции.

Шифрование выполняется SecurityService.

---

# StorageProvider

StorageProvider является уровнем абстракции файловой системы.

Он скрывает:

* LittleFS;
* FATFS;
* SDMMC;
* особенности ESP-IDF.

Все операции ввода-вывода проходят через StorageProvider.

---

# Storage Layout

Подсистема хранения использует два физических носителя.

## Internal Storage

LittleFS используется для:

* базы данных;
* пользовательских записей;
* конфигурации;
* служебных файлов.

---

## External Storage

microSD используется для:

* резервного копирования;
* импорта;
* экспорта;
* пользовательских архивов.

Основная база данных не работает непосредственно с microSD.

---

```text id="bjlwm4"
GUI

↓

StorageService

↓

StorageProvider

↓

LittleFS
```

Типичный сценарий резервного копирования:

```text id="jz2rrm"
StorageService

↓

StorageProvider

↓

LittleFS

↓

microSD
```

---

# File Organization

Типичная структура внутреннего хранилища:

```text id="zptd8p"
/vault/

/settings/

/system/

/cache/

/logs/
```

Структура может расширяться без изменения публичного API StorageService.

---

# File Access

Прямое использование:

* fopen();
* fread();
* fwrite();
* LittleFS API;
* FATFS API

в прикладных компонентах запрещено.

Все операции выполняются через StorageService.

---

# Database Access

Работа с пользовательскими записями выполняется только через VaultService.

VaultService использует StorageService.

GUI никогда не работает с файлами напрямую.

---

# Backup

StorageService отвечает за создание резервных копий.

Типичный процесс:

```text id="6h8j4w"
LittleFS

↓

Export

↓

Encryption

↓

microSD
```

Каждая операция должна проверяться на успешное завершение.

---

# Import

При импорте выполняются следующие этапы:

1. проверка структуры файла;
2. проверка версии;
3. проверка контрольной суммы;
4. расшифрование (при необходимости);
5. импорт данных.

Импорт не должен повреждать существующую базу данных.

---

# Export

Экспорт выполняется через StorageService.

При необходимости экспортируемые данные шифруются SecurityService.

---

# Transactions

При изменении данных рекомендуется использовать атомарную запись.

Типичная последовательность:

```text id="eqpp4d"
Create Temporary File

↓

Write Data

↓

Verify

↓

Replace Original
```

Такой подход снижает вероятность повреждения данных при аварийном завершении работы.

---

# Versioning

Все структуры хранения должны содержать информацию о версии.

При несовместимых изменениях StorageService выполняет миграцию данных.

Миграция должна быть полностью документирована.

---

# Error Handling

Все операции хранения должны проверяться.

Типичные ошибки:

* отсутствие файла;
* повреждение файловой системы;
* нехватка памяти;
* ошибка записи;
* ошибка чтения;
* отсутствие microSD.

Ошибки передаются вызывающему компоненту через единый механизм обработки.

---

# Performance

Рекомендуется:

* минимизировать количество операций записи;
* избегать частого открытия и закрытия файлов;
* использовать буферизацию;
* не выполнять длительные операции в GUI Task.

---

# Thread Safety

StorageService должен обеспечивать корректную работу при обращении из нескольких задач.

Доступ к внутреннему хранилищу должен быть синхронизирован.

Не допускается одновременная запись в один и тот же файл.

---

# Testing

Подсистема хранения должна тестироваться отдельно.

Необходимо проверять:

* создание файлов;
* чтение;
* запись;
* удаление;
* резервное копирование;
* импорт;
* экспорт;
* восстановление после ошибок.

---

# Best Practices

При разработке рекомендуется:

* использовать только публичный API StorageService;
* избегать прямой работы с файловыми системами;
* не смешивать хранение данных и бизнес-логику;
* использовать атомарные операции записи;
* минимизировать количество обращений к Flash;
* регулярно проверять целостность данных.

# Summary

Подсистема хранения **KeyKeeper2** построена вокруг **StorageService** и **StorageProvider**, которые обеспечивают единый механизм работы с внутренним и внешним хранилищем.

Все операции с пользовательскими данными выполняются через сервисный слой, что изолирует компоненты от особенностей файловых систем, упрощает сопровождение проекта и обеспечивает возможность безопасного развития архитектуры без изменения прикладного кода.
