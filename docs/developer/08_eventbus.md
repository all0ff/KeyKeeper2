# EventBus Development Guide

**Project:** KeyKeeper2

**Version:** 2.0

---

# Purpose

Документ определяет правила разработки и использования **EventBus** в проекте **KeyKeeper2**.

Он описывает:

* архитектуру событийной системы;
* модель публикации событий;
* подписку на события;
* жизненный цикл сообщений;
* взаимодействие компонентов;
* рекомендации по проектированию событий.

Документ предназначен для всех разработчиков проекта.

---

# Architecture Position

EventBus является центральным механизмом обмена сообщениями между компонентами.

Общая архитектура:

```text id="6ytr4j"
GUI

↓

EventBus

↓

Service Layer

↓

Storage / USB / Web / Security
```

Компоненты взаимодействуют друг с другом через EventBus, а не напрямую.

---

# Design Principles

EventBus построен на следующих принципах:

* слабая связанность компонентов;
* отсутствие прямых зависимостей;
* асинхронное взаимодействие;
* централизованная маршрутизация событий;
* единая модель сообщений.

---

# Responsibilities

EventBus отвечает за:

* публикацию событий;
* регистрацию подписчиков;
* доставку сообщений;
* маршрутизацию событий;
* изоляцию компонентов.

EventBus не содержит бизнес-логики.

---

# Communication Model

Каждый компонент может:

* публиковать события;
* подписываться на события.

Типичная схема:

```text id="pjh7wz"
Publisher

↓

EventBus

↓

Subscriber
```

Издатель не знает, кто получит сообщение.

Подписчик не знает, кто отправил событие.

---

# Event Lifecycle

Каждое событие проходит одинаковый жизненный цикл.

```text id="t8n5sv"
Create

↓

Publish

↓

Queue

↓

Dispatch

↓

Handle

↓

Destroy
```

После обработки событие считается завершённым.

---

# Event Structure

Каждое событие должно содержать:

* идентификатор;
* источник;
* тип события;
* полезные данные;
* время создания (при необходимости).

Структура события должна быть минимальной и однозначной.

---

# Event Categories

Рекомендуется разделять события по категориям.

Например:

* GUI;
* Security;
* Storage;
* USB;
* Wi-Fi;
* Web;
* System;
* Settings.

Такое разделение упрощает сопровождение проекта.

---

# Publish

Публикация выполняется через единый интерфейс EventBus.

Компонент не должен знать, сколько подписчиков существует.

Публикация должна быть неблокирующей.

---

# Subscribe

Компоненты подписываются только на необходимые события.

Не рекомендуется создавать универсальных подписчиков, обрабатывающих все типы сообщений.

---

# Data Flow

Типичный пользовательский сценарий:

```text id="8mru6h"
User

↓

GUI

↓

EventBus

↓

VaultService

↓

StorageService
```

USB-сценарий:

```text id="wh7n9p"
GUI

↓

EventBus

↓

USBService
```

Сетевой сценарий:

```text id="g6kx3f"
GUI

↓

EventBus

↓

WiFiService

↓

WebService
```

---

# Component Independence

Компоненты не должны:

* вызывать методы друг друга напрямую;
* использовать внутренние структуры другого сервиса;
* обращаться к чужим данным.

Взаимодействие должно выполняться только через EventBus или публичный API сервиса.

---

# Event Processing

Обработчики событий должны:

* выполнять минимальный объём работы;
* не выполнять длительные операции;
* не блокировать очередь сообщений;
* при необходимости передавать тяжёлые операции специализированным сервисам.

---

# Thread Safety

EventBus должен обеспечивать безопасную работу в многозадачной среде.

Публикация и обработка событий могут выполняться из различных задач.

Внутренняя синхронизация полностью скрыта внутри EventBus.

---

# Error Handling

Ошибки доставки событий должны обрабатываться централизованно.

Типичные ошибки:

* отсутствует подписчик;
* переполнение очереди;
* повреждённое сообщение;
* ошибка обработки.

EventBus не должен завершать работу системы из-за ошибки отдельного обработчика.

---

# Performance

Рекомендуется:

* использовать компактные структуры событий;
* не передавать большие объекты через EventBus;
* передавать ссылки или идентификаторы вместо копирования данных;
* минимизировать количество публикуемых сообщений.

---

# Event Naming

Имена событий должны быть понятными и однозначными.

Например:

```text id="u8es1t"
SecurityUnlocked

VaultOpened

StorageSaved

USBConnected

USBTransferFinished

WiFiConnected

WebServerStarted
```

Использование сокращений не рекомендуется.

---

# Testing

EventBus должен тестироваться независимо от остальных компонентов.

Необходимо проверять:

* регистрацию подписчиков;
* публикацию событий;
* доставку сообщений;
* обработку нескольких подписчиков;
* обработку ошибок;
* работу под нагрузкой.

---

# Best Practices

При разработке рекомендуется:

* использовать EventBus для обмена информацией между компонентами;
* публиковать только завершённые события;
* избегать циклических зависимостей;
* не выполнять тяжёлую обработку в обработчиках событий;
* минимизировать объём передаваемых данных;
* придерживаться единой схемы именования событий.

# Summary

**EventBus** является центральным механизмом взаимодействия компонентов проекта **KeyKeeper2**.

Все сервисы и подсистемы обмениваются информацией посредством публикации и обработки событий, что обеспечивает слабую связанность компонентов, высокую расширяемость системы и соответствие компонентной архитектуре проекта. EventBus не содержит бизнес-логики и служит исключительно инфраструктурным механизмом доставки сообщений между независимыми сервисами.
