# FreeRTOS Development Guide

**Project:** KeyKeeper2

**Version:** 2.0

---

# Purpose

Документ определяет правила использования **FreeRTOS** в проекте **KeyKeeper2**.

Он описывает:

* архитектуру многозадачности;
* организацию задач;
* синхронизацию компонентов;
* обмен сообщениями;
* взаимодействие с EventBus;
* рекомендации по разработке.

Документ не является руководством по FreeRTOS.

---

# Architecture Position

FreeRTOS является основой выполнения программного обеспечения.

Общая структура системы:

```text id="2vgxux"
Application

↓

Service Layer

↓

FreeRTOS

↓

ESP-IDF

↓

Hardware
```

Все компоненты работают поверх FreeRTOS.

---

# Design Principles

При использовании FreeRTOS необходимо соблюдать следующие принципы:

* минимальное количество задач;
* отсутствие блокирующих операций в GUI;
* обмен данными через сообщения;
* минимизация разделяемого состояния;
* чёткое разделение ответственности между задачами.

---

# Task Model

Каждая задача должна выполнять только одну область ответственности.

Типичные задачи проекта:

* GUI Task;
* EventBus Task;
* USB Task;
* Web Task;
* WiFi Task;
* Storage Task (при необходимости);
* Background Task.

Создание дополнительных задач должно быть архитектурно обосновано.

---

# Recommended Architecture

Типичная схема взаимодействия:

```text id="8qhrmz"
GUI Task

↓

EventBus

↓

Service Layer

↓

Storage / USB / Web
```

Компоненты не должны взаимодействовать друг с другом напрямую через глобальные объекты.

---

# GUI Task

GUI Task является единственной задачей, имеющей доступ к LVGL.

Все операции с объектами интерфейса выполняются только из этой задачи.

Другие задачи не должны обращаться к объектам LVGL напрямую.

---

# EventBus Task

EventBus обеспечивает передачу сообщений между компонентами.

Его задачи:

* публикация событий;
* доставка подписчикам;
* минимизация связанности компонентов.

EventBus не содержит бизнес-логики.

---

# Service Tasks

Сервисы могут иметь собственные задачи только в случае необходимости.

Например:

* WebService;
* USBService;
* WiFiService.

SecurityService, SettingsService и VaultService предпочтительно работают синхронно через публичный API.

---

# Communication

Основной способ взаимодействия между задачами:

* очереди сообщений;
* EventBus;
* уведомления задач (Task Notifications) — для простых сигналов;
* семафоры — только при необходимости.

Прямой доступ к данным другой задачи запрещён.

---

# Queues

Очереди используются для передачи данных между задачами.

Типичные примеры:

* события GUI;
* команды USB;
* сетевые запросы;
* сообщения EventBus.

Очереди должны иметь ограниченный размер и контролируемое переполнение.

---

# Mutexes

Мьютексы применяются только для защиты действительно разделяемых ресурсов.

Их использование должно быть минимальным.

Не допускается длительное удержание мьютекса.

---

# Semaphores

Семафоры используются для синхронизации задач и обработки событий.

Они не должны применяться вместо очередей для передачи данных.

---

# Timers

Для периодических операций используются программные таймеры FreeRTOS.

Типичные задачи:

* автоблокировка;
* обновление интерфейса;
* периодическая синхронизация;
* обслуживание фоновых процессов.

---

# Priorities

Приоритеты задач должны отражать их функциональную важность.

Рекомендуемый порядок:

```text id="qgksn9"
High

GUI

USB

Web

WiFi

Background

Idle
```

Не допускается неоправданное использование максимальных приоритетов.

---

# Stack Management

Каждая задача должна иметь минимально достаточный размер стека.

Во время разработки необходимо контролировать использование стека средствами FreeRTOS.

Избыточный запас памяти не рекомендуется.

---

# Blocking Operations

Следует избегать длительных блокирующих операций.

Особенно запрещается выполнять длительные операции в:

* GUI Task;
* EventBus Task.

Продолжительные операции должны выполняться в специализированных сервисах.

---

# Thread Safety

Все компоненты должны быть потокобезопасными.

Если компонент используется несколькими задачами, его интерфейс должен обеспечивать корректную синхронизацию.

Разделяемое состояние следует минимизировать.

---

# Memory Allocation

Рекомендуется:

* создавать задачи при инициализации системы;
* избегать постоянного создания и удаления задач во время работы;
* минимизировать динамическое выделение памяти.

---

# Error Handling

Все ошибки FreeRTOS должны обрабатываться.

Особое внимание следует уделять:

* невозможности создания задачи;
* переполнению очередей;
* переполнению стека;
* ошибкам синхронизации.

Игнорирование ошибок не допускается.

---

# Best Practices

При разработке рекомендуется:

* использовать EventBus для взаимодействия компонентов;
* минимизировать количество задач;
* избегать блокирующих вызовов;
* использовать очереди вместо глобальных переменных;
* ограничивать использование мьютексов;
* тщательно подбирать размеры стеков;
* регулярно контролировать производительность системы.

# Summary

Проект **KeyKeeper2** использует **FreeRTOS** как основу многозадачной архитектуры.

Многозадачность построена на независимых сервисах, взаимодействующих через EventBus и очереди сообщений. Такой подход обеспечивает модульность, низкую связанность компонентов, предсказуемое поведение системы и соответствует общей компонентной архитектуре проекта.
