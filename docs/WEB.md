# 1. Purpose

Настоящий документ определяет архитектуру веб-подсистемы проекта **KeyKeeper2**.

Документ описывает:

- архитектуру Web UI;
- работу WiFiService;
- работу WebService;
- REST API;
- Captive Portal;
- требования безопасности;
- взаимодействие с другими компонентами проекта.

- ARCHITECTURE.md
- SOFTWARE.md

- STORAGE.md

# 2. Web Overview

Устройство предоставляет встроенный веб-интерфейс для локального управления.

Web UI предназначен исключительно для работы внутри локальной сети или через точку доступа устройства.

Использование облачных сервисов не предусмотрено.

---

## Supported Features

Web-интерфейс поддерживает:

- просмотр записей;
- создание записей;
- редактирование записей;
- удаление записей;
- поиск;
- импорт;
- экспорт;
- резервное копирование;
- восстановление;
- изменение настроек устройства.

---

## Non-Goals

Web-подсистема не отвечает за:

- хранение данных;
- проверку PIN;
- генерацию OTP;
- управление GUI устройства.

Все перечисленные функции реализуются специализированными сервисами проекта.

---

# 3. Design Principles

Веб-подсистема строится на следующих принципах:

- Component Isolation;
- Security First;
- REST Architecture;
- Event-Driven Architecture;
- Documentation First.

---

## Local First

Все операции выполняются локально.

Передача пользовательских данных через внешние серверы не допускается.

---

## Separation of Responsibilities

Подсистема разделена на два независимых компонента:

- WiFiService;
- WebService.

Каждый компонент имеет собственную область ответственности.

---

# 4. Architecture

Веб-подсистема располагается в отдельных компонентах проекта.

```text
components/

wifi/
web/
```

Типовая схема взаимодействия:

```text
Browser

↓

Wi-Fi

↓

WebService

↓

EventBus

↓

VaultService

↓

StorageService
```

GUI устройства не взаимодействует с браузером напрямую.

Все запросы проходят через сервисный слой.

---

## Component Responsibilities

### WiFiService

Отвечает за:

- запуск Wi-Fi;
- остановку Wi-Fi;
- режим Access Point;
- режим Station;
- управление подключениями.

---

### WebService

Отвечает за:

- HTTP Server;
- REST API;
- обработку запросов;
- генерацию ответов;
- Web UI;
- публикацию событий.

---

# 5. WiFiService

WiFiService управляет всеми функциями беспроводной сети.

Он является единственной точкой доступа к возможностям Wi-Fi.

---

## Responsibilities

WiFiService отвечает за:

- инициализацию Wi-Fi;
- выбор режима работы;
- управление точкой доступа;
- подключение к существующей сети;
- мониторинг состояния соединения.

---

## Supported Modes

Поддерживаются следующие режимы:

- Access Point;
- Station.

Одновременная работа в режиме AP+STA может быть добавлена в будущем.

---

## Connection Management

WiFiService должен отслеживать:

- состояние подключения;
- количество клиентов;
- параметры сети;
- изменение IP-адреса.

Изменение состояния сопровождается публикацией соответствующих событий.

---

# 6. WebService

WebService обеспечивает взаимодействие между браузером пользователя и внутренними сервисами проекта.

Он не содержит бизнес-логики и не работает напрямую с базой данных.

---

## Responsibilities

WebService отвечает за:

- запуск HTTP-сервера;
- регистрацию обработчиков;
- обслуживание Web UI;
- обработку REST-запросов;
- формирование HTTP-ответов.

---

## Request Processing

Каждый запрос проходит одинаковый жизненный цикл:

```text
HTTP Request

↓

WebService

↓

SecurityService

↓

EventBus

↓

Target Service

↓

HTTP Response
```

WebService не принимает решений о доступе к данным и не обходит SecurityService.

---

# 7. REST API

WebService предоставляет REST API для взаимодействия Web UI с внутренними сервисами проекта.

REST API является единственным способом доступа веб-интерфейса к функциональности устройства.

---

## Design Principles

REST API строится на следующих принципах:

- Stateless;
- JSON Only;
- Security First;
- Component Isolation.

Каждый запрос должен быть независимым и содержать всю необходимую информацию.

---

## Supported Operations

REST API поддерживает операции:

- получение списка записей;
- получение информации о записи;
- создание записи;
- изменение записи;
- удаление записи;
- поиск;
- резервное копирование;
- восстановление;
- изменение настроек.

---

## Response Format

Все ответы возвращаются в формате JSON.

Типичный ответ:

```json
{
    "status": "ok",
    "data": { }
}
```

При возникновении ошибки:

```json
{
    "status": "error",
    "message": "Permission denied"
}
```

---

## Versioning

REST API должен поддерживать версионирование.

Рекомендуемый формат:

```text
/api/v1/
```

Изменения, нарушающие совместимость, должны сопровождаться увеличением версии API.

---

# 8. Captive Portal

При работе устройства в режиме Access Point поддерживается Captive Portal.

---

## Purpose

Captive Portal обеспечивает автоматическое открытие Web UI после подключения пользователя к точке доступа устройства.

---

## Workflow

Типичный сценарий:

```text
Client

↓

Connect to Wi-Fi

↓

Captive Portal

↓

Browser

↓

Web UI
```

Пользователю не требуется вручную вводить IP-адрес устройства.

---

## Availability

Captive Portal работает только в режиме Access Point.

В режиме Station веб-интерфейс доступен по IP-адресу устройства в локальной сети.

---

# 9. Authentication & Security

Все операции Web UI должны соответствовать требованиям подсистемы безопасности.

---

## SecurityService

WebService не выполняет:

- проверку PIN;
- управление сессией;
- контроль разрешений.

Все проверки выполняются через **SecurityService**.

---

## Protected Operations

К защищённым относятся:

- просмотр конфиденциальных данных;
- изменение записей;
- удаление записей;
- импорт;
- экспорт;
- резервное копирование;
- восстановление.

---

## Session Management

После успешной аутентификации создаётся пользовательская сессия.

При завершении сессии доступ к защищённым операциям автоматически прекращается.

---

## HTTPS

На текущем этапе проекта взаимодействие предполагается только в доверенной локальной сети.

Поддержка HTTPS рассматривается как возможное направление дальнейшего развития.

---

# 10. EventBus Integration

WebService взаимодействует с другими компонентами исключительно через **EventBus**.

---

## Published Events

WebService публикует события:

- WebServerStarted;
- WebServerStopped;
- ApiRequestReceived;
- ClientConnected;
- ClientDisconnected;
- WebError.

---

## Subscribed Events

WebService может подписываться на события:

- DatabaseLoaded;
- DatabaseSaved;
- SessionUnlocked;
- SessionLocked;
- ConfigurationChanged;
- ShutdownRequested.

---

## Processing

Полученные события используются для обновления состояния Web UI и синхронизации работы с другими компонентами.

---

# 11. Performance

Web-подсистема должна обеспечивать стабильную работу без влияния на основные функции устройства.

---

## Requirements

При реализации необходимо:

- минимизировать использование оперативной памяти;
- использовать потоковую передачу данных при необходимости;
- избегать блокирующих операций;
- быстро освобождать временные ресурсы.

---

## Responsiveness

Длительные операции, такие как импорт, экспорт или резервное копирование, не должны блокировать обработку новых HTTP-запросов.

При необходимости они должны выполняться в отдельных задачах FreeRTOS с уведомлением пользователя о ходе выполнения.

---

# 12. Future Extensions

Архитектура Web-подсистемы должна предусматривать возможность дальнейшего развития.

Планируемые направления:

- HTTPS;
- WebSocket;
- OTA Update;
- управление несколькими устройствами;
- расширенный REST API;
- OpenAPI (Swagger) документация;
- поддержка Progressive Web App (PWA);
- локализация Web UI.

Все новые функции должны быть реализованы без нарушения существующего публичного API WebService.

---

# 13. Summary

Подсистема **Web** обеспечивает современный локальный веб-интерфейс для управления устройством **KeyKeeper2**, сохраняя полное соответствие архитектурным принципам проекта.

Функции беспроводной сети реализуются компонентом **WiFiService**, а обработка HTTP-запросов и REST API — компонентом **WebService**. Все обращения к данным и защищённым операциям выполняются через **SecurityService**, **EventBus** и соответствующие сервисы, что исключает прямые зависимости между компонентами.

Такое разделение ответственности обеспечивает модульность, безопасность, простоту сопровождения и возможность дальнейшего развития Web-подсистемы без изменения её архитектурных основ.
