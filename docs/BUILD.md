# 1. Purpose

Настоящий документ описывает процесс сборки, настройки и разработки проекта **KeyKeeper2**.

Документ предназначен для:

- подготовки среды разработки;
- сборки проекта;
- прошивки устройства;
- отладки;
- сопровождения проекта.

BUILD.md является дополнением к документам:

- SOFTWARE.md
- CODING_STYLE.md

# 2. Supported Environment

Проект разрабатывается исключительно с использованием официального **ESP-IDF**.

Использование Arduino Framework не предусмотрено.

---

## Supported Versions

Поддерживаемые версии инструментов:

| Tool | Version |
|-------|----------|
| ESP-IDF | 5.5.x |
| C++ | C++20 |
| CMake | 3.24+ |
| Ninja | Latest |
| Python | 3.11+ |
| Git | Latest |

Использование других версий допускается только после проверки совместимости.

---

# 4. Install ESP-IDF

Среда разработки должна быть установлена в соответствии с официальной документацией ESP-IDF.

После установки рекомендуется проверить работоспособность команд:

```bash
idf.py --version
```

```bash
python --version
```

```bash
cmake --version
```

Все инструменты должны корректно определяться из командной строки.

# 5. Project Structure

Основная структура проекта:

```text
KeyKeeper2/

components/
docs/
developer/
hardware/
icons/
main/
managed_components/
partitions/
```

---

## Components

Все функциональные модули располагаются в каталоге:

```text
components/
```

Каждый компонент имеет собственный каталог и независимый `CMakeLists.txt`.

Пример:

```text
components/

gui/
storage/
vault/
security/
usb/
wifi/
web/
settings/
system/
bsp/
```

Новые компоненты должны соответствовать архитектуре проекта и быть описаны в документации.

---

## Documentation

Вся проектная документация располагается в каталоге:

```text
docs/
```

Документация должна обновляться одновременно с изменением архитектуры или функциональности проекта.

---

## Developer Notes

Материалы для разработчиков находятся в каталоге:

```text
developer/
```

Эти документы содержат рекомендации по использованию отдельных технологий проекта (ESP-IDF, LVGL, FreeRTOS, Storage, USB, Wi-Fi и других).

# 6. Build Configuration

Конфигурация проекта определяется средствами ESP-IDF.

Основные файлы конфигурации:

```text
sdkconfig

sdkconfig.defaults

CMakeLists.txt
```

---

## sdkconfig.defaults

Файл `sdkconfig.defaults` содержит рекомендуемые параметры конфигурации проекта.

Он должен использоваться как базовая конфигурация при первой сборке.

Изменение этого файла должно выполняться только при необходимости и сопровождаться обновлением документации.

---

## CMake

Все компоненты проекта подключаются через систему CMake.

Каждый компонент обязан содержать собственный файл:

```text
CMakeLists.txt
```

Сборочная система автоматически обнаруживает компоненты, расположенные в каталоге `components/`.

---

# 7. Build Types

Проект поддерживает несколько типов сборки.

---

## Debug

Используется во время разработки.

Особенности:

- расширенное журналирование;
- дополнительные проверки;
- символы отладки;
- максимальная информативность.

---

## Release

Используется для публикации прошивки.

Особенности:

- отключение лишнего журналирования;
- оптимизация размера;
- оптимизация производительности;
- отсутствие отладочной информации.

Переход между режимами сборки должен выполняться средствами ESP-IDF без изменения исходного кода.

---

# 8. Build Commands

Все операции сборки выполняются с использованием утилиты `idf.py`.

---

## Configure Target

Перед первой сборкой необходимо выбрать целевую платформу.

```bash
idf.py set-target esp32s3
```

Эта команда создаёт необходимую конфигурацию проекта.

---

## Full Build

Полная сборка проекта:

```bash
idf.py build
```

В результате создаются:

- загрузчик;
- таблица разделов;
- основная прошивка.

---

## Clean Build

Очистка каталога сборки:

```bash
idf.py clean
```

Полное удаление результатов сборки:

```bash
idf.py fullclean
```

После `fullclean` рекомендуется выполнить повторную сборку проекта.

---

## Reconfigure

При изменении структуры проекта рекомендуется выполнить:

```bash
idf.py reconfigure
```

Это позволяет пересоздать конфигурацию CMake без удаления остальных файлов сборки.

---

# 9. Flashing

После успешной сборки прошивка может быть записана в устройство.

---

## Flash Firmware

```bash
idf.py flash
```

Если устройство подключено к единственному последовательному порту, дополнительных параметров не требуется.

---

## Specify Serial Port

При необходимости можно явно указать последовательный порт.

Например:

```bash
idf.py -p COM5 flash
```

или

```bash
idf.py -p /dev/ttyUSB0 flash
```

---

## Flash and Monitor

Для прошивки и одновременного открытия терминала:

```bash
idf.py flash monitor
```

---

## Erase Flash

Полная очистка Flash-памяти:

```bash
idf.py erase-flash
```

После очистки требуется повторная запись прошивки.

---

# 10. Serial Monitor

ESP-IDF предоставляет встроенный последовательный терминал.

---

## Start Monitor

```bash
idf.py monitor
```

---

## Exit Monitor

Для выхода из терминала используется стандартная комбинация клавиш ESP-IDF.

---

## Logging

Проект использует встроенную систему журналирования ESP-IDF.

Во время разработки рекомендуется использовать уровни:

- Error;
- Warning;
- Info;
- Debug (при необходимости).

Уровень журналирования определяется конфигурацией проекта.

---

# 11. Debugging

Проект поддерживает программную отладку средствами ESP-IDF.

---

## Supported Methods

Рекомендуется использовать:

- встроенный логгер ESP-IDF;
- GDB;
- JTAG (при наличии аппаратной поддержки).

---

## Debug Build

Для режима Debug рекомендуется:

- включить символы отладки;
- использовать расширенное журналирование;
- отключить оптимизации, затрудняющие анализ кода.

Конкретные параметры определяются конфигурацией ESP-IDF.

# 12. Continuous Integration

Проект должен быть готов к использованию систем непрерывной интеграции (CI).

---

## CI Goals

Автоматическая сборка должна проверять:

- успешную компиляцию;
- отсутствие ошибок CMake;
- корректность структуры проекта;
- отсутствие предупреждений высокого уровня (по возможности).

## Future Integration

В дальнейшем может быть добавлена поддержка:

- GitHub Actions;

- убедиться в успешной сборке проекта;
- проверить отсутствие ошибок компиляции;

- при необходимости добавить новый ADR.

# 14. Release Build

Перед выпуском новой версии необходимо выполнить полный цикл проверки.

---

## Release Checklist

Рекомендуется убедиться, что:

- проект собирается без ошибок;
- отсутствуют критические предупреждения;
- документация актуальна;
- версия прошивки обновлена;
- версия базы данных соответствует документации;
- изменения отражены в Roadmap и ADR (при необходимости).

---

## Release Artifacts

Для каждого релиза рекомендуется формировать:

- файл прошивки (`.bin`);
- таблицу разделов;
- загрузчик;
- контрольные суммы (Checksum);
- краткое описание изменений (Release Notes).

---

# 15. Troubleshooting

Наиболее распространённые проблемы при сборке и способы их решения.

---

## CMake Configuration Error

Если CMake не обнаруживает новые компоненты:

```bash
idf.py reconfigure
```

или

```bash
idf.py fullclean
idf.py build
```

---

## Build Failed

Рекомендуется проверить:

- установленную версию ESP-IDF;
- активированное окружение ESP-IDF;
- корректность `sdkconfig`;
- наличие всех компонентов проекта.

---

## Flash Failed

Проверить:

- подключение USB;
- выбранный COM-порт;
- наличие питания устройства;
- режим загрузчика ESP32-S3.

---

## Component Not Found

Необходимо убедиться, что:

- компонент расположен в каталоге `components/`;
- присутствует файл `CMakeLists.txt`;
- структура каталога соответствует архитектуре проекта.

---

# 16. Summary

Проект **KeyKeeper2** использует стандартную систему сборки **ESP-IDF** и **CMake**, что обеспечивает переносимость, воспроизводимость и совместимость с официальной экосистемой Espressif.

Процесс разработки основан на принципах **Documentation First** и **Architecture Before Code**. Все изменения должны сопровождаться успешной сборкой, тестированием и актуализацией документации.

Следование рекомендациям настоящего документа позволяет поддерживать единый процесс разработки, упрощает подключение новых участников проекта и обеспечивает стабильность сборки на всех этапах жизненного цикла программного обеспечения.
