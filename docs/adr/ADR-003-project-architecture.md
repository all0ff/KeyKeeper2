# ADR-003 — Project Architecture

**Status:** Accepted

**Date:** YYYY-MM-DD

**Version:** 2.0

---

# Context

Проект **KeyKeeper2** представляет собой встроенную систему, объединяющую графический интерфейс, защищённое хранилище данных, USB HID, Web UI, Wi-Fi, файловую систему и подсистему безопасности.

По мере развития проекта количество функциональных модулей значительно увеличивается. Использование монолитной архитектуры или тесно связанных компонентов приводит к усложнению сопровождения, снижению повторного использования кода и увеличению количества ошибок.

Для обеспечения масштабируемости, независимого развития компонентов и упрощения тестирования принято решение использовать компонентную архитектуру с сервисным слоем и событийной моделью взаимодействия.

---

# Decision

Проект строится как набор независимых компонентов.

Каждый компонент имеет:

* собственную область ответственности;
* минимальный публичный API;
* скрытую внутреннюю реализацию;
* независимый жизненный цикл.

Взаимодействие между компонентами осуществляется через **Service Layer** и **EventBus**.

---

# Architecture Overview

Основная структура компонентов:

```text
components/

app/
bsp/
gui/
security/
settings/
storage/
system/
usb/
vault/
web/
wifi/
```

Каждый компонент отвечает только за собственную функциональность.

---

# Component Responsibilities

## app

Главный компонент приложения.

Отвечает за:

* запуск системы;
* последовательность инициализации;
* управление жизненным циклом приложения.

---

## bsp

Board Support Package.

Предоставляет доступ к аппаратным ресурсам:

* дисплею;
* кнопкам;
* энкодеру;
* подсветке;
* другим периферийным устройствам.

---

## gui

Пользовательский интерфейс.

Отвечает за:

* экраны;
* навигацию;
* отображение данных;
* взаимодействие с пользователем.

GUI не содержит бизнес-логики и не обращается напрямую к подсистеме хранения данных.

---

## security

Подсистема безопасности.

Отвечает за:

* проверку PIN-кода;
* управление пользовательской сессией;
* автоблокировку;
* контроль разрешений;
* предоставление доступа к защищённым операциям.

---

## vault

Подсистема работы с пользовательскими данными.

Отвечает за:

* аккаунты;
* категории;
* OTP;
* поиск;
* избранное;
* операции с данными Vault.

---

## storage

Подсистема хранения данных.

Отвечает за:

* LittleFS;
* microSD;
* резервное копирование;
* импорт;
* экспорт;
* файловую систему.

---

## usb

Подсистема USB HID.

Отвечает за:

* передачу данных;
* эмуляцию HID-клавиатуры;
* пользовательские последовательности ввода.

---

## wifi

Подсистема беспроводной сети.

Отвечает за:

* режим Access Point;
* режим Station;
* управление соединениями.

---

## web

Веб-подсистема.

Отвечает за:

* HTTP Server;
* REST API;
* Captive Portal;
* Web UI.

---

## settings

Подсистема хранения настроек.

Отвечает за:

* параметры пользователя;
* язык;
* тему оформления;
* системные настройки.

---

## system

Инфраструктурный компонент.

Отвечает за:

* EventBus;
* Logger;
* общие сервисы системы.

---

# Communication Model

Компоненты должны взаимодействовать через сервисный слой и EventBus.

Типичная последовательность взаимодействия:

```text
GUI

↓

EventBus

↓

SecurityService

↓

VaultService

↓

StorageService
```

Прямые зависимости между независимыми компонентами должны быть сведены к минимуму.

---

# Rationale

Компонентная архитектура обеспечивает:

* слабую связанность компонентов;
* независимую разработку подсистем;
* простое модульное тестирование;
* удобство сопровождения;
* масштабируемость;
* повторное использование кода;
* соответствие принципам **Single Responsibility** и **Component Isolation**.

---

# Consequences

После принятия данного решения:

* все новые функции должны реализовываться внутри соответствующих компонентов;
* запрещается размещать бизнес-логику вне специализированных сервисов;
* новые компоненты должны проектироваться независимо от внутренней реализации существующих модулей;
* любые изменения архитектуры должны сопровождаться обновлением документации и, при необходимости, созданием нового ADR.

---

# Alternatives Considered

## Монолитная архитектура

Преимущества:

* простота первоначальной реализации;
* меньшее количество файлов.

Недостатки:

* высокая связанность компонентов;
* сложность сопровождения;
* ухудшение масштабируемости;
* затруднённое тестирование.

Данный вариант был отклонён.

---

## Многослойная архитектура без компонентного разделения

Позволяет разделить код по уровням, однако не обеспечивает достаточной независимости отдельных подсистем.

По мере роста проекта сопровождение такой архитектуры становится значительно сложнее.

# Summary

Проект **KeyKeeper2** использует компонентную архитектуру, основанную на независимых сервисах, событийной модели взаимодействия и строгом разделении ответственности.

Такой подход обеспечивает высокую масштабируемость, удобство сопровождения и позволяет развивать отдельные подсистемы независимо друг от друга, сохраняя единые архитектурные принципы проекта.
