# ADR-005 — Storage Provider

**Status:** Accepted

**Date:** YYYY-MM-DD

**Version:** 2.0

---

# Context

Проект **KeyKeeper2** использует несколько физических носителей данных и различных механизмов хранения информации.

В настоящее время поддерживаются:

* LittleFS во внутренней Flash-памяти;
* microSD;
* резервные копии;
* импорт и экспорт данных.

Бизнес-логика проекта не должна зависеть от конкретной реализации файловой системы или типа носителя.

Для обеспечения независимости компонентов необходимо использовать единый уровень абстракции доступа к данным.

---

# Decision

В проекте используется компонент **StorageProvider**, реализующий единый интерфейс доступа к данным независимо от физического носителя.

Все операции чтения и записи выполняются исключительно через StorageService и StorageProvider.

Ни один другой компонент не должен обращаться к файловой системе напрямую.

---

# Storage Architecture

Общая схема взаимодействия:

```text
GUI

↓

VaultService

↓

StorageService

↓

StorageProvider

↓

LittleFS / microSD
```

StorageProvider скрывает особенности конкретного носителя данных.

---

# Responsibilities

StorageProvider отвечает за:

* открытие файлов;
* создание файлов;
* чтение данных;
* запись данных;
* удаление файлов;
* получение информации о файлах;
* выбор используемого носителя.

StorageProvider не содержит бизнес-логики приложения.

---

# Supported Storage Backends

На текущем этапе проекта поддерживаются:

## LittleFS

Используется как основное внутреннее хранилище устройства.

Предназначено для:

* базы данных Vault;
* пользовательских настроек;
* служебных файлов.

---

## microSD

Используется для:

* резервного копирования;
* восстановления;
* импорта;
* экспорта;
* хранения дополнительных файлов пользователя.

---

# Storage Selection

Выбор физического носителя выполняет StorageService.

Остальные компоненты работают только с абстрактным интерфейсом StorageProvider и не знают, где фактически расположены данные.

---

# Public Interface

StorageProvider предоставляет единый набор операций.

Типичный интерфейс включает:

* Open();
* Close();
* Read();
* Write();
* Remove();
* Exists();
* CreateDirectory();
* ListFiles();
* GetFileInfo().

Конкретная реализация зависит от выбранного носителя.

---

# Rationale

Использование StorageProvider обеспечивает:

* независимость бизнес-логики от файловой системы;
* возможность замены носителя без изменения компонентов верхнего уровня;
* повторное использование кода;
* упрощение тестирования;
* единый API доступа к данным.

Это соответствует принципам **Component Isolation** и **Single Responsibility**.

---

# Consequences

После принятия данного решения:

* VaultService работает только через StorageService;
* StorageService использует StorageProvider;
* прямой доступ к LittleFS и microSD из других компонентов запрещён;
* добавление нового типа хранилища не требует изменения бизнес-логики приложения.

---

# Alternatives Considered

## Прямой доступ к LittleFS

Преимущества:

* простая реализация;
* меньше уровней абстракции.

Недостатки:

* сильная зависимость компонентов от файловой системы;
* невозможность прозрачной замены носителя;
* дублирование кода доступа к файлам.

Данный вариант был отклонён.

---

## Отдельная реализация для каждого компонента

Предполагалось, что каждый компонент самостоятельно работает с файловой системой.

Недостатки:

* повторение одинакового кода;
* сложность сопровождения;
* нарушение принципа единой ответственности.

Данный вариант также был отклонён.

# Summary

Проект **KeyKeeper2** использует **StorageProvider** как единый уровень абстракции для доступа к данным.

Такой подход изолирует бизнес-логику от конкретной файловой системы, упрощает сопровождение, облегчает тестирование и обеспечивает возможность расширения проекта за счёт поддержки новых типов хранилищ без изменения существующей архитектуры.
