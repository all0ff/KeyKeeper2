# ADR-007 — Account Model

**Status:** Accepted

**Date:** YYYY-MM-DD

**Version:** 2.0

---

# Context

Основной функцией проекта **KeyKeeper2** является безопасное хранение и использование учётных данных пользователя.

Для обеспечения единообразной работы всех компонентов необходимо определить единую модель представления записей (Account Model).

Модель должна использоваться всеми подсистемами проекта:

* VaultService;
* GUI;
* USBService;
* WebService;
* Backup;
* Import / Export;
* Search;
* Favorites.

Все операции с пользовательскими данными должны работать с одной и той же структурой.

---

# Decision

В проекте используется единая модель данных **Account**, представляющая одну запись хранилища.

Все сервисы работают исключительно с объектами данной модели.

Запрещается создавать альтернативные представления записи внутри отдельных компонентов.

---

# Account Structure

Каждая запись содержит стандартный набор полей.

Типичная структура включает:

* уникальный идентификатор;
* название записи;
* категорию;
* URL;
* имя пользователя;
* пароль;
* OTP Secret;
* заметки;
* признак «Избранное»;
* дату создания;
* дату изменения.

Дополнительные поля могут быть добавлены без нарушения совместимости модели.

---

# Responsibilities

## VaultService

Является владельцем модели Account.

Отвечает за:

* создание записей;
* изменение записей;
* удаление записей;
* поиск;
* генерацию OTP;
* проверку целостности данных.

---

## GUI

Использует модель только для отображения информации пользователю.

GUI не изменяет внутреннюю структуру объекта Account напрямую.

---

## USBService

Использует отдельные поля записи для передачи данных через USB HID.

USBService не хранит экземпляры Account и не изменяет их содержимое.

---

## WebService

Предоставляет доступ к данным Account через REST API.

Веб-интерфейс использует сериализованное представление модели.

---

## StorageService

Отвечает за сохранение и загрузку объектов Account.

Формат хранения не влияет на публичную модель данных.

---

# Data Ownership

Единственным владельцем объектов Account является **VaultService**.

Другие компоненты получают доступ к данным только через публичный API сервиса.

Это исключает появление нескольких независимых копий одной записи.

---

# Identification

Каждая запись должна иметь уникальный идентификатор.

Идентификатор используется для:

* поиска;
* обновления;
* удаления;
* синхронизации;
* импорта и экспорта.

Изменение идентификатора существующей записи не допускается.

---

# Search

Поиск осуществляется по данным модели Account.

Поиск может выполняться по:

* названию;
* имени пользователя;
* URL;
* категории;
* заметкам.

Механизм поиска является частью VaultService.

---

# Favorites

Признак «Избранное» является частью модели Account.

Подсистема GUI использует его только для отображения и фильтрации.

Логика хранения признака реализуется VaultService.

---

# OTP Support

Модель Account может содержать секрет TOTP.

Генерация одноразового пароля выполняется исключительно VaultService.

Другие компоненты не должны самостоятельно вычислять OTP.

---

# Rationale

Использование единой модели Account обеспечивает:

* единообразное представление данных;
* отсутствие дублирования структур;
* простую сериализацию;
* единый API для всех компонентов;
* упрощение сопровождения;
* расширяемость модели без изменения архитектуры.

---

# Consequences

После принятия данного решения:

* все операции выполняются через VaultService;
* компоненты не создают собственные модели записи;
* импорт, экспорт и резервное копирование используют одинаковую структуру данных;
* любые изменения модели Account должны сопровождаться обновлением документации и проверкой совместимости форматов хранения.

---

# Alternatives Considered

## Отдельные модели для каждого компонента

Рассматривалась возможность использования собственных структур данных в GUI, USB и Web.

Недостатки:

* дублирование кода;
* сложность синхронизации;
* увеличение количества преобразований данных;
* риск расхождения представлений одной записи.

Данный вариант был отклонён.

---

## Работа напрямую с форматом хранения

Рассматривалась возможность использования структуры базы данных в качестве модели приложения.

Недостатки:

* сильная зависимость бизнес-логики от формата хранения;
* сложность изменения структуры базы данных;
* нарушение принципа разделения ответственности.

Данный вариант также был отклонён.

# Summary

Проект **KeyKeeper2** использует единую модель данных **Account** для представления пользовательских записей.

Централизованное управление моделью через **VaultService** обеспечивает согласованность данных, упрощает взаимодействие между компонентами и позволяет развивать функциональность проекта без нарушения архитектурных принципов.
