# ADR-012 — Documentation First

**Status:** Accepted

**Date:** YYYY-MM-DD

**Version:** 2.0

---

# Context

Проект **KeyKeeper2** представляет собой долгосрочную разработку, включающую большое количество компонентов, сервисов и взаимосвязанных подсистем.

Разработка ведётся с использованием искусственного интеллекта, а также предполагает длительное сопровождение и возможное участие нескольких разработчиков.

При отсутствии единой актуальной документации возникают следующие проблемы:

* расхождение архитектуры и реализации;
* нарушение принципов проектирования;
* повторная реализация уже существующих решений;
* увеличение количества ошибок;
* сложность сопровождения и масштабирования проекта.

Для предотвращения этих проблем необходимо определить единый процесс разработки, в котором документация является первичным источником архитектурных решений.

---

# Decision

В проекте принимается принцип **Documentation First**.

Любое изменение архитектуры, интерфейсов компонентов, структуры данных или поведения системы должно быть сначала отражено в документации.

Только после утверждения документации допускается реализация программного кода.

# Documentation Responsibilities

## REQUIREMENTS.md

Определяет требования к системе.

Содержит:

* функциональные требования;
* нефункциональные требования;
* ограничения проекта;
* сценарии использования.

---

## ARCHITECTURE.md

Описывает архитектуру программного обеспечения.

Определяет:

* компоненты;
* сервисы;
* взаимодействие подсистем;
* архитектурные принципы.

---

## SOFTWARE.md

Определяет внутреннюю структуру реализации.

Содержит:

* описание сервисов;
* внутренние интерфейсы;
* модели данных;
* структуру каталогов;
* правила взаимодействия компонентов.

---

## Component Documentation

Документы отдельных подсистем:

* GUI.md;
* STORAGE.md;
* SECURITY.md;
* USB.md;
* WEB.md;
* EVENTS.md;
* BUILD.md;
* CODING_STANDARD.md.

Каждый документ описывает только собственную область ответственности.

---

## ADR

Architecture Decision Records фиксируют архитектурные решения проекта.

Каждый ADR отвечает на вопросы:

* какая проблема решалась;
* какое решение принято;
* почему выбран именно этот вариант;
* какие последствия имеет принятое решение.

ADR не заменяют основную документацию, а дополняют её.

# Development Workflow

Любая новая функциональность реализуется по следующей последовательности.

```text id="8znnzt"
Requirement

↓

Documentation

↓

Architecture Review

↓

Implementation

↓

Testing

↓

Documentation Update
```

Нарушение этой последовательности не допускается.

---

# Change Management

При изменении архитектуры необходимо:

1. Обновить REQUIREMENTS (если изменяются требования).
2. Обновить ARCHITECTURE.
3. Обновить SOFTWARE.
4. Обновить соответствующую компонентную документацию.
5. При необходимости создать новый ADR или обновить существующий.
6. Только после этого изменять исходный код.

---

# AI Development

Документация является основным источником информации при использовании искусственного интеллекта для разработки.

ИИ должен использовать:

* REQUIREMENTS.md;
* ARCHITECTURE.md;
* SOFTWARE.md;
* Component Documentation;
* ADR;
* AI_PROMPT.md.

Исходный код не должен использоваться как источник архитектурных решений, если они уже определены в документации.

---

# Rationale

Принцип **Documentation First** обеспечивает:

* единое понимание архитектуры проекта;
* согласованность между документацией и кодом;
* снижение количества ошибок;
* упрощение сопровождения;
* возможность безопасного использования ИИ при разработке;
* предсказуемость процесса внесения изменений.

---

# Consequences

После принятия данного решения:

* запрещается изменять архитектуру только в исходном коде;
* любые архитектурные изменения должны сопровождаться обновлением документации;
* новые компоненты должны быть описаны до начала их реализации;
* документация считается первичным источником архитектурной информации.

---

# Alternatives Considered

## Code First

Рассматривался подход, при котором сначала создаётся программный код, а документация оформляется позже.

Недостатки:

* быстрое устаревание документации;
* расхождение архитектуры и реализации;
* сложности сопровождения;
* высокий риск появления противоречий.

Данный вариант был отклонён.

---

## Documentation After Release

Предполагалось оформлять документацию только после завершения реализации функциональности.

Недостатки:

* потеря архитектурных решений;
* неполное описание системы;
* сложность последующего анализа изменений.

Данный вариант также был отклонён.

# Summary

Проект **KeyKeeper2** использует принцип **Documentation First**, согласно которому документация является первичным источником архитектурных решений и обязательной основой для разработки программного обеспечения.

Любые изменения требований, архитектуры или поведения системы сначала фиксируются в документации, затем проходят архитектурную проверку и только после этого реализуются в исходном коде. Такой подход обеспечивает согласованность проекта, упрощает сопровождение и делает процесс разработки предсказуемым как для разработчиков, так и для систем искусственного интеллекта.
