# ADR-008 — Security Model

**Status:** Accepted

**Date:** YYYY-MM-DD

**Version:** 2.0

---

# Context

Проект **KeyKeeper2** предназначен для хранения конфиденциальной информации пользователя, включая пароли, логины, URL, секреты TOTP и другие чувствительные данные.

Система предоставляет несколько способов доступа к данным:

* локальный графический интерфейс;
* USB HID;
* Web UI;
* резервное копирование;
* импорт и экспорт.

Использование нескольких точек доступа создаёт риск обхода механизмов защиты при реализации отдельных компонентов.

Для обеспечения единообразной модели безопасности необходимо централизовать все проверки доступа.

---

# Decision

В проекте используется единая централизованная модель безопасности.

Все проверки прав доступа выполняются исключительно компонентом **SecurityService**.

Ни один другой компонент не имеет права самостоятельно принимать решение о предоставлении доступа к защищённым данным.

---

# Security Architecture

Общая архитектура безопасности:

```text
User

↓

GUI / USB / Web

↓

SecurityService

↓

VaultService

↓

StorageService
```

Любая операция, связанная с конфиденциальными данными, проходит через SecurityService.

---

# Responsibilities

## SecurityService

SecurityService отвечает за:

* проверку PIN-кода;
* управление пользовательской сессией;
* автоматическую блокировку;
* контроль времени активности;
* проверку разрешений;
* предоставление доступа к защищённым операциям.

SecurityService является единственной точкой принятия решений о безопасности.

---

## VaultService

VaultService отвечает только за работу с данными.

Он не выполняет:

* проверку PIN;
* управление сессией;
* контроль времени активности.

---

## GUI

GUI отвечает исключительно за взаимодействие с пользователем.

GUI может инициировать запрос на разблокировку, но не принимает решений о доступе.

---

## USBService

USBService отвечает только за передачу данных через USB HID.

Он не знает:

* правильный ли PIN введён;
* разблокировано ли устройство;
* разрешена ли операция.

Передача данных возможна только после успешной проверки SecurityService.

---

## WebService

WebService отвечает за обработку HTTP-запросов.

Все защищённые операции выполняются только после успешной проверки SecurityService.

---

# Session Model

После успешного ввода PIN создаётся пользовательская сессия.

Пока сессия активна, разрешены защищённые операции.

После завершения сессии доступ автоматически прекращается.

---

## Session Lifecycle

```text
Locked

↓

PIN Verification

↓

Unlocked

↓

User Activity

↓

Timeout

↓

Locked
```

---

# Protected Operations

Проверка SecurityService обязательна для:

* просмотра паролей;
* передачи данных через USB;
* генерации OTP;
* изменения записей;
* удаления записей;
* импорта;
* экспорта;
* резервного копирования;
* восстановления.

---

# EventBus Integration

SecurityService взаимодействует с другими компонентами через EventBus.

Основные события:

* SessionUnlocked;
* SessionLocked;
* PinAccepted;
* PinRejected;
* SecurityTimeout.

Другие компоненты используют эти события для изменения своего состояния.

---

# Rationale

Централизация механизмов безопасности обеспечивает:

* единые правила проверки доступа;
* отсутствие дублирования логики;
* простоту сопровождения;
* возможность изменения политики безопасности в одном месте;
* уменьшение вероятности ошибок реализации.

Это соответствует принципам:

* Single Responsibility;
* Component Isolation;
* Security First.

---

# Consequences

После принятия данного решения:

* запрещается выполнять проверку PIN вне SecurityService;
* запрещается хранить состояние пользовательской сессии в других компонентах;
* все защищённые операции должны проходить через SecurityService;
* добавление новых способов доступа к данным требует интеграции с SecurityService.

---

# Alternatives Considered

## Проверка безопасности в каждом компоненте

Рассматривалась возможность реализации проверки PIN в GUI, USB и Web независимо.

Недостатки:

* дублирование кода;
* различное поведение компонентов;
* сложность сопровождения;
* высокий риск ошибок безопасности.

Данный вариант был отклонён.

---

## Проверка безопасности внутри VaultService

Рассматривалась возможность переноса логики безопасности в VaultService.

Недостатки:

* смешение ответственности;
* нарушение принципа Single Responsibility;
* невозможность использовать единые механизмы для Web UI, USB и других подсистем.

Данный вариант также был отклонён.

# Summary

Проект **KeyKeeper2** использует централизованную модель безопасности, основанную на компоненте **SecurityService**.

Все проверки прав доступа, управление пользовательской сессией и контроль защищённых операций выполняются исключительно этим сервисом. Такой подход обеспечивает единообразную реализацию механизмов безопасности, снижает связанность компонентов и полностью соответствует компонентной архитектуре проекта.
