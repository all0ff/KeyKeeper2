**Status:** Accepted

**Date:** YYYY-MM-DD

**Version:** 2.0

# Context

Проект **KeyKeeper2** представляет собой автономное устройство для безопасного хранения и использования конфиденциальных данных пользователя.

Система объединяет несколько функциональных подсистем:

* защищённое хранилище (Vault);
* графический пользовательский интерфейс;
* USB HID;
* Web UI;
* Wi-Fi;
* локальное хранение данных;
* систему безопасности.

Для обеспечения независимости компонентов и понятной архитектуры необходимо определить общий контекст приложения и границы ответственности каждой подсистемы.

---

# Decision

Архитектура приложения строится вокруг сервисного слоя, объединяющего независимые компоненты.

Каждая подсистема взаимодействует с другими исключительно через публичные интерфейсы сервисов и EventBus.

Бизнес-логика не должна располагаться в пользовательском интерфейсе или аппаратных драйверах.

---

Общая схема приложения:

```text id="n7bzxg"

├── SecurityService
```

Каждый уровень выполняет только собственные задачи.

---

# User Layer

Пользователь взаимодействует с устройством посредством:

* дисплея;
* энкодера;
* кнопок;
* USB HID;
* Web UI.

Ни один пользовательский интерфейс не содержит бизнес-логики.

---

# GUI Layer

GUI отвечает исключительно за отображение информации и обработку действий пользователя.

Основные функции:

* отображение экранов;
* навигация;
* отображение статуса системы;
* получение пользовательских команд.

GUI передаёт запросы через EventBus и не обращается напрямую к сервисам хранения данных.

---

# Service Layer

Сервисный слой реализует основную бизнес-логику проекта.

---

## SecurityService

Отвечает за:

* проверку PIN-кода;
* управление пользовательской сессией;
* автоблокировку;
* контроль доступа;
* авторизацию защищённых операций.

---

## VaultService

Отвечает за:

* работу с аккаунтами;
* категориями;
* избранным;
* поиском;
* генерацией OTP.

---

## StorageService

Отвечает за:

* сохранение данных;
* загрузку данных;
* резервное копирование;
* импорт;
* экспорт;
* файловую систему.

---

## USBService

Отвечает за:

* передачу данных через USB HID;
* выполнение последовательностей ввода;
* взаимодействие с TinyUSB.

---

## WebService

Отвечает за:

* HTTP Server;
* REST API;
* обработку Web UI;
* взаимодействие с браузером пользователя.

---

## WiFiService

Отвечает за:

* запуск Wi-Fi;
* Access Point;
* Station Mode;
* управление соединениями.

---

## SettingsService

Отвечает за:

* пользовательские настройки;
* язык интерфейса;
* тему оформления;
* системные параметры.

---

# Infrastructure Layer

Инфраструктурный слой обеспечивает общие механизмы работы приложения.

В него входят:

* EventBus;
* Logger;
* FreeRTOS;
* системные службы.

Инфраструктурный слой не содержит бизнес-логики.

# Design Principles

Контекст приложения строится на следующих принципах:

* Component Isolation;
* Single Responsibility;
* Service Layer;
* Event-Driven Architecture;
* Documentation First.

Каждый компонент должен выполнять только собственную область ответственности.

---

# Consequences

После принятия данного решения:

* пользовательские интерфейсы не содержат бизнес-логики;
* все операции проходят через сервисный слой;
* взаимодействие между компонентами осуществляется через EventBus и публичные API;
* новые функции должны интегрироваться в существующую архитектуру без нарушения её принципов.

---

# Alternatives Considered

## Монолитное приложение

Рассматривался вариант размещения всей логики в едином приложении без выделения сервисов.

Недостатки:

* высокая связанность компонентов;
* сложность сопровождения;
* невозможность независимого тестирования;
* увеличение количества архитектурных зависимостей.

Данный вариант был отклонён.

# Summary

Контекст приложения **KeyKeeper2** основан на разделении системы на независимые сервисы, взаимодействующие через EventBus и публичные интерфейсы.

Такой подход обеспечивает модульность, безопасность, масштабируемость и единообразную архитектуру всего проекта, а также упрощает дальнейшее сопровождение и развитие программного обеспечения.
