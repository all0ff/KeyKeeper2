# ADR-011 — Board Support Package

**Status:** Accepted

**Date:** YYYY-MM-DD

**Version:** 2.0

---

# Context

Проект **KeyKeeper2** разрабатывается для аппаратной платформы на базе **ESP32-S3** и использует различные периферийные устройства:

* TFT-дисплей;
* энкодер;
* кнопки;
* подсветку;
* USB;
* microSD;
* внутреннюю Flash-память;
* светодиодные индикаторы;
* другие аппаратные интерфейсы.

Если прикладные компоненты будут напрямую работать с аппаратурой, это приведёт к сильной связанности программного обеспечения с конкретной платой и значительно усложнит перенос проекта на другое оборудование.

Для обеспечения независимости архитектуры необходимо изолировать аппаратно-зависимый код.

---

# Decision

В проекте используется отдельный компонент **Board Support Package (BSP)**.

BSP является единственной подсистемой, имеющей прямой доступ к аппаратному обеспечению.

Все остальные компоненты взаимодействуют с аппаратурой исключительно через публичный API BSP.

---

# Architecture

Общая схема взаимодействия:

```text
Application

↓

GUI / USB / Storage / WiFi

↓

BSP

↓

ESP-IDF Drivers

↓

Hardware
```

BSP скрывает особенности конкретной аппаратной реализации.

---

# Responsibilities

Компонент BSP отвечает за:

* инициализацию аппаратных устройств;
* настройку GPIO;
* управление дисплеем;
* обработку кнопок;
* работу с энкодером;
* управление подсветкой;
* доступ к аппаратным интерфейсам;
* предоставление единого API верхнему уровню приложения.

---

# Hardware Abstraction

BSP реализует уровень аппаратной абстракции.

Прикладные компоненты не должны знать:

* номера GPIO;
* параметры SPI;
* конфигурацию дисплея;
* используемый драйвер подсветки;
* особенности конкретной ревизии платы.

Эти детали полностью скрываются внутри BSP.

---

# Display Support

BSP предоставляет интерфейс для работы с дисплеем.

Он отвечает за:

* инициализацию дисплея;
* настройку SPI (или другого интерфейса);
* управление подсветкой;
* взаимодействие с LVGL.

GUI работает только с API LVGL и не взаимодействует с аппаратным драйвером дисплея напрямую.

---

# Input Devices

BSP обрабатывает аппаратные устройства ввода:

* энкодер;
* кнопки;
* дополнительные органы управления.

После обработки аппаратных событий BSP передаёт их в систему через EventBus или соответствующие сервисы.

---

# Storage Interfaces

BSP отвечает только за инициализацию аппаратных интерфейсов хранения данных.

Например:

* SPI Flash;
* SDMMC;
* SPI для microSD.

Работа с файловой системой относится к компоненту StorageService.

---

# USB Support

BSP обеспечивает аппаратную инициализацию USB-контроллера.

Протокол USB HID реализуется компонентом USBService.

Такое разделение исключает смешение аппаратной и прикладной логики.

---

# Rationale

Использование BSP обеспечивает:

* независимость приложения от конкретной платы;
* простую замену аппаратной платформы;
* уменьшение связанности компонентов;
* единый механизм доступа к периферии;
* удобство тестирования;
* повторное использование кода.

Это соответствует принципам:

* Hardware Abstraction Layer;
* Single Responsibility;
* Component Isolation.

---

# Consequences

После принятия данного решения:

* прямой доступ к GPIO из прикладных компонентов запрещён;
* все аппаратно-зависимые операции реализуются только в BSP;
* изменение аппаратной платформы требует изменения только BSP;
* остальные компоненты проекта остаются неизменными.

---

# Alternatives Considered

## Прямой доступ компонентов к ESP-IDF

Рассматривалась возможность использования драйверов ESP-IDF непосредственно в GUI, USB и других компонентах.

Недостатки:

* сильная зависимость от аппаратной платформы;
* дублирование кода;
* усложнение сопровождения;
* невозможность простой замены аппаратной части.

Данный вариант был отклонён.

---

## Аппаратный код внутри каждого компонента

Предполагалось, что каждый компонент самостоятельно управляет необходимой периферией.

Недостатки:

* нарушение принципа единой ответственности;
* сложность сопровождения;
* увеличение количества зависимостей;
* риск конфликтов между компонентами.

Данный вариант также был отклонён.

# Summary

Проект **KeyKeeper2** использует отдельный компонент **Board Support Package (BSP)** в качестве уровня аппаратной абстракции.

BSP является единственной подсистемой, взаимодействующей с аппаратным обеспечением напрямую. Все остальные компоненты используют только его публичный API, что обеспечивает переносимость проекта, уменьшает связанность модулей и полностью соответствует компонентной архитектуре программного обеспечения.
