# KeyKeeper2 Software Requirements Specification

Version: 1.1.0

Status: Draft

---

# 1. Purpose

Настоящий документ определяет функциональные и нефункциональные требования к проекту **KeyKeeper2**.

Документ является основным источником требований для разработки программного обеспечения и служит базой для:

- архитектуры проекта;
- проектирования компонентов;
- разработки программного обеспечения;
- тестирования;
- подготовки пользовательской документации.

Любые изменения функциональности проекта должны сопровождаться обновлением данного документа.

---

# 2. Project Overview

## 2.1 General Description

KeyKeeper2 представляет собой автономный менеджер паролей на базе ESP32-S3 с аппаратным управлением при помощи энкодера и цветного дисплея.

Устройство предназначено для безопасного хранения учетных данных и быстрого ввода их на компьютере посредством USB HID Keyboard.

Все пользовательские данные хранятся локально.

Использование облачных сервисов не предусмотрено.

---

## 2.2 Main Features

Проект должен обеспечивать:

- хранение учетных записей;
- хранение URL;
- хранение имени пользователя;
- хранение пароля;
- хранение заметок;
- поддержку категорий;
- поддержку избранного;
- поддержку TOTP;
- поддержку HOTP;
- быстрый поиск;
- резервное копирование;
- импорт;
- экспорт;
- USB HID Keyboard;
- локальный Web UI;
- Wi-Fi Access Point;
- Captive Portal;
- современный графический интерфейс;
- поддержку нескольких языков.

---

## 2.3 Design Goals

Проект разрабатывается как профессиональный open-source проект.

Основные цели:

- высокая надежность;
- простота использования;
- безопасность хранения данных;
- модульная архитектура;
- расширяемость;
- длительная поддержка проекта;
- минимальное количество зависимостей.

---

# 3. Design Principles

При разработке должны использоваться следующие принципы.

- Documentation First
- Architecture Before Code
- Component-Based Architecture
- Event-Driven Architecture
- Security First
- SOLID
- DRY
- KISS
- RAII

Все изменения архитектуры должны сопровождаться обновлением документации и соответствующего ADR.

---

# 4. Software Architecture Requirements

Архитектура проекта должна быть построена на независимых компонентах.

Структура компонентов:

```text
components/

app/
bsp/
gui/
storage/
vault/
security/
usb/
wifi/
web/
settings/
system/
```

Каждый компонент должен:

- иметь собственную область ответственности;
- предоставлять публичный API;
- быть независимым от GUI;
- не иметь циклических зависимостей;
- взаимодействовать через сервисы или EventBus.

---

## 4.1 Service Layer

В проекте должны использоваться следующие основные сервисы.

```text
StorageService

VaultService

SecurityService

USBService

WiFiService

WebService

SettingsService

ThemeService

LanguageService
```

---

## 4.2 Event System

Компоненты должны взаимодействовать посредством централизованного EventBus.

Допускается:

- публикация событий;
- подписка на события;
- вызов публичных API.

Не допускается:

- доступ к внутренним данным других компонентов;
- использование глобальных объектов;
- циклические зависимости.

---

# 5. Hardware Requirements

Проект предназначен для аппаратной платформы ESP32-S3.

Минимальная конфигурация:

- ESP32-S3;
- встроенная Flash;
- PSRAM (при наличии);
- цветной TFT-дисплей;
- энкодер;
- кнопка энкодера;
- USB OTG;
- microSD;
- SPI Flash;
- Wi-Fi.

---

## 5.1 Supported Interfaces

Должны поддерживаться:

- SPI;
- I²C;
- GPIO;
- USB;
- UART;
- PWM.

---

## 5.2 Display

Требования:

- цветной дисплей;
- поддержка LVGL 9;
- аппаратная регулировка подсветки;
- плавная анимация;
- стабильная работа интерфейса.

---

## 5.3 Input Device

Основным устройством управления является энкодер.

Поддерживаются:

- вращение влево;
- вращение вправо;
- короткое нажатие;
- длинное нажатие.

Дополнительные кнопки не являются обязательными.

---

# 6. User Interface Requirements

Интерфейс должен быть полностью оптимизирован для управления энкодером.

Использование сенсорного экрана не является обязательным.

---

## 6.1 Main Screen

После загрузки устройства отображается стартовый экран.

Он должен обеспечивать быстрый доступ к двум действиям:

```text
Short BACK → Unlock

Long BACK → Print Password

Short OK → Print URL
```

После разблокировки пользователь получает доступ к основной базе учетных записей.

---

## 6.2 Navigation

Навигация должна быть максимально простой.

Поддерживаются:

- списки;
- меню;
- карточки;
- диалоги;
- подтверждения;
- сообщения.

Пользователь должен иметь возможность управлять устройством одной рукой.

---

## 6.3 Visual Style

Интерфейс должен использовать:

- темную тему;
- единый набор цветов;
- собственный набор монохромных пиктограмм;
- единый набор шрифтов;
- единый стиль элементов управления.

---

## 6.4 Localization

Интерфейс должен поддерживать несколько языков.

Минимально:

- English;
- Русский.

---

# 7. Account Management Requirements

Устройство должно поддерживать хранение большого количества учетных записей.

Каждая запись должна содержать:

- название;
- URL;
- логин;
- пароль;
- заметку;
- категорию;
- признак "Избранное";
- дату создания;
- дату изменения.

---

## 7.1 Search

Должен поддерживаться:

- быстрый поиск;
- фильтрация;
- категории;
- избранное.

---

## 7.2 OTP

Должна поддерживаться работа с:

- TOTP;
- HOTP.

При наличии OTP пользователь должен иметь возможность:

- просматривать код;
- отправлять код через USB.

---

# 8. USB Requirements

Устройство должно определяться компьютером как стандартная USB HID Keyboard.

Использование дополнительных драйверов не допускается.

---

## 8.1 Quick Screen

Стартовый экран должен обеспечивать быстрый ввод наиболее часто используемых данных.

Поддерживаются следующие действия:

```text
Short BACK → Unlock

Long BACK → Print Password

Short OK → Print URL
```

Если пароль по умолчанию отсутствует, команда Print Password не должна выполнять никаких действий.

---

## 8.2 USB Output

Поддерживается отправка:

- URL;
- логина;
- пароля;
- OTP.

Последовательность ввода должна быть полностью настраиваемой.

---

## 8.3 Timing

Должны настраиваться:

- задержка перед началом ввода;
- задержка между символами;
- задержка между полями.

---

# 9. Security Requirements

Безопасность является обязательной частью проекта.

Все защищённые операции должны выполняться только через SecurityService.

---

## 9.1 PIN

Устройство должно поддерживать PIN-код.

PIN используется для:

- разблокировки устройства;
- изменения настроек безопасности;
- доступа к защищённым операциям.

---

## 9.2 Lock

Должны поддерживаться:

- ручная блокировка;
- автоматическая блокировка;
- блокировка после включения устройства.

---

## 9.3 Permissions

Перед выполнением следующих действий должна выполняться проверка безопасности:

- Print Password;
- Print OTP;
- Export Vault;
- Change PIN;
- Restore Backup;
- Web Login.

---

## 9.4 Future Security

Архитектура должна предусматривать возможность добавления:

- AES-256 Encryption;
- Secure Element;
- нескольких пользователей;
- различных уровней доступа.

Добавление перечисленных возможностей не должно требовать изменения архитектуры проекта.

---

# 10. Storage Requirements

Все пользовательские данные должны храниться локально.

Использование облачных сервисов не допускается.

Storage Layer отвечает исключительно за хранение данных и не содержит бизнес-логики.

Подробная спецификация хранения определяется документом **STORAGE.md**.

---

## 10.1 Storage Backend

Поддерживаются:

- LittleFS;
- microSD.

Возможность выбора носителя должна определяться настройками проекта.

---

## 10.2 Backup

Должны поддерживаться:

- создание резервной копии;
- восстановление резервной копии;
- экспорт базы;
- импорт базы.

Все операции должны выполняться через StorageService.

---

# 11. Web Interface Requirements

Устройство должно предоставлять локальный Web UI для управления данными и настройками.

Web UI работает только внутри локальной сети и не использует внешние облачные сервисы.

Подробная спецификация приведена в документе **WEB.md**.

---

## 11.1 Access Modes

Должны поддерживаться:

- Wi-Fi Access Point;
- Wi-Fi Station;
- Captive Portal.

---

## 11.2 Web Functions

Через Web UI пользователь должен иметь возможность:

- просматривать учетные записи;
- создавать новые записи;
- редактировать записи;
- удалять записи;
- выполнять поиск;
- выполнять импорт;
- выполнять экспорт;
- создавать резервные копии;
- изменять настройки устройства.

---

## 11.3 Authentication

Доступ к Web UI должен требовать авторизации.

Авторизация должна использовать механизмы SecurityService.

После блокировки устройства Web UI также должен быть заблокирован.

---

## 11.4 REST API

Web UI должен использовать внутренний REST API.

REST API не должен обращаться напрямую к Storage.

Все операции выполняются через сервисный слой.

---

# 12. Settings Requirements

Все пользовательские настройки должны храниться централизованно.

Настройки доступны только через SettingsService.

---

## 12.1 General Settings

Должны поддерживаться:

- язык интерфейса;
- тема оформления;
- яркость дисплея;
- таймер отключения дисплея;
- таймер автоблокировки.

---

## 12.2 USB Settings

Должны настраиваться:

- пароль по умолчанию;
- последовательность печати;
- задержка перед вводом;
- задержка между символами;
- задержка между полями.

---

## 12.3 Security Settings

Должны поддерживаться:

- изменение PIN;
- длина PIN (4–6 цифр);
- включение Auto Lock;
- время Auto Lock;
- разрешения Web UI.

---

## 12.4 GUI Settings

Пользователь должен иметь возможность настроить:

- анимации;
- включение/отключение жестов;
- чувствительность энкодера (при необходимости);
- отображение подсказок.

---

# 13. Performance Requirements

Интерфейс должен работать плавно и отзывчиво.

---

## 13.1 GUI Performance

Требования:

- отсутствие заметных задержек;
- плавная прокрутка;
- плавные анимации;
- мгновенная реакция на действия пользователя.

---

## 13.2 Storage Performance

Операции поиска должны выполняться максимально быстро.

Повторное открытие базы данных должно использовать кэширование.

---

## 13.3 USB Performance

Передача данных должна происходить без пропуска символов.

USB HID должен корректно работать с Windows, Linux и macOS.

---

# 14. Memory Requirements

Программное обеспечение должно эффективно использовать ресурсы ESP32-S3.

---

## 14.1 RAM

Следует минимизировать:

- динамические выделения памяти;
- копирование объектов;
- создание временных буферов.

---

## 14.2 Flash

Структура проекта должна обеспечивать возможность добавления новых функций без существенного увеличения размера прошивки.

---

## 14.3 Cache

Допускается использование:

- GUI Cache;
- Vault Cache;
- Icon Cache.

Кэширование должно быть прозрачным для пользователя.

---

# 15. Reliability Requirements

Система должна корректно работать при длительной непрерывной эксплуатации.

---

## 15.1 Error Recovery

При возникновении ошибки приложение не должно аварийно завершаться.

При возможности должна выполняться автоматическая попытка восстановления.

---

## 15.2 Data Integrity

Все операции записи должны обеспечивать целостность данных.

При неожиданном отключении питания база данных не должна переходить в неконсистентное состояние.

---

## 15.3 Backup Reliability

Резервные копии должны проверяться перед восстановлением.

Повреждённые файлы не должны импортироваться.

---

# 16. Logging Requirements

Журналирование предназначено исключительно для диагностики.

---

## 16.1 Log Levels

Должны поддерживаться:

- Error;
- Warning;
- Info;
- Debug.

---

## 16.2 Sensitive Data

Запрещается выводить в журнал:

- PIN;
- пароль;
- OTP;
- секретные ключи;
- содержимое Vault.

---

# 17. Coding Requirements

---

- ESP-IDF 5.5.x.

## 17.3 GUI
