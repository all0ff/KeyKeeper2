# KeyKeeper2 Software Design Specification

Version: 2.0.0

Status: Draft

---

# Purpose

Данный документ определяет программную архитектуру проекта **KeyKeeper2**.

Он описывает внутреннее устройство программного обеспечения, взаимодействие компонентов, программные слои, основные сервисы и правила реализации.

Документ предназначен для разработчиков и является основой для написания программного кода.

В отличие от **ARCHITECTURE.md**, данный документ описывает не только структуру системы, но и принципы её работы.

---

# Software Overview

KeyKeeper2 представляет собой автономный менеджер паролей для ESP32-S3.

Основные возможности:

- безопасное хранение учётных записей;
- хранение TOTP/HOTP;
- USB HID Keyboard;
- современный GUI на LVGL 9;
- локальный Web UI;
- Wi-Fi Access Point;
- Captive Portal;
- импорт и экспорт базы данных;
- резервное копирование;
- работа полностью без облачных сервисов.

Программное обеспечение разрабатывается исключительно на **ESP-IDF 5.5.x**.

---

# Software Goals

Программная архитектура должна обеспечивать:

- модульность;
- расширяемость;
- повторное использование кода;
- независимость компонентов;
- простоту сопровождения;
- высокую производительность;
- минимальное потребление памяти;
- безопасность;
- возможность долгосрочного развития проекта.

---

# Design Principles

При разработке используются следующие принципы:

- Documentation First;
- Architecture Before Code;
- Component-Based Architecture;
- Event-Driven Architecture;
- Security First;
- SOLID;
- DRY;
- KISS;
- RAII.

Любое изменение архитектуры должно сопровождаться обновлением документации.

---

# Software Layers

Программное обеспечение разделено на независимые уровни.

```text
Application

↓

GUI Layer

↓

Service Layer

↓

Security Layer

↓

Storage Layer

↓

Board Support Package

↓

ESP-IDF
```

Каждый уровень взаимодействует только с соседним уровнем.

Обращение через несколько уровней запрещается.

---

# Component Overview

Программное обеспечение состоит из следующих компонентов.

```text
components/

app/
bsp/
gui/
storage/
vault/
security/
usb/
wifi/
web/
settings/
system/
```

Каждый компонент имеет собственную область ответственности и предоставляет только публичный API.

---

# Application Layer

Application Layer является верхним уровнем программной архитектуры.

Он отвечает за:

- запуск приложения;
- инициализацию компонентов;
- регистрацию сервисов;
- управление жизненным циклом системы;
- последовательность запуска;
- последовательность завершения работы.

Application Layer не содержит бизнес-логики.

---

## Responsibilities

Основные задачи:

- создание объектов;
- связывание компонентов;
- запуск сервисов;
- контроль состояния системы.

---

## Internal Structure

```text
Application

↓

Component Registration

↓

Service Registration

↓

System Startup

↓

Main Loop
```

---

# GUI Layer

GUI реализован полностью на **LVGL 9**.

GUI отвечает только за взаимодействие пользователя с устройством.

GUI не содержит:

- бизнес-логики;
- работы с файлами;
- криптографии;
- работы с USB;
- работы с Wi-Fi.

Все действия пользователя преобразуются в вызовы сервисов или события EventBus.

---

## GUI Components

Основные подсистемы GUI:

```text
ScreenManager

ThemeManager

Localization

WidgetFactory

DialogManager
```

---

## ScreenManager

Управляет жизненным циклом экранов.

Отвечает за:

- создание экранов;
- переключение экранов;
- навигацию;
- анимации.

---

## ThemeManager

Предоставляет:

- цвета;
- размеры;
- отступы;
- стили;
- шрифты;
- пиктограммы.

GUI не использует фиксированные значения цветов или размеров.

---

## Localization

Все строки приложения находятся в таблицах локализации.

GUI получает только идентификатор строки.

Добавление нового языка не требует изменения экранов.

---

## WidgetFactory

Отвечает за создание повторно используемых элементов интерфейса.

Например:

- кнопок;
- карточек аккаунтов;
- диалогов;
- строк меню;
- элементов списка.

---

## DialogManager

Управляет отображением:

- сообщений;
- подтверждений;
- предупреждений;
- информационных окон.

---

## GUI Navigation

Навигация между экранами выполняется через ScreenManager.

```text
Screen

↓

ScreenManager

↓

Presenter

↓

Service
```

Экран не взаимодействует с сервисами напрямую.

---

# Service Layer

Service Layer содержит всю бизнес-логику проекта.

Ни один другой уровень не должен реализовывать бизнес-правила.

---

## Main Services

```text
StorageService

VaultService

SecurityService

USBService

WiFiService

WebService

SettingsService

ThemeService

LanguageService
```

Каждый сервис отвечает только за одну область ответственности.

---

## StorageService

Отвечает за:

- открытие базы данных;
- сохранение данных;
- резервное копирование;
- импорт;
- экспорт.

StorageService является единственной точкой доступа к StorageProvider.

---

## VaultService

Отвечает за работу с учётными записями.

Основные функции:

- чтение;
- запись;
- поиск;
- категории;
- избранное;
- OTP;
- метаданные.

VaultService не занимается проверкой безопасности.

---

## SecurityService

Центральный сервис безопасности проекта.

Все защищённые операции проходят через него.

Отвечает за:

- проверку PIN;
- состояние Locked/Unlocked;
- Auto Lock;
- управление сессией;
- проверку разрешений.

---

## USBService

Предоставляет единый интерфейс работы с USB HID.

Отвечает за:

- печать URL;
- печать логина;
- печать пароля;
- печать OTP;
- очередь передачи;
- управление задержками.

Перед выполнением защищённых операций выполняется запрос к SecurityService.

---

## WiFiService

Инкапсулирует работу Wi-Fi.

Поддерживает:

- Access Point;
- Station;
- Captive Portal;
- сетевые настройки.

GUI не взаимодействует напрямую с ESP Wi-Fi.

---

## WebService

Предоставляет интерфейс для локального Web UI.

Отвечает за:

- REST API;
- Web Server;
- обработку запросов;
- авторизацию пользователей;
- взаимодействие с VaultService.

---

## SettingsService

Единая точка доступа к настройкам.

Использует NVS.

Все изменения параметров приложения выполняются только через SettingsService.

---

## ThemeService

Предоставляет информацию о текущей теме оформления.

GUI не хранит параметры оформления самостоятельно.

---

## LanguageService

Предоставляет локализованные строки интерфейса.

Поддерживает динамическое переключение языка без изменения логики GUI.

---

# Security Layer

Security Layer является самостоятельным уровнем программной архитектуры.

Все операции, связанные с конфиденциальными данными, проходят через SecurityService.

```text
GUI

↓

SecurityService

↓

Permission Check

↓

Vault / USB / Web
```

Ни один компонент не должен самостоятельно реализовывать проверки безопасности.

---

## Internal Structure

```text
SecurityService

├── PinManager

├── LockManager

├── SessionManager

└── PermissionManager
```

---

## SecurityService

Главная точка доступа к подсистеме безопасности.

Координирует работу всех внутренних менеджеров и предоставляет единый публичный API для остальных компонентов проекта.

---

## PinManager

Отвечает за:

- хранение параметров PIN;
- проверку PIN-кода;
- изменение PIN;
- контроль неверных попыток ввода.

---

## LockManager

Управляет состоянием устройства:

- Locked;
- Unlocked;
- Auto Lock;
- ручная блокировка.

---

## SessionManager

Отвечает за управление пользовательской сессией.

Подготавливает архитектуру к поддержке нескольких пользователей и Web-аутентификации.

---

## PermissionManager

Определяет возможность выполнения защищённых операций.

Например:

- Print Password;
- Print OTP;
- Export Vault;
- Change PIN;
- Web Login.

Все решения о предоставлении доступа принимаются только здесь.

---

# Storage Layer

Storage Layer отвечает исключительно за долговременное хранение данных.

Он полностью отделён от бизнес-логики и не содержит информации о структуре учётных записей.

```text
VaultService

↓

StorageProvider

↓

LittleFS / microSD
```

Storage Layer обеспечивает единый интерфейс хранения независимо от физического носителя.

Подробная спецификация приведена в документе **STORAGE.md**.

---

# Hardware Layer

Hardware Layer изолирует программную архитектуру от аппаратной платформы.

Все обращения к периферии проходят только через **Board Support Package (BSP)**.

```text
Application

↓

Services

↓

BSP

↓

ESP-IDF Drivers

↓

Hardware
```

---

## Board Support Package

BSP предоставляет единый интерфейс доступа к аппаратным ресурсам устройства.

Поддерживаемое оборудование:

- LCD Display;
- Touch (при наличии);
- Rotary Encoder;
- Buttons;
- Backlight;
- USB;
- SPI;
- I²C;
- Flash;
- LittleFS;
- microSD;
- RTC;
- GPIO.

При замене аппаратной платформы изменения должны ограничиваться компонентом BSP.

---

## BSP Responsibilities

Компонент отвечает за:

- инициализацию оборудования;
- настройку драйверов ESP-IDF;
- предоставление унифицированного API;
- обработку аппаратных событий;
- управление энергопотреблением.

BSP не содержит бизнес-логики приложения.

---

# Component Interaction

Компоненты взаимодействуют исключительно через публичные интерфейсы и EventBus.

```text
                GUI
                 │
       ┌─────────┼──────────┐
       ▼         ▼          ▼
 Security     Vault       Web
    │            │          │
    │            ▼          │
    │        Storage        │
    │                       │
    ├────────► USB          │
    │                       │
    └────────► Settings ◄───┘
                 │
                 ▼
              EventBus
```

Такая схема минимизирует связанность компонентов и облегчает сопровождение проекта.

---

## Communication Rules

Разрешено:

- вызов публичного API;
- публикация событий;
- подписка на события.

Запрещено:

- доступ к внутренним данным другого компонента;
- использование глобальных объектов вместо сервисов;
- циклические зависимости.

---

# Event Flow

Все события проходят через централизованный EventBus.

```text
Input

↓

GUI

↓

Service

↓

EventBus

↓

Subscribers
```

Примеры событий:

- DeviceLocked;
- DeviceUnlocked;
- PinChanged;
- AccountSelected;
- AccountUpdated;
- SettingsChanged;
- BackupStarted;
- BackupFinished;
- USBConnected;
- USBDisconnected;
- WiFiStarted;
- WiFiStopped.

Полный перечень событий приведён в документе **EVENTS.md**.

---

# Startup Sequence

Система запускается в строго определённом порядке.

```text
Power On

↓

Bootloader

↓

ESP-IDF

↓

BSP

↓

Settings

↓

Storage

↓

Security

↓

USB

↓

Wi-Fi

↓

GUI

↓

Application Ready
```

Каждый этап запуска выполняется только после успешной инициализации предыдущего.

При возникновении критической ошибки дальнейшая инициализация прекращается.

---

# Shutdown Sequence

При завершении работы выполняется обратная последовательность.

```text
Application

↓

GUI

↓

USB

↓

Wi-Fi

↓

Storage

↓

Settings

↓

BSP
```

Перед завершением должны быть сохранены все изменённые данные и корректно остановлены фоновые задачи.

---

# Thread Model

Программное обеспечение использует многозадачность FreeRTOS.

Предполагаемая структура задач:

```text
GUI Task

USB Task

Wi-Fi Task

Web Task

Storage Task

Security Task

Background Task
```

---

## GUI Task

Отвечает за:

- LVGL;
- обработку пользовательского ввода;
- анимации;
- обновление экранов.

---

## USB Task

Отвечает за:

- TinyUSB;
- очередь передачи;
- последовательную отправку данных.

---

## Wi-Fi Task

Обрабатывает:

- сетевые подключения;
- Captive Portal;
- сетевые события.

---

## Web Task

Обслуживает:

- HTTP Server;
- REST API;
- Web UI.

---

## Storage Task

Выполняет операции:

- чтения;
- записи;
- резервного копирования;
- импорта;
- экспорта.

Длительные операции хранения не должны блокировать GUI.

---

## Security Task

Отвечает за:

- Auto Lock;
- контроль времени бездействия;
- обработку запросов безопасности;
- управление пользовательской сессией.

---

## Background Task

Используется для фоновых операций, не требующих немедленного выполнения.

Например:

- очистка временных данных;
- обновление индексов;
- обслуживание очередей.

---

# Memory Model

Проект ориентирован на рациональное использование памяти ESP32-S3.

Используются следующие области памяти:

```text
Flash

↓

LittleFS

↓

NVS

↓

RAM

↓

Temporary Buffers
```

---

## RAM Allocation

Память условно разделяется на:

- GUI Cache;
- Vault Cache;
- Session Data;
- USB Queue;
- Temporary Buffers.

После завершения операции временные данные должны освобождаться.

---

## Secure Memory

Конфиденциальные данные не должны храниться в памяти дольше необходимого.

К таким данным относятся:

- PIN;
- пароли;
- OTP;
- секретные ключи.

После использования буферы должны очищаться.

---

## Dynamic Allocation

Использование динамической памяти допускается только там, где это действительно необходимо.

Предпочтительно:

- RAII;
- std::unique_ptr;
- std::vector;
- std::array.

Следует избегать частых операций выделения памяти в циклах.

---

# Error Handling

Каждый компонент обязан корректно обрабатывать ошибки.

Основные принципы:

- не завершать работу аварийно;
- возвращать информативный статус;
- сохранять согласованное состояние системы;
- публиковать события об ошибках при необходимости.

Критические ошибки должны фиксироваться в журнале.

---

## Error Categories

Ошибки разделяются на несколько категорий:

- Storage Errors;
- Security Errors;
- USB Errors;
- Network Errors;
- GUI Errors;
- Internal Errors.

Каждая категория должна иметь собственный набор кодов ошибок.

---

# Future Extensions

Архитектура программного обеспечения должна позволять добавление новых возможностей без изменения существующих компонентов.

Планируемые расширения:

- AES-256 Encryption;
- Secure Element;
- NFC;
- Bluetooth;
- OTA Updates;
- Multiple Vaults;
- Multi-User Support;
- User Macros;
- Plugin System;
- дополнительные языки интерфейса;
- новые темы оформления.

Все расширения должны интегрироваться через существующие сервисы и EventBus.

# Summary

Документ **SOFTWARE.md** определяет программную архитектуру проекта **KeyKeeper2** и описывает взаимодействие всех программных компонентов, сервисов и подсистем.

Архитектура построена на принципах **Documentation First**, **Component-Based Architecture**, **Event-Driven Architecture** и **Security First**, обеспечивая модульность, масштабируемость и простоту сопровождения.

Выделение самостоятельного уровня **Security Layer** позволяет централизовать управление безопасностью, исключить дублирование логики проверки доступа и подготовить проект к внедрению AES-256, Secure Element и многопользовательского режима без изменения существующей архитектуры.

Документ **SOFTWARE.md** является основой для реализации программной части проекта и должен поддерживаться в актуальном состоянии совместно с **ARCHITECTURE.md** и другими архитектурными документами.
